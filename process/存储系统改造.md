## 背景与动机

### 问题起源

commit `98f2a07` 添加了 `!tlb_fill_req` 门控修复 BRAM 碰撞，但导致 **13 个 MMU 测试 + 2 个特权测试** 大规模回归失败。基线 `a3d0dcb`（PTW 通过 dcache 重设计）是已知良好状态。

### 根因分析

MMU 原设计采用**双独立 FSM**（i-side + d-side），共享双端口 BRAM TLB：
- Port A: i-side 查找
- Port B: d-side 查找 + TLB fill 写入

**碰撞场景**：d-side 查找（Port B 读）与 TLB fill（Port B 写）在同一周期发生 → BRAM 输出未定义 → CPU 读到垃圾数据。

### 修复方案评估

Oracle 分析了 5 种方案：

| 方案 | 描述 | 评估 |
|------|------|------|
| (a) `!tlb_fill_req` 门控 | 碰撞时抑制 d-side 查找 | ❌ 导致大规模回归 |
| (b) 延迟 fill | 碰撞时推迟 fill 1 周期 | ⚠️ 复杂，fill 时序敏感 |
| (c) 双周期 fill | fill 拆为 read-then-write | ⚠️ 性能退化，逻辑复杂 |
| (d) 碰撞检测 + FSM 重定向 | 碰撞时 d-side 重做 lookup | ⚠️ 补丁式修复，不治本 |
| **(e) 取消 MMU 独立性** | **统一 FSM，CPU handshake 驱动** | **✅ 采用** |

### 最终方案：取消 MMU 独立性

**核心思想**：CPU 显式请求翻译 → MMU 阻塞直到完成 → 消除所有并发访问 bug。

**优势**：
- 移除 walk arbiter、collision detection、pending queue、i_miss/d_miss 信号 — 约 325 行逻辑
- BRAM 互斥由 FSM 保证：T_LOOKUP/T_RELOOKUP 用 Port A 读，T_FILL 用 Port B 写，永不重叠
- 架构简化，不再有碰撞类 bug

**代价**：
- i-side 和 d-side 不再并发翻译（项目不需要性能，可接受）
- fetch 需多周期 handshake（bare 模式 3 周期，TLB hit 4 周期，miss 更长）

## Phase 2: MMU.sv 统一翻译 FSM 重写

### 2.1 新接口设计

**输入（替换旧的 i_vaddr/i_translate_en/d_vaddr/d_access_type/d_translate_en）：**

| 信号 | 宽度 | 说明 |
|------|------|------|
| `translate_req` | 1 | CPU 请求翻译（保持至 done） |
| `translate_vaddr` | 32 | 虚拟地址 |
| `translate_access` | 2 | 00=FETCH, 01=LOAD, 10=STORE |
| `translate_priv` | 2 | 当前特权级 |
| `translate_satp` | 32 | 当前 satp CSR |
| `translate_sum` | 1 | mstatus.SUM |
| `translate_mxr` | 1 | mstatus.MXR |

**输出：**

| 信号 | 宽度 | 说明 |
|------|------|------|
| `translate_done` | 1 | 翻译完成（1 周期脉冲） |
| `translate_paddr` | 32 | 物理地址（done 时有效） |
| `translate_fault` | 1 | 页错误 / 访问错误 |
| `translate_cause` | 4 | 异常 cause 码 |
| `translate_vaddr_out` | 32 | 错误虚拟地址 |

**向后兼容输出（保留，供 icache/dcache/cpu_csr 使用）：**

- `i_paddr` = `translate_paddr`
- `i_ready` = `translate_done && !translate_fault`
- `i_miss` = 0（恒零）
- `i_page_fault`, `i_pf_cause`, `i_pf_vaddr`
- `d_paddr`, `d_ready`, `d_miss`=0, `d_page_fault`, `d_pf_cause`, `d_pf_vaddr`（同上）

### 2.2 统一 FSM 状态

```
T_IDLE → T_LOOKUP → T_CHECK → T_WALK → T_FILL → T_RELOOKUP → T_RECHECK → T_DONE/T_FAULT
                                                                              ↑
                                                                         T_FLUSH
```

| 状态 | 说明 | BRAM 端口使用 |
|------|------|---------------|
| T_IDLE | 等待 translate_req 或 flush | — |
| T_LOOKUP | 发起 TLB Port A 读（BRAM 1 周期延迟） | Port A 读 |
| T_CHECK | TLB 输出有效，判断 hit/miss/fault | — |
| T_WALK | PTW 遍历页表 | — |
| T_FILL | 写入 filled PTE 到 TLB Port B | **Port B 写** |
| T_RELOOKUP | fill 后重新发起 TLB Port A 读 | Port A 读 |
| T_RECHECK | 重新检查 lookup 结果 | — |
| T_DONE | 翻译成功，translate_done 脉冲 | — |
| T_FAULT | 翻译错误，translate_done + translate_fault 脉冲 | — |
| T_FLUSH | TLB 刷新中 | Port B 写 |

**互斥保证**：T_LOOKUP/T_RELOOKUP 仅用 Port A 读，T_FILL 仅用 Port B 写，永不重叠。

### 2.3 关键设计决策

- **latched_sv32** = `latched_satp[31] && (latched_priv_mode != PRIV_M)` — M 模式或 satp=0 时直接走 bare 模式
- **PTW 接口不变** — 输入直接从 latched 值取，无 arbiter mux
- **satp_changed 检测保留** — 任何 satp 写入刷新 TLB（含 M 模式）
- **sfence_vma** 触发 T_FLUSH 状态
- **d_lookup_req = 0** — Port B 永不读，仅用于 fill 写

### 2.4 代码统计

| 指标 | 旧 | 新 | 变化 |
|------|----|----|------|
| 总行数 | 745 | 604 | -141 (-19%) |
| FSM 数量 | 2 (i-side + d-side) | 1 (统一) | -1 |
| walk arbiter | 有 | 无 | 移除 |
| collision detection | 有 | 无 | 移除 |
| pending queue | 有 | 无 | 移除 |

## Phase 3: core_top.sv + cpu_controller.sv 重接线

### 3.1 core_top.sv 修改

**新增信号：**

```systemverilog
wire        mmu_translate_req;
wire [31:0] mmu_translate_vaddr;
wire [1:0]  mmu_translate_access;
wire        mmu_translate_done;
wire [31:0] mmu_translate_paddr;
wire        mmu_translate_fault;
wire [3:0]  mmu_translate_cause;
wire [31:0] mmu_translate_vaddr_out;
wire [31:0] mmu_inst_paddr;    // ⚠ 必须声明为 [31:0]，否则默认 1-bit 导致 CPU 死锁
wire [31:0] mmu_data_paddr;
```

**translate_req 逻辑：**

```systemverilog
assign mmu_translate_req    = if_valid || (mem_valid && mem_en);
assign mmu_translate_vaddr  = if_valid ? fetch_vaddr : mem_dataAddr_32;
assign mmu_translate_access = if_valid ? 2'b00 : (mem_hwrite ? 2'b10 : 2'b01);
```

**结果路由：**

```systemverilog
assign mmu_inst_paddr       = mmu_translate_paddr;
assign mmu_data_paddr       = mmu_translate_paddr;
assign mmu_inst_ready       = mmu_translate_done && !mmu_translate_fault;
assign mmu_data_ready       = mmu_translate_done && !mmu_translate_fault;
assign mmu_inst_page_fault  = mmu_translate_fault && if_valid;
assign mmu_data_page_fault  = mmu_translate_fault && mem_valid;
```

**MMU 实例更新：**
- 移除：`.i_vaddr`, `.i_translate_en`, `.d_vaddr`, `.d_access_type`, `.d_translate_en`
- 新增：`.translate_req`, `.translate_vaddr`, `.translate_access`, `.translate_priv(priv_mode)`, `.translate_satp(csr_satp)`, `.translate_sum(csr_mstatus[18])`, `.translate_mxr(csr_mstatus[19])`
- 新增输出：`.translate_done`, `.translate_paddr`, `.translate_fault`, `.translate_cause`, `.translate_vaddr_out`

**Bug 修复：** `mmu_inst_paddr` 和 `mmu_data_paddr` 必须声明为 `wire [31:0]`，否则 SystemVerilog 默认 1-bit wire → icache/dcache 收到 1-bit 地址 → CPU 完全死锁（x28=0, x29=0）。

### 3.2 cpu_controller.sv 修改

- 移除 `mmu_inst_miss` 输入端口
- 移除 `mmu_data_miss` 输入端口
- STATE_FETCH：移除 `mmu_inst_miss` stall 分支 → `fault → TRAP_ENTER, else if_done → DECODE`
- STATE_MEM：移除 `mmu_data_miss && mem_data_access` stall 分支 → `fault → TRAP_ENTER, else mem_done → WB`

### 3.3 无需修改的文件

| 文件 | 原因 |
|------|------|
| `icache_ctrl.sv` | `mmu_ready` 门控逻辑不变，兼容 1-cycle pulse |
| `dcache_ctrl.sv` | 同上 |
| `cpu_csr.sv` | page fault 通过 core_top 直连 trap controller，不经过 cpu_csr |
| `tlb.sv` | 双端口 BRAM 不变，Port B 永不读 |
| `ptw.sv` | 接口不变 |

## Phase 6: Bug 修复（2026-06-26）

### 6.1 icache stale refill response bug

**症状**：cache_fencei test 3 (test_fencei_preserve_data) 失败 — 4 个 store 到同一 cache line 后 fence.i，load 回来得到错误值。CPU 在 0x800000e0 取到 NOP (0x00000013) 而非正确指令。

**根因**：icache 在 `S_REFILL` 等待 refill 响应时，若 CPU 取指地址改变（`req_changed=1`），icache cancel refill 回到 `S_IDLE`。但 `cpu_bus_bridge` 不知道请求已取消，继续完成旧 AXI 读突发并置 `icache_refill_valid_r=1`。之后 icache 发出新 refill 请求（不同地址同 set），bridge 完成时 icache 误将旧数据当作新地址数据接受。

**具体场景**：
1. Icache miss at 0x800030E0 (set 7, tag 0x30) → S_REFILL
2. CPU 分支改变取指地址 → req_changed → icache cancel, 回 S_IDLE
3. Icache 处理新请求 → miss at 0x800000E0 (set 7, tag 0x00) → S_REFILL, latched_addr=0x800000E0
4. Bridge 完成旧的 0x800030E0 refill → icache_refill_valid_r=1
5. Icache 在 S_REFILL 看到 refill_valid=1，误将 0x800030E0 的 NOP 数据当作 0x800000E0 的指令 → CPU 执行 NOP 而非正确指令

**修复**（3 文件）：

| 文件 | 修改 | 说明 |
|------|------|------|
| `cpu_bus_bridge.sv` | +1 output port `icache_refill_resp_addr` | 暴露完成 refill 的基地址 |
| `icache_ctrl.sv` | +1 input `refill_resp_addr`, +`refill_addr_match` 验证 | 地址匹配才接受数据；stale 丢弃回 S_IDLE |
| `core_top.sv` | 连接新信号 | wire 声明 + 实例端口 |

**关键设计决策**：
- `refill_addr_match = (refill_resp_addr[31:5] == latched_addr[31:5])` — 比较 cache-line 对齐地址
- `bram_enb` 门控 `refill_addr_match` — stale 响应不写入数据 BRAM
- Stale 丢弃后回 `S_IDLE`（不是 `S_REFILL`）— 避免 `invalidate_req` 死锁（sfence.vma 等 icache_invalidate_done，icache 卡在 S_REFILL 则永远无法处理 invalidate）

### 6.2 MMU satp_changed 条件修复

**症状**：TC_MMU_035 失败 — M-mode 写 satp 后 TLB 不刷新，第二次翻译仍用旧页表根。

**根因**：`satp_changed = (satp != satp_prev) && (priv_mode != PRIV_M)` — M-mode 的 satp 写入被忽略。

**修复**：`satp_changed = (satp != satp_prev)` — 移除 `priv_mode != PRIV_M` 条件，任何 satp 变化都刷新 TLB。

### 6.3 exception_interrupt_basic 修复

**症状**：mtimecmp 写入 0 导致立即触发中断。

**修复**：mtimecmp 写入值改为 0xFFFFFFFF。

## 关键经验教训

### 1. SystemVerilog 隐式 wire 宽度

`mmu_inst_paddr` 和 `mmu_data_paddr` 未声明为 `wire [31:0]`，SystemVerilog 默认 1-bit wire。Vivado xvlog 仅报 INFO（`assumed default net type wire`），但 icache 收到 1-bit 地址导致 CPU 完全死锁。

**教训**：所有连续赋值的信号必须显式声明宽度和类型。可在文件头加 `` `default_nettype none `` 防止此类 bug。

### 2. 统一 FSM 的 translate_req 保持问题

`translate_req = if_valid || (mem_valid && mem_en)` 在 CPU 停留在 FETCH/MEM 期间持续为高。MMU 完成翻译后回到 T_IDLE 会立即重新翻译。这不是 bug（icache/dcache 会捕获 translate_done 脉冲），但增加了不必要的 TLB 查找。

**潜在优化**：添加 `translate_ack` 握手，CPU 收到 `translate_done` 后拉低 `translate_req`，避免重复翻译。

### 3. icache/dcache 对 pulse 型 mmu_ready 的兼容性

原设计中 `mmu_inst_ready` 是电平信号（bare 模式下恒 1），新设计中变为 1-cycle 脉冲。icache_ctrl.sv 的 `mmu_ready` 门控逻辑兼容脉冲（在 S_IDLE 和 S_TAG_READ 状态检查），无需修改。

### 4. icache refill cancel 后的 stale response 问题

icache cancel refill（req_changed）后，cpu_bus_bridge 不知道请求已取消，仍会完成旧的 AXI 读突发。icache 必须验证 refill 响应地址匹配当前请求，否则丢弃。这是 AXI 总线共享（icache + dcache 共用 bridge）的固有问题 — 请求方 cancel 后响应方无法感知。

**教训**：共享总线协议中，请求方 cancel 必须有机制通知响应方，或响应必须携带足够信息供请求方验证。

## Phase 6: PTW-cache 时序 bug 修复 + 全面回归验证

> 日期: 2026-06-27

### 背景

Phase 5 回归测试遗留 18 个失败（10 通过 / 18 失败）。本阶段完成全部排查与修复。

### 6.4 PTW-cache 接口时序 bug（dcache_ctrl.sv）

**症状**：15 个全系统测试失败（所有 MMU 全系统测试 + 所有特权测试 + cache_mmu_interact）。所有测试 `x28=0`（pass_count=0），`first_fail_id=1`。`privilege_priv_transition` 出现页错误风暴（PC=0x800002c0 反复触发 instruction page fault），日志达 48MB。

**根因**：

PTW 通过 dcache 读取 PTE。`ptw_req_ready_r` 在 `S_READ_HIT` 周期置位，但该寄存器信号在**下一周期**（`S_IDLE`）才对外生效。组合逻辑 `ptw_live_rdata` 只在 `state == S_READ_HIT` 或 `state == S_REFILL` 时返回有效数据，`S_IDLE` 时返回 `32'b0`：

```systemverilog
// BUG: S_IDLE 时 ptw_req_ready_r=1 但 ptw_live_rdata=0
wire [31:0] ptw_live_rdata = (state == S_READ_HIT) ? rdata_word :
                             (state == S_REFILL && refill_valid) ? refill_word :
                             32'b0;  // ← ptw_req_ready_r 生效时走到这里
```

时序图：
```
Cycle N  (S_READ_HIT):  rdata=正确PTE, ptw_req_ready_r<=1  ← 数据有效
Cycle N+1 (S_IDLE):     rdata=0x00000000, ptw_req_ready_r=1  ← ready拉高但数据变0
```

PTW 在 `ptw_cache_ready=1` 时采样 `ptw_cache_rdata`，读到全零 → V=0 → 页错误 → trap handler 地址也触发页错误 → 死循环。

CPU 读路径（`live_cpu_rdata`）已有 `bypass_data` 兜底，PTW 路径遗漏了。

**修复**（`dev/rtl/core/dcache_ctrl.sv`）：

```systemverilog
wire [31:0] ptw_live_rdata = (state == S_READ_HIT) ? rdata_word :
                             (state == S_REFILL && refill_valid) ? refill_word :
                             ptw_req_ready_r ? bypass_data : 32'b0;
```

### 8.2 修复细节

#### TB 误用 `check_mem_word`
三个 audit TB 都调用 `check_mem_word(addr, _val)` 期望把内存值返回到 `_val`。但 `check_mem_word` 是**比较器**——它把 `_val` 当作期望值进行比较，不回写实际值。结果 `_val` 保持未初始化值，所有子测试显示 UNRUN。

**修复**：改用直接 BRAM 读 `u_soc.sim_ram.u_axi_ram.BRAM[(addr - 0x80000000) / 4]`。

#### 缺 `fence.i`
dcache 是 write-back，`test_report` 写入的结果区数据在 dcache 脏行中未刷新到 BRAM。TB 读取 BRAM 看到的是旧值。

**修复**：在所有 3 个 audit 程序的 `test_report` 后添加 `fence.i`。

#### csr_bugs test_8 假设错误
test_8 假设 S-mode 写 `scounteren` 会触发非法指令异常。但 `scounteren` 是 SRW（Supervisor Read/Write）CSR，S-mode 写入是合法的。

**修复**：删除 test_8，EXPECTED_TOTAL 从 8 改为 7。

#### cpu_full 期望值过时
trap_handler 使用 mscratch 作为 trap 计数器。x21 最终值是 mscratch 计数（9），x22 是最后一条 trap 记录地址。TB 期望值基于旧版本的行为。

**验证**：在 origin/main 和 mmu-simplify 上产生**完全相同**的值 → 确认不是回归。
