## 第13章. "A" 原子指令扩展, 版本 2.1

原子指令扩展，命名为 "A"，包含以原子方式读-改-写内存的指令，以支持在同一内存空间中运行的多个 RISC-V hart 之间的同步。提供的两种原子指令形式为 load-reserved/store-conditional 指令和原子 fetch-and-op 内存指令。两种类型的原子指令都支持各种内存一致性排序，包括无序、acquire、release 和顺序一致语义。这些指令使 RISC-V 能够支持 RCsc 内存一致性模型。(Gharachorloo et al., 1990)

**评论：** _经过大量讨论，语言社区和架构社区似乎最终就 release consistency 作为标准内存一致性模型达成了一致，因此 RISC-V 的原子支持围绕此模型构建。_

A 扩展包含由 Zaamo 和 Zalrsc 扩展提供的指令。

## 13.1. 指定原子指令的排序

基础 RISC-V ISA 具有宽松的内存模型，使用 FENCE 指令来施加额外的排序约束。地址空间由执行环境划分为内存域和 I/O 域，FENCE 指令提供选项来对这两个地址域中的一个或两个的访问进行排序。

为了更有效地支持 release consistency (Gharachorloo et al., 1990)，每条原子指令有两个位，_aq_ 和 _rl_，用于指定其他 RISC-V hart 所观察到的额外内存排序约束。这些位对两个地址域（内存或 I/O）之一的访问进行排序，具体取决于原子指令正在访问哪个地址域。对另一个域的访问不隐含排序约束，应使用 FENCE 指令对两个域之间的访问进行排序。

如果两个位都清零，则不施加额外的排序约束于原子内存操作。如果仅设置 _aq_ 位，原子内存操作被视为 _acquire_ 访问，即此 RISC-V hart 上的后续内存操作不得被观察到在 acquire 内存操作之前发生。如果仅设置 _rl_ 位，原子内存操作被视为 _release_ 访问，即 release 内存操作不得被观察到在此 RISC-V hart 上任何更早的内存操作之前发生。如果同时设置 _aq_ 和 _rl_ 位，原子内存操作是 _顺序一致的_，在同一个 RISC-V hart 上对同一个地址域不得被观察到在任何更早内存操作之前或任何更晚内存操作之后发生。

对单个内存字或双字的复杂原子内存操作使用 load-reserved (LR) 和 store-conditional (SC) 指令执行。LR.W 从 _rs1_ 中的地址加载一个字，将符号扩展的值放入 _rd_，并注册一个 _保留集_——一组包含所寻址字中字节的字节集合。SC.W 有条件地将 _rs2_ 中的字写入 _rs1_ 中的地址：SC.W 仅在保留仍然有效且保留集包含正在写入的字节时成功。如果 SC.W 成功，指令将 _rs2_ 中的字写入内存，并将零写入 _rd_。如果 SC.W 失败，指令不写入内存，并将非零值写入 _rd_。任何 SC.W 指令在通过内存权限检查之前不得退休，但失败的 SC.W 是否产生隐式地址转换和保护性内存访问的副作用（如设置页表项 D 位）是未指定的。对于内存保护目的，失败的 SC.W 可以视为存储。无论成功或失败，执行 SC.W 指令都会使此 hart 持有的任何保留失效。LR.D 和 SC.D 类似地作用于双字，且仅在 RV64 上可用。对于 RV64，LR.W 和 SC.W 将放入 _rd_ 的值符号扩展。

**评论：** _compare-and-swap (CAS) 和 LR/SC 都可用于构建无锁数据结构。经过广泛讨论，我们选择了 LR/SC，原因如下：1) CAS 存在 ABA 问题，而 LR/SC 避免了该问题，因为它监视对地址的所有写入，而不仅仅是检查数据值的变化；2) CAS 还需要一种新的整数指令格式来支持三个源操作数（地址、比较值、交换值）以及不同的内存系统消息格式，这将使微架构复杂化；3) 此外，为避免 ABA 问题，其他系统提供双宽 CAS (DW-CAS) 以允许与数据字一起测试和递增计数器。这需要在一个指令中读取五个寄存器并写入两个寄存器，并且还需要一种新的更大的内存系统消息类型，进一步复杂化实现；4) LR/SC 为许多原语提供了更高效的实现，因为仅需要一次加载，而 CAS 需要两次（CAS 指令前的一次加载以获取用于推测计算的值，然后 CAS 指令中的第二次加载以检查值是否在更新前未改变）。_

**评论：** _LR/SC 相对于 CAS 的主要缺点是活锁，我们在某些情况下通过下面描述的架构保证的最终前向进展来避免。另一个担忧是当前 x86 架构及其 DWCAS 的影响是否会复杂化同步库和其他假定 DW-CAS 为基本机器原语的软件的移植。一个可能的缓解因素是最近 x86 增加了事务内存指令，这可能导致远离 DW-CAS。_

**评论：** _更一般地说，多字原子原语是可取的，但关于它应采取何种形式仍有相当大的争论，且保证前向进展为系统增加了复杂性。_

SC 指令永远不能被另一个 RISC-V hart 在建立保留的 LR 指令之前观察到。

**评论：** _通过在 LR 指令上设置 aq 位，LR/SC 序列可以被赋予 acquire 语义。通过在 SC 指令上设置 rl 位，LR/SC 序列可以被赋予 release 语义。假设对其他原子操作有合适的映射，在 LR 指令上设置 aq 位并且在 SC 指令上设置 rl 位使得 LR/SC 序列在 C++ 的 `memory_order_seq_cst` 意义上是顺序一致的。这样的序列不作为屏障来排序该序列前后的普通加载和存储指令。对其他 C++ 原子操作的具体指令映射，或更强的"顺序一致性"概念，可能要求在 LR 或 SC 指令中的一条或两条上都设置这两个位。_

**评论：** _如果 LR 或 SC 上均未设置任一位，则 LR/SC 序列可以被观察到在同一 RISC-V hart 的周围内存操作之前或之后发生。当 LR/SC 序列用于实现并行归约操作时，这可能是合适的。_

## 13.3. Store-Conditional 指令的最终成功

Zalrsc 扩展定义了 _受约束的 LR/SC 循环_，具有以下特性：

- 循环仅包含一个 LR/SC 序列以及在失败时重试该序列的代码，且必须由最多 16 条按顺序放置在内存中的指令组成。

- LR/SC 序列以 LR 指令开始，以 SC 指令结束。在 LR 和 SC 指令之间执行的动态代码只能包含基础 "I" 指令集中的指令，排除加载、存储、后向跳转、被采用的后向分支、JALR、FENCE 和 SYSTEM 指令。C（以及 Zca）和 Zcb 扩展中前述 "I" 指令的压缩形式也是允许的。

- 重试失败 LR/SC 序列的代码可以包含后向跳转和/或分支以重复 LR/SC 序列，但其他方面与 LR 和 SC 之间的代码具有相同的约束。

- LR 和 SC 的地址必须位于具有 _LR/SC 最终性_ 属性的内存区域内。执行环境负责传达哪些区域具有此属性。

- SC 必须指向与同一 hart 执行的最新 LR 相同的有效地址和相同的数据大小。

不位于受约束的 LR/SC 循环内的 LR/SC 序列是 _不受约束的_。不受约束的 LR/SC 序列可能在某些实现的某些尝试上成功，但在其他实现上可能永远不会成功。

**评论：** _我们将 LR/SC 循环的长度限制在基础 ISA 的 64 个连续指令字节内，以避免对指令缓存和 TLB 大小及关联性施加不适当的限制。类似地，我们不允许循环内的其他加载和存储，以避免对在私有缓存内跟踪保留的简单实现中的数据缓存关联性施加限制。对分支和跳转的限制限制了在序列中花费的时间。浮点操作和整数乘除法被禁止，以简化操作系统在缺乏适当硬件支持的实现上模拟这些指令。_

**评论：** _不禁止软件使用不受约束的 LR/SC 序列，但可移植软件必须检测序列反复失败的情况，然后回退到不依赖不受约束的 LR/SC 序列的替代代码序列。允许实现无条件地使任何不受约束的 LR/SC 序列失败。_

[#norm:constrained_lrsc_forward_progress]#如果 hart _H_ 进入受约束的 LR/SC 循环，执行环境必须保证以下事件之一最终发生：

- _H_ 或某个其他 hart 向 _H_ 的受约束 LR/SC 循环中的 LR 指令的保留集执行成功的 SC。

- 某个其他 hart 向 _H_ 的受约束 LR/SC 循环中的 LR 指令的保留集执行无条件存储或 AMO 指令，或者系统中的某个其他设备向该保留集写入。

- _H_ 执行分支或跳转退出受约束的 LR/SC 循环。

- _H_ 陷入陷阱。#

**评论：** _注意这些定义允许实现偶尔因任何原因使 SC 指令失败，前提是不违反上述保证。_

**评论：** _作为最终性保证的结果，如果执行环境中的某些 hart 正在执行受约束的 LR/SC 循环，且执行环境中没有其他 hart 或设备向该保留集执行无条件存储或 AMO，那么至少有一个 hart 最终将退出其受约束的 LR/SC 循环。相反，如果其他 hart 或设备继续向该保留集写入，则不能保证任何 hart 将退出其 LR/SC 循环。_

**评论：** _加载和 load-reserved 指令本身不妨碍其他 hart 的 LR/SC 序列的进展。我们注意到此约束意味着，除其他外，由其他 hart（可能在同一个核内）执行的加载和 load-reserved 指令不能无限期地阻碍 LR/SC 的进展。例如，由共享缓存的另一个 hart 引起的缓存驱逐不能无限期地阻碍 LR/SC 的进展。通常，这意味着保留的跟踪独立于任何共享缓存的驱逐。类似地，hart 内部的推测执行引起的缓存未命中不能无限期地阻碍 LR/SC 的进展。_

**评论：** _这些定义承认 SC 指令可能因实现原因而虚假失败的可能性，只要最终取得进展即可。_

**评论：** _CAS 的一个优势是它保证某个 hart 最终取得进展，而 LR/SC 原子序列在某些系统上可能无限期活锁。为避免此担忧，我们为某些 LR/SC 序列增加了架构级别的活锁自由保证。_

**评论：** _此规范的早期版本施加了更强的无饥饿保证。然而，较弱的活锁自由保证足以实现 C11 和 C++11 语言，且在某些微架构风格中更容易提供。_

原子内存操作 (AMO) 指令为多处理器同步执行读-改-写操作，并以 R-type 指令格式编码。这些 AMO 指令原子地从 _rs1_ 中的地址加载一个数据值，将该值放入寄存器 _rd_，对加载的值和 _rs2_ 中的原始值应用二元运算符，然后将结果存储回 _rs1_ 中的原始地址。AMO 可以操作内存中的 _双字_（仅 RV64）或 _字_。对于 RV64，32 位 AMO 始终将放入 _rd_ 的值符号扩展，并忽略 _rs2_ 原始值的高 32 位。

对于 AMO，Zaamo 扩展要求 _rs1_ 中保存的地址自然对齐到操作数的大小（即双字为八字节对齐，字为四字节对齐）。如果地址未自然对齐，将产生地址未对齐异常或访问故障异常。如果未对齐访问不应被模拟，那么即使未对齐情况下的内存访问本来可以完成，也会产生访问故障异常。

未对齐原子粒度 PMA 在 Volume II 中定义，可选地放宽此对齐要求。如果存在，未对齐原子粒度 PMA 指定未对齐原子粒度的大小，以 2 的幂次字节数表示。未对齐原子粒度 PMA 仅适用于 AMO、基础 ISA 中定义的加载和存储，以及 F、D 和 Q 扩展中定义的且不超过 XLEN 位以及其压缩编码的加载和存储。对于该集合中的指令，如果所有访问的字节位于同一个未对齐原子粒度内，指令不会因地址对齐原因引发异常，且对于 RVWMO 目的，指令将只产生一个内存操作——即它将原子地执行。

支持的操作包括交换、整数加法、按位 AND、按位 OR、按位 XOR 以及有符号和无符号整数的最大值和最小值。在没有排序约束的情况下，这些 AMO 可用于实现并行归约操作，通常通过写入 `x0` 来丢弃返回值。

**评论：** _我们提供了 fetch-and-op 风格的原子原语，因为它们比 LR/SC 或 CAS 更好地扩展到高度并行的系统。简单的微架构可以使用 LR/SC 原语实现 AMO，前提是实现能保证 AMO 最终完成。更复杂的实现也可以在内存控制器处实现 AMO，并可以在目标为 `x0` 时优化掉获取原始值的操作。_

**评论：** _所选的 AMO 集合旨在高效支持 C11/C++11 原子内存操作，并支持内存中的并行归约。AMO 的另一个用途是对 I/O 空间中的内存映射设备寄存器提供原子更新（例如，设置、清除或翻转位）。_

**评论：** _Zaamo 扩展使微控制器类实现能够利用 A 扩展中 AMO 子集的原子原语。通常此类实现没有缓存，因此可能无法自然地支持 Zalrsc 扩展提供的 LR/SC 指令。_

为帮助实现多处理器同步，AMO 可选地提供 release consistency 语义。如果设置 _aq_ 位，则此 RISC-V hart 上的后续内存操作不得被观察到在 AMO 之前发生。相反，如果设置 _rl_ 位，则其他 RISC-V hart 不会在 AMO 之前观察到该 RISC-V hart 上先于 AMO 的内存访问。在 AMO 上同时设置 _aq_ 和 _rl_ 位使序列顺序一致，意味着它不能与同一 hart 上更早或更晚的内存操作重排序。

**评论：** _AMO 被设计为高效实现 C11 和 C++11 内存模型。尽管 FENCE R, RW 指令足以实现 acquire 操作，FENCE RW, W 足以实现 release，但与设置了相应 aq 或 rl 位的 AMO 相比，两者都隐含了额外的非必要排序。_

**评论：** _清单 3 展示了一个由 test-and-test-and-set 自旋锁保护的临界区示例代码序列。注意第一个 AMO 标记 aq 以将锁获取排序在临界区之前，第二个 AMO 标记 rl 以将临界区排序在锁释放之前。_

```
        li           t0, 1        # Initialize swap value.
    again:
        lw           t1, (a0)     # Check if lock is held.
        bnez         t1, again    # Retry if held.
        amoswap.w.aq t1, t0, (a0) # Attempt to acquire lock.
        bnez         t1, again    # Retry if held.
        # ...
        # Critical section.
        # ...
        amoswap.w.rl x0, x0, (a0) # Release lock by storing 0.
```

**评论：** _清单 3. 互斥的示例代码。`a0` 包含锁的地址。_

**评论：** _我们建议对锁获取和释放均使用清单 3 所示的 AMO Swap 惯用模式，以简化推测锁省略的实现。(Rajwar & Goodman, 2001)_

**评论：** _"A" 扩展中的指令可用于提供顺序一致的加载和存储，但这比必要情况更多地约束了内存访问的硬件重排序。C++ 顺序一致加载可以实现为设置了 aq 的 LR。然而，LR/SC 的最终成功保证可能会减慢对同一有效地址的并发加载。顺序一致存储可以实现为将旧值写入 `x0` 并设置了 rl 的 AMOSWAP。然而多余的加载可能施加对于该用例不必要的排序约束。具体的编译约定可能要求在 LR 和 AMOSWAP 指令中的一条或两条上都设置 aq 和 rl 位。_
