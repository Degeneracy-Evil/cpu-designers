## 第33章 密码学扩展：向量指令，版本 1.0

本文档描述了 RISC-V 指令集架构的向量密码学扩展。

## 33.1. 引言

本文档描述了 RISC-V **向量**密码学扩展。此处描述的所有指令均基于向量寄存器。这些指令设计为高性能，以大型应用和服务器级核心为主要目标。配套章节 _Volume I: Scalar & Entropy Source Instructions_ 描述了针对未实现向量扩展的较小核心的密码学指令。

## 33.1.1. 目标受众

密码学是一个专业领域，需要不同背景的人员协作以实现安全高效的实现。在可能的情况下，我们已尽力使本规范对所有读者都能理解，但我们认识到，其中涉及的动机以及对算法和其他规范和标准的引用，对非领域专家来说可能较为陌生。

本规范预计会被不同背景的人员阅读和执行。我们试图在此描述这些背景，简要说明我们期望他们了解的内容以及与本规范的关系。

## 密码学家和密码学软件开发人员

这些是我们期望使用本规范中指令编写代码的人员。他们应理解我们包含的指令的动机，并熟悉我们引用的大多数算法和外部标准。

## 计算机架构师

我们不期望架构师具有密码学背景。但我们期望架构师能够检查我们的指令是否存在实现问题，理解指令在上下文中如何使用，并就如何最佳地适配密码学家的需求提出建议。

## 数字设计工程师和微架构师

这些是在核心内部实现规范的人员。同样，不假定具有密码学专业知识，但我们期望他们解读规范并预见到任何硬件实现问题。特别地，他们应了解在硬件中高效实现 AES 和 SM4 SBox 的相关文献。

## 验证工程师

这些人员负责确保扩展在硬件中的正确实现。不假定具有密码学背景。我们期望他们从规范中识别出有趣的测试用例。

这些绝非关注本规范的唯一人群，但他们是我们在编写时最着重考虑的人群。

## 33.1.2. Sail 规范

RISC-V 维护一个 ISA 规范的形式化模型，使用 Sail ISA 规范语言实现。请注意，_Sail_ 指的是规范语言本身，而存在一个用 Sail 编写的 _RISC-V 模型_。

## 33.1.3. 策略

在制定此扩展时，我们试图遵循以下策略：

- 当需要在：1) 支持某种算法的多种实现策略，或 2) 支持单一实现风格（性能更高/成本更低）之间选择时；向量密码学扩展将选择更受限但性能更高的选项。这符合 RISC-V 规范其他部分的常见模式，其中为执行特定任务提供推荐（但非必需）的指令序列作为示例，使硬件和软件实现者都可以仅针对单一用例进行优化。

- 这些扩展将被设计为良好支持**现存**的标准化密码学构造。它不会试图支持提议中的标准或仅存于学术界的密码学构造。与 RISC-V 向量密码学扩展标准化同时或在其后确立的密码学标准，将由未来的 RISC-V 向量密码学标准扩展来处理。

- 历史上曾有过一些讨论（Lee et al., 2004），关于通用计算中新支持的操作如何为密码学算法提供新的基础。本标准不会试图预测哪些新的有用的低级操作**可能**成为未来密码学构造的构建块。

- 关于侧信道对策：在相关情况下，提议的指令必须旨在消除任何时序侧信道的可能性。所有指令应以数据无关时序实现。即，这些指令的执行延迟不应随不同输入值而变化。


## 33.1.4. 元素组

许多向量密码学指令操作于比元素更宽的操作数（元素当前限制为 64 位宽）。通常，这些操作数是 128 位和 256 位宽。在许多情况下，这些操作数由组合在一起的较小操作数组成（例如，每个 SHA-2 操作数由 4 个字组成）。然而，在其他情况下，这些操作数是单个值（例如，在 AES 轮指令中，每个操作数是 128 位块或轮密钥）。

我们将这些操作数视为一个或多个**元素组**（element groups）的向量，如第 31.19 节所定义。

每个操作于元素组的向量密码学指令明确指定其三个定义参数：EGW、EGS 和 EEW。

|指令组|扩展|EGW|EEW|EGS|
|---|---|---|---|---|
|AES|Zvkned|128|32|4|
|SHA256|zvknh[ab]|128|32|4|
|SHA512|zvknhb|256|64|4|
|GCM|Zvkg|128|32|4|
|SM4|Zvksed|128|32|4|
|SM3|Zvksh|256|32|8|

- _元素组宽度 (_ `EGW` _) - 元素组中的总位数_
- _有效元素宽度 (_ `EEW` _) - 每个元素中的位数_
- _元素组大小 (_ `EGS` _) - 元素组中的元素数_

对于本规范中的所有向量密码学指令，`EEW` = `SEW`。

**评论：** _每条密码学指令所需的_ `SEW` _被选择为与实现目标算法时通常所需的内容相匹配。_

- 向量元素组是一个或多个元素组的向量。
- 标量元素组是单个元素组。

在 `VLEN` < `EGW` 的实现中，元素组可以通过使用 `LMUL` >1 跨寄存器形成。

**评论：** _由于应用处理器的向量扩展要求最低 VLEN 为 128，因此大多数此类实现最多需要 LMUL=2 来形成本规范中最大的元素组。_

_然而，VLEN 较小的实现（如嵌入式设计）将需要更大的_ `LMUL` _来形成必要的元素组。重要的是要记住，这会减少可用的寄存器组数量，以至于可能很难或不可能为预期的密码学算法编写高效的代码。_

_例如，_ `VLEN` _=32 的实现需要设置_ `LMUL` _=8 来为_ `SM3` _创建 256 位元素组。这意味着只有 4 个寄存器组，其中 3 个会被单条_ `SM3` _消息扩展指令消耗。_

与所有向量指令一样，处理的元素数量由向量长度 `vl` 指定。操作的元素组数量则为 `vl` / `EGS`。同样，起始元素组为 `vstart` / `EGS`。向量密码学指令对 `vl` 和 `vstart` 的限制见第 33.1.5 节。

## 33.1.5. 指令约束

RVV 1.0 指定的所有标准向量指令约束均适用于向量密码学指令。除此之外，还引入了一些额外的特定约束。

以下为特定向量密码学指令的各种约束的快速参考。

## vl 和 vstart 约束

由于 `vl` 和 `vstart` 指的是元素，使用元素组的向量密码学指令要求这些值是元素组大小 ( `EGS` ) 的整数倍。

违反 `vl` 或 `vstart` 要求的指令是**保留的**。

|指令|EGS|
|---|---|
|vaes*|4|
|vsha2*|4|
|vg*|4|
|vsm3*|8|
|vsm4*|4|

## LMUL 约束

对于元素组指令，`LMUL` * `VLEN` 必须始终至少与 `EGW` 一样大，否则会引发*非法指令异常*，即使 `vl` =0。

|指令|SEW|EGW|
|---|---|---|
|vaes*|32|128|
|vsha2*|32|128|
|vsha2*|64|256|
|vg*|32|128|
|vsm3*|32|256|
|vsm4*|32|128|

## SEW 约束

某些向量密码学指令仅针对特定 `SEW` 定义。在这种情况下，所有其他 `SEW` 值都是**保留的**。

|指令|所需 SEW|
|---|---|
|vaes*|32|
|Zvknha: vsha2*|32|
|Zvknhb: vsha2*|32 或 64|
|vclmul[h]|64|
|vg*|32|
|vsm3*|32|
|vsm4*|32|

## 向量/标量约束

本规范定义了使用标量元素组的新向量/标量 (.vs) 指令。标量元素组操作数具有 `EMUL = ceil(EGW / VLEN)`。

**评论：** _对于任何 VLEN >= EGW 的实现，标量元素组操作数不需要对齐到 LMUL。_

在本规范定义的 `.vs` 指令中，`vs2` 持有一个 128 位标量元素组。对于 `VLEN` ≥ 128 的实现，`vs2` 指单个寄存器。因此，`vd` 寄存器组不得与 `vs2` 寄存器重叠。然而，在 `VLEN` < 128 的实现中，`vs2` 指的是由容纳 128 位标量元素组所需的寄存器数量组成的寄存器组。在这种情况下，`vd` 寄存器组不得与此 `vs2` 寄存器组重叠。

|指令|寄存器|不能重叠|
|---|---|---|
|vaes*.vs|vs2|vd|
|vsm4r.vs|vs2|vd|
|vsha2c[hl]|vs1, vs2|vd|
|vsha2ms|vs1, vs2|vd|
|vsm3me|vs2|vd|
|vsm3c|vs2|vd|


## 33.1.6. 向量-标量指令

RISC-V 向量扩展为向量-标量操作定义了三种编码，它们从 GPR 或 FP 寄存器获取标量操作数：
- OPIVX: 标量 GPR _x_ 寄存器
- OPFVF: 标量 FP _f_ 寄存器
- OPMVX: 标量 GPR _x_ 寄存器

然而，向量扩展包括向量归约操作，这些操作也可被视为向量-标量操作，因为标量操作数从向量寄存器 `vs1` 的元素 0 提供。向量操作数在向量寄存器组 `vs2` 中提供。这些归约操作在其助记符中都使用 `.vs` 后缀。此外，归约操作都在目标寄存器 `vd` 的元素 0 中产生标量结果。

向量密码学扩展定义的向量-标量指令与这些向量归约操作相似，它们从向量寄存器获取标量操作数。然而，不同之处在于它们从 `vs2` 获取标量元素组，并向 `vd` 返回**向量**结果，`vd` 同时也是源向量操作数。这些向量-标量密码学指令在其助记符中也使用 `.vs` 后缀。

**评论：** _我们选择使用_ `vs2` _作为标量操作数，_ `vd` _作为向量操作数，这样我们就可以使用_ `vs1` _说明符作为这些指令的额外编码位，从而使这些指令具有更小的编码占用，为未来的其他指令留出更多空间。_

这些指令使得可以将单个密钥（在 `vs2` 中作为标量元素组指定）应用于寄存器组 `vd` 的每个元素组。

**评论：** _在应用处理器中，标量元素组最多占用一个寄存器。然而，在 VLEN<128 的实现中，它们将占用 2 个（VLEN=64）或 4 个（VLEN=32）寄存器。_

**评论：** _多个 AES 加密轮（例如）使用相同的轮密钥并行执行是很常见的（例如在计数模式下）。这些向量-标量密码学指令允许将轮密钥指定为标量元素组，而不必首先将公共密钥散布到整个向量组。_

## 33.1.7. 软件可移植性

以下内容包含一些指南，使基于向量密码学的代码能够在具有不同 `VLEN` 值的实现之间移植。

## 应用处理器

应用处理器预期遵循 V 扩展，因此将具有 `VLEN` ≥ 128。

由于大多数**密码学专用**指令具有 `EGW` =128，因此对于 `VLEN` =128 的实现，这些指令无需特别处理。

然而，SHA-512 和 SM3 指令具有 `EGW` =256。对于 `VLEN` =128 的实现，需要将这些指令的 `LMUL` 加倍，以便在寄存器对之间创建 256 位元素。这种 `LMUL` 加倍编写的代码不会影响 `VLEN` ≥ 256 的实现返回的结果，因为 `vl` 控制处理多少个元素组。因此，我们建议实现 SHA-512 和 SM3 的库采用这种 `LMUL` 加倍，以确保软件可以在所有 `VLEN` ≥ 128 的实现上运行。

虽然对这些指令加倍 `LMUL` 对于 `VLEN` ≥ 256 的实现是**安全的**，但这可能不是最优的，因为它会导致不必要的寄存器压力，并可能在某些微架构中造成性能损失。因此，我们建议除了为 SHA-512 和 SM3 提供可移植代码外，库还应该在这些指令的 `VLEN` ≥ 256 时包含更优化的代码。

|算法|指令|VLEN|LMUL|
|---|---|---|---|
|SHA-512|vsha2*|64|vl/2|
|SM3|vsm3*|32|vl/4|

## 嵌入式处理器

嵌入式处理器通常具有 `VLEN` < 128 的实现。这将需要代码以更大的 `LMUL` 值编写，以启用元素组的形成。

`.vs` 指令需要 `EGW` =128 的标量元素组。在 `VLEN` < 128 的实现中，这些标量元素组必然跨寄存器形成。这与向量指令中的大多数标量不同，后者通常消耗单个寄存器的一部分。

我们建议为 `VLEN` =32 和 `VLEN` =64 提供不同的代码，因为为 `VLEN` =32 编写的代码对 `VLEN` =64 的实现可能过于繁重。

## 33.2. 扩展概述

本节介绍向量密码学指令集扩展规范中的所有扩展。

Zvknhb 和 Zvbc 向量密码学扩展——以及相应的组合扩展 Zvkn、Zvknc、Zvkng 和 Zvksc——依赖于 Zve64x。

所有其他向量密码学扩展依赖于 `Zve32x`。

注意：如果支持 `Zve32x`，则 `Zvkb` 或 `Zvbb` 提供对 EEW 为 8、16 和 32 的支持。如果支持 `Zve64x`，则 `Zvkb` 或 `Zvbb` 还额外支持 EEW 64。

本向量密码学规范中定义的所有**密码学专用**指令（即 Zvkned、Zvknh[ab]、Zvkg、Zvksed 和 Zvksh 中的指令，但**不**包括 Zvbb、Zvkb 或 Zvbc）应以 RISC-V 标量密码学扩展规范中定义的数据无关执行延迟执行。重要的是要注意，向量密码学指令独立于 `Zkt` 扩展的实现，并且不要求实现 `Zkt`。

本规范包括 Zvkt 扩展，当实现时，要求某些向量指令（包括 Zvbb、Zvkb 和 Zvbc）以数据无关执行延迟执行。

各密码学扩展的检测使用统一的基于软件的 RISC-V 发现方法。

**评论：** _在撰写本文时，这些发现机制仍在开发中。_

## 33.2.4. **`Zvkg`** - 向量 GCM/GMAC

用于高效实现 GHASHH 的指令，GHASHH 用于 Galois/计数器模式 (GCM) 和 Galois 消息认证码 (GMAC)。

所有这些指令操作于由四个 32 位元素组成的 128 位元素组。

GHASHH 在 "Recommendation for Block Cipher Modes of Operation: Galois/Counter Mode (GCM) and GMAC" (Dworkin, 2007)（NIST 规范）中定义。

**评论：** _GCM 与分组密码（例如 AES 和 SM4）结合使用以加密消息并提供认证。GMAC 用于提供消息认证而不加密。_

为帮助避免侧信道时序攻击，这些指令应以数据无关时序实现。

要处理的元素组数量为 `vl` / `EGS`。`vl` 必须设置为要处理的 `SEW=32` 元素数量，因此必须是 `EGS=4` 的倍数。同样，`vstart` 必须是 `EGS=4` 的倍数。

|SEW|EGW|助记符|指令|
|---|---|---|---|
|32|128|vghsh.vv|向量 GHASH 加-乘|
|32|128|vgmul.vv|向量 GHASH 乘|

## 33.2.5. **`Zvkned`** - NIST 套件：向量 AES 分组密码

加速 AES 分组密码加密、解密和密钥调度函数的指令，如 Federal Information Processing Standards Publication 197 (NIST, 2001) 中所定义。

所有这些指令操作于由四个 32 位元素组成的 128 位元素组。

为获得最佳性能，建议在 `VLEN` >=128 的系统上实现这些指令。在 `VLEN` <128 的系统上，可通过使用 LMUL =2 和 LMUL=4 将两个或四个寄存器中的 32 位元素连接起来形成元素组。

为帮助避免侧信道时序攻击，这些指令应以数据无关时序实现。

要处理的元素组数量为 `vl` / `EGS`。`vl` 必须设置为要处理的 `SEW=32` 元素数量，因此必须是 `EGS=4` 的倍数。同样，`vstart` 必须是 `EGS=4` 的倍数。

|SEW|EGW|助记符|指令|
|---|---|---|---|
|32|128|vaesef.[vv,vs]|向量 AES 加密最终轮|

## 33.2.15. **`Zvkt`** - 向量数据无关执行延迟

Zvkt 扩展要求以下列表中所有已实现的指令以 RISC-V 标量密码学扩展规范中定义的数据无关执行延迟执行。

数据无关执行延迟 (DIEL) 适用于指令的所有**数据操作数**，即使是那些不属于主体或非活跃的操作数。然而，DIEL 不适用于其他值，如 vl、vtype 和掩码（当用于控制掩码向量指令的执行时）。此外，DIEL 不适用于指令编码中指定的常量值，如零寄存器 ( `x0` ) 的使用，以及在立即数形式的指令中，立即数字段中的值（即 imm 和 uimm）。

在某些情况下——在下面的列表中明确指定——用作控制而非数据的操作数豁免于 DIEL。

**评论：** _DIEL 有助于防止用于确定本应保密的数值的侧信道时序攻击。此类值包括密码学密钥、明文和部分加密文本。DIEL 不旨在保持软件（及其包含的密码学算法）的机密性，因为假设攻击者已经知道这些。这就是为什么 DIEL 不适用于嵌入指令编码中的常量。_

_不在主体中或被掩码关闭的元素的值不应对指令的执行延迟产生影响，这一点很重要。有时此类元素包含也需要保密的数据。_
