## 29.1. Zc*概述

## 29.2. C

C扩展是以下扩展的超集：

- Zca
- 如果指定了F，则包含Zcf（仅RV32）
- 如果指定了D，则包含Zcd

由于C定义了与Zca、Zcf和Zcd相同的指令，规则如下：

- C总是蕴含Zca
- C+F蕴含Zcf（仅RV32）
- C+D蕴含Zcd

## 29.3. Zce

Zce扩展旨在用于微控制器，包括所有相关的Zc扩展。

- 在不带F的RV32上指定Zce包含Zca、Zcb、Zcmp、Zcmt
- 在带F的RV32上指定Zce包含Zca、Zcb、Zcmp、Zcmt*和*Zcf
- 在RV64上指定Zce始终包含Zca、Zcb、Zcmp、Zcmt
  - Zcf在RV64中不存在

因此，常见的ISA字符串可以如下更新以包含相关的Zc扩展，例如：

- RV32IMC变为RV32IM_Zce
- RV32IMCF变为RV32IMF_Zce

## 29.4. MISA.C

如果选择了以下扩展，则MISA.C被设置：

- Zca且非F
- Zca、Zcf和F（但非D）被指定（仅RV32）
- Zca、Zcf和Zcd如果D被指定（仅RV32）
  - 此配置排除Zcmp、Zcmt
- Zca、Zcd如果D被指定（仅RV64）
  - 此配置排除Zcmp、Zcmt

## 29.5. Zca

Zca扩展被添加为一种引用C扩展中不包含浮点加载和存储指令的方式。

因此它*排除*了所有16位浮点加载和存储：*c.flw*、*c.flwsp*、*c.fsw*、*c.fswsp*、*c.fld*、*c.fldsp*、*c.fsd*、*c.fsdsp*。

**评论：** C扩展仅在D和F也被指定时才包含F/D指令。

## 29.6. Zcf（仅RV32）

Zcf是现有的压缩单精度浮点加载和存储集合：*c.flw*、*c.flwsp*、*c.fsw*、*c.fswsp*。

Zcf仅与RV32相关，不能为RV64指定。

Zcf扩展依赖于Zca和F扩展。

## 29.7. Zcd

Zcd是现有的压缩双精度浮点加载和存储集合：*c.fld*、*c.fldsp*、*c.fsd*、*c.fsdsp*。

Zcd扩展依赖于Zca和D扩展。

## 29.8. Zcb

Zcb具有简单的代码体积节省指令，这些指令在所有CPU上都容易实现。

所有编码目前对所有架构都是保留的，且与任何现有扩展没有冲突。

**评论：** Zcb可以在任何CPU上实现，因为这些指令是应用类配置文件中现有32位指令的16位版本。

Zcb扩展依赖于Zca扩展。

如各个指令页面所示，Zcb中的许多指令依赖于另一个扩展的实现。例如，*c.mul*仅在M或Zmmul被实现时才实现，*c.sext.b*仅在Zbb被实现时才实现。

*c.mul*编码使用CA寄存器格式，与其他指令如*c.sub*、*c.xor*等一起。

**评论：** *c.sext.w是c.addiw rd, 0 (RV64)的伪指令。*

## 29.9. Zcmp

Zcmp扩展是一组可以作为现有32位RISC-V指令序列执行的指令。

此扩展重用了*c.fsdsp*的一些编码。因此它与Zcd*不兼容*，Zcd在C和D扩展同时存在时被包含。

**评论：** Zcmp主要面向嵌入式类CPU，因为实现复杂性较高。此外，它不兼容应用类配置文件。

Zcmp扩展依赖于Zca扩展。

PUSH/POP汇编语法使用多个变量，其含义如下：

- *reg_list*是一个包含1到13个寄存器的列表（ra和0到12个s寄存器）
  - 有效值：{ra}、{ra, s0}、{ra, s0-s1}、{ra, s0-s2}、…、{ra, s0-s8}、{ra, s0-s9}、{ra, s0-s11}
  - 注意{ra, s0-s10}是*无效*的，提供12个列表而非13个以获得更好的编码
- *stack_adj*是栈帧的总大小。
  - 有效值随寄存器列表长度和具体编码而变化，详见各指令页面。

|RV32|RV64|助记符|指令|
|---|---|---|---|
|yes|yes|cm.push *{reg_list}*, -*stack_adj*|cm.push|
|yes|yes|cm.pop *{reg_list}*, *stack_adj*|cm.pop|
|yes|yes|cm.popret *{reg_list}*, *stack_adj*|cm.popret|
|yes|yes|cm.popretz *{reg_list}*, *stack_adj*|cm.popretz|
|yes|yes|cm.mva01s *rs1'*, *rs2'*|将两个s0-s7寄存器移动到a0-a1|
|yes|yes|cm.mvsa01 *r1s'*, *r2s'*|将a0-a1移动到两个不同的s0-s7寄存器|

## 29.10. Zcmt

Zcmt添加了表跳转指令，还添加了jvt CSR。如果实现了Smstateen，则jvt CSR需要状态使能。详情参见jvt CSR，表跳转基向量和控制寄存器。

此扩展重用了*c.fsdsp*的一些编码。因此它与Zcd*不兼容*，Zcd在C和D扩展同时存在时被包含。

**评论：** Zcmt主要面向嵌入式类CPU，因为实现复杂性较高。此外，它与RVA配置文件不兼容。

Zcmt扩展依赖于Zca和Zicsr扩展。

|RV32|RV64|助记符|指令|
|---|---|---|---|
|yes|yes|cm.jt *index*|通过表跳转|
|yes|yes|cm.jalt *index*|通过表跳转并链接|

## 29.13. PUSH/POP寄存器指令

这些指令统称为PUSH/POP：

- cm.push
- cm.pop
- cm.popret
- cm.popretz

术语PUSH指*cm.push*。

术语POP指*cm.pop*。

术语POPRET指*cm.popret和cm.popretz*。

这些指令的公共细节在本节中。

## 29.13.1. PUSH/POP功能概述

PUSH、POP、POPRET用于减少函数序幕和尾声的大小。

1. PUSH指令
   - 调整栈指针以创建栈帧
   - 将寄存器列表中指定的寄存器压入（存储到）栈帧

2. POP指令
   - 从栈帧弹出（加载）寄存器列表中的寄存器
   - 调整栈指针以销毁栈帧

3. POPRET指令
   - 从栈帧弹出（加载）寄存器列表中的寄存器
   - *cm.popretz*还将零移入*a0*作为返回值
   - 调整栈指针以销毁栈帧
   - 执行*ret*指令从函数返回

## 29.13.2.1. 栈指针调整处理

这些指令都自动调整栈指针，调整量足以覆盖保存或恢复的寄存器所需的内存。此外，编码中的*spimm*字段允许栈指针以16字节的额外增量进行调整。编码中只有一个小范围的可用值；如果范围不够，可以使用单独的*c.addi16sp*来增加范围。

## 29.13.2.2. 寄存器列表处理

不支持不包含*s11*的*{ra, s0-s10}*寄存器列表。因此在这种情况下必须使用*{ra, s0-s11}*寄存器列表。

## 29.13.3. PUSH/POP故障处理

正确执行要求*sp*引用幂等内存（另见非幂等内存处理），因为内核必须能够处理在序列期间检测到的陷阱。整个PUSH/POP序列在从陷阱处理程序返回后重新执行，并且序列期间可能发生多次陷阱。

如果在序列期间发生陷阱，*xEPC*使用指令的PC更新，*xTVAL*（如果不是只读零）使用坏地址更新（如果是访问故障），*xCAUSE*使用陷阱类型更新。

**评论：** *是否允许在序列执行期间发生中断由实现定义。*

## 29.13.4. 执行的软件视图

## 29.13.4.1. PUSH序列的软件视图

从软件角度看，PUSH序列表现为：

- 一系列写入伪代码所需字节的存储操作
  - 字节可以按任何顺序写入。
  - 字节可以组合成更大的访问。
  - 任何字节可能被多次写入。
- 一次栈指针调整

**评论：** *如果实现允许在序列期间中断，并且中断处理程序使用sp分配栈内存，那么在中断之前执行的任何存储操作都可能被处理程序覆盖。这是安全的，因为内存是幂等的，存储操作将在执行恢复时重新执行。*

栈指针调整必须仅在确定整个PUSH指令将提交时才提交。

存储操作也可能从总线返回不精确故障。内核实现是等待总线响应后再继续序列的最后阶段，还是在完成PUSH指令后处理错误响应，由平台定义。

例如：

```
cm.push  {ra, s0-s5}, -64
```

对软件表现为：

```
# sp-1到sp-28的任何字节可能在指令完成之前被多次写入
# 因此这些更新可能在栈指针以下的中断/异常处理程序中可见
sw  s5, -4(sp)
sw  s4, -8(sp)
sw  s3,-12(sp)
sw  s2,-16(sp)
sw  s1,-20(sp)
sw  s0,-24(sp)
sw  ra,-28(sp)
# 这必须只执行一次，并且只在所有存储操作完成且没有任何精确故障后执行
# 因此此更新仅在cm.push已完成时在中断/异常处理程序中可见
addi sp, sp, -64
```

## 29.13.4.2. POP/POPRET序列的软件视图

从软件角度看，POP/POPRET序列表现为：

- 一系列读取伪代码所需字节的加载操作。
  - 字节可以按任何顺序加载。
  - 字节可以组合成更大的访问。
  - 任何字节可能被多次加载。
- 一次栈指针调整
- 可选的`li a0, 0`
- 可选的`ret`

如果在序列期间发生陷阱，则在陷阱之前执行的任何加载操作都可能更新架构状态。一旦陷阱处理程序完成，加载操作将重新执行，因此值将被覆盖。因此允许实现在发生故障之前更新一些目标寄存器。

可选的`li a0, 0`、栈指针调整和可选的`ret`必须仅在确定整个POP/POPRET指令将提交时才提交。

对于POPRET，一旦栈指针调整已提交，`ret`必须执行。

例如：

```
cm.popretz {ra, s0-s3}, 32;
```

对软件表现为：

```
# 这些加载指令中的任何或全部可能多次执行
# 因此这些更新可能在中断/异常处理程序中可见
lw   s3, 28(sp)
lw   s2, 24(sp)
lw   s1, 20(sp)
lw   s0, 16(sp)
lw   ra, 12(sp)
# 这些必须只执行一次，仅在所有加载操作成功完成后执行
# 所有指令必须原子执行
# 因此这些更新在中断/异常处理程序中不可见
li a0, 0
addi sp, sp, 32
ret
```

## 29.13.5. 非幂等内存处理

实现可能需要将PUSH/POP指令发出到非幂等内存。

如果内核实现不支持PUSH/POP到非幂等内存，内核可以使用幂等性PMA来检测它，并采取加载（POP/POPRET）或存储（PUSH）访问故障异常以避免不可预测的结果。

软件应仅在软件能够容忍所需内存访问在导致异常的情况下被重复发出时，才对非幂等内存区域使用这些指令。

## 29.14. 表跳转概述

*cm.jt*（通过表跳转）和*cm.jalt*（通过表跳转并链接）被称为表跳转。

表跳转在指令内存中使用一个256条目XLEN宽的表来包含函数地址。表必须至少64字节对齐。

表条目遵循当前数据字节序。这与始终为小端序的正常指令获取不同。

*cm.jt*和*cm.jalt*编码索引该表，允许访问完整XLEN宽地址空间中的函数。

这被用作一种字典压缩形式，以减少*jal* / *auipc+jalr* / *jr* / *auipc+jr*指令的代码大小。

表跳转允许链接器用*cm.jt*或*cm.jalt*编码以及表中的一个条目替换以下指令序列：

- 32位*j*调用
- 32位*jal* ra调用
- 64位*auipc+jr*调用到固定位置
- 64位*auipc+jalr ra*调用到固定位置
  - 使用*auipc+jr/jalr*序列是因为从PC的偏移超出了±1 MB范围。

如果实现了返回地址栈，那么由于*cm.jalt*等价于*jal ra*，它会被压入栈。

## 29.14.1. jvt

表的基址位于jvt CSR中（参见jvt CSR，表跳转基向量和控制寄存器），每个表条目是XLEN位。

如果同一个函数被以链接和不链接两种方式调用，则它必须在表中有两个条目。这通常由同一个函数被以尾调用和非尾调用方式调用引起。

## 29.14.2. 表跳转故障处理

对于表跳转指令，指令选择的表条目被视为指令本身的扩展。因此，表跳转指令的执行涉及两次指令获取，第一次读取指令（*cm.jt* / *cm.jalt*），第二次从跳转向量表（JVT）读取。两次指令获取都是*隐式*读取，并且都需要执行权限；读取权限不相关。建议第二次获取被硬件触发器和断点忽略。

对跳转向量表的内存写入需要指令屏障（*fence.i*）来保证它们对指令获取可见。

多个上下文可能具有不同的跳转向量表。如果自上次*fence.i*以来内存中的表未被更新，则可以在它们之间切换JVT而无需指令屏障。

如果任一次指令获取发生异常，xEPC设置为表跳转指令的PC，xCAUSE设置为预期的故障类型，xTVAL（如果未设置为零）包含导致故障的获取地址。

## 29.14.3. jvt CSR

### 概要

表跳转基向量和控制寄存器

地址：

0x017

权限：

URW

格式（RV32）：

```
31          6  5      0
base[XLEN-1:6] (WARL) mode
XLEN-6              6
```

格式（RV64）：

```
63          6  5      0
base[XLEN-1:6] (WARL) mode
XLEN-6              6
```

### 描述

*jvt*寄存器是一个XLEN位WARL读/写寄存器，保存跳转表配置，包括跳转表基地址（BASE）和跳转表模式（MODE）。

如果实现了第29.10节，则*jvt*也必须实现，但可以包含只读值。如果*jvt*是可写的，寄存器可持有的值集可能因实现而异。BASE字段中的值必须始终在64字节边界上对齐。注意CSR仅包含地址*base*的XLEN-1到6位。在计算跳转表访问时，*base*的低六位填充零以获得XLEN位跳转表基地址*jvt.base*，该地址始终在64字节边界上对齐。

*jvt.base*在启用虚拟内存时是虚拟地址。

*jvt.base*指向的内存被视为指令内存，用于执行表跳转指令，意味着具有执行访问权限。

*表41. jvt.mode定义*

||*表41. jvt.mode定义*|
|---|---|
|jvt.mode|注释|
|000000|跳转表模式|
|其他|保留用于未来标准使用|

*jvt.mode*是一个WARL字段，因此只能被编程为已实现的模式。因此发现机制是尝试编程不同的模式并读回值以查看哪些可用。跳转表模式*必须*被实现。

**评论：** *未来RISC-V Unified Discovery方法将报告可用模式。*

### 架构状态

*jvt* CSR向系统软件上下文（如OS进程）添加架构状态，因此必须在上下文切换时保存/恢复。
