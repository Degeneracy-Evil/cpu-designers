## 第34章 控制流完整性（CFI）

控制流完整性（Control-flow Integrity，CFI）功能有助于防御面向返回编程（ROP）和面向调用/跳转编程（COP/JOP）风格的控制流破坏攻击。这些攻击方法利用授权模块中的代码序列，序列中至少有一条指令是控制转移指令，该指令依赖于攻击者控制的数据（这些数据位于返回栈或内存中，用于获取调用或跳转的目标地址）。攻击者通过将控制流指令（例如 `JALR`、`C.JR`、`C.JALR`）从原始目标地址转移到新目标来拼接这些序列，这种转移通过修改返回栈中或用于获取跳转/调用目标地址的内存中的数据来实现。

RV32/RV64提供两种类型的控制转移指令——无条件跳转和条件分支。条件分支在指令的立即数字段中编码偏移量，因此是不易受控制流破坏影响的直接分支。使用 `JAL` 的无条件直接跳转将控制转移到距离当前 `pc` ±1 MiB范围内的目标。使用 `JALR` 的无条件间接跳转通过将指令中编码的符号扩展12位立即数与 `rs1` 寄存器相加来获取其分支目标。

RV32I/RV64I没有专用于调用过程或从过程返回的指令。可以使用 `JAL` 或 `JALR` 执行过程调用，并使用 `JALR` 从过程返回。然而，RISC-V ABI定义了以下约定：`JAL` / `JALR` 中 `rd`（即链接寄存器）是 `x1` 或 `x5` 时为过程调用，`JALR` 中 `rs1` 是约定的链接寄存器（即 `x1` 或 `x5`）时为从过程返回。该架构允许使用这些提示和约定来支持返回地址预测（参见表3）。

RVC压缩指令标准扩展提供了无条件跳转和条件分支指令。`C.J` 和 `C.JAL` 指令在指令的立即数字段中编码偏移量，因此不易受控制流破坏影响。`C.JR` 和 `C.JALR` RVC指令执行到寄存器 `rs1` 中地址的无条件控制转移。`C.JALR` 还将跳转后指令的地址（`pc+2`）写入链接寄存器 `x1`，是一个过程调用。如果 `rs1` 是约定的链接寄存器（即 `x1` 或 `x5`），则 `C.JR` 是从过程返回；否则它是间接跳转。

术语 **调用（call）** 用于指代以链接寄存器为目的地的 `JAL` 或 `JALR` 指令，即 _rd_ ≠ `x0`。按照约定，链接寄存器是 `x1` 或 `x5`。使用 `JAL` 或 `C.JAL` 的 _调用_ 称为直接调用。`C.JALR` 展开为 `JALR x1, 0(rs1)`，是一个 _调用_。使用 `JALR` 或 `C.JALR` 的 _调用_ 称为 _间接调用（indirect-call）_。

术语 **返回（return）** 用于指代 _rd_ = `x0` 且 _rs1_ = `x1` 或 _rs1_ = `x5` 的 `JALR` 指令。`C.JR` 指令展开为 `JALR x0, 0(rs1)`，如果 _rs1_ = `x1` 或 _rs1_ = `x5`，则为 _返回_。

术语 **间接跳转（indirect-jump）** 用于指代 _rd_ = `x0` 且 _rs1_ 不是 `x1` 或 `x5`（即不是返回）的 `JALR` 指令。`C.JR` 指令中如果 _rs1_ 不是 `x1` 或 `x5`（即不是返回），则为 _间接跳转_。

Zicfiss和Zicfilp扩展建立在这些约定和提示的基础上，分别提供后向边和前向边控制流完整性。

Zicfilp扩展的非特权ISA在第34.1节中规定，Zicfiss扩展的非特权ISA在第34.2节中规定。这些扩展的特权ISA在特权ISA规范中规定。

## 34.1. 着陆板（Zicfilp）

为了强制前向边控制流完整性，Zicfilp扩展引入了着陆板（`LPAD`）指令。`LPAD` 指令必须放置在作为间接跳转或调用有效目标的程序位置。`LPAD` 指令（参见第34.1.2节）使用 `AUIPC` 主操作码编码，其中 _rd_ = `x0`。

编译器在地址可取函数的开头以及任何间接跳转目标处发出着陆板指令。仅通过直接调用或直接跳转到达的函数不需要着陆板指令。

着陆板旨在为通过间接调用和跳转执行的控制转移提供完整性，这被称为前向边保护。当Zicfilp处于活动状态时，hart跟踪一个预期着陆板（`ELP`）状态，该状态由 _间接调用_ 或 _间接跳转_ 更新，要求分支目标处有一条着陆板指令。如果目标处的指令不是着陆板，则引发软件检查异常。

着陆板可以选择性地关联一个20位标签。启用标签后，可以使用基于编程语言的策略定义从间接调用或跳转位置可达的着陆板数量。着陆板标签使软件能够在将间接调用/跳转位置与有效目标配对时实现更高的精度。当使用着陆板标签时，间接调用或间接跳转位置可以指定着陆板的预期标签，从而约束程序中每个间接调用或间接跳转位置可达的着陆板集合。

在最简单的形式中，程序可以构建为使用单个标签值来实现粗粒度版本的前向边控制流完整性。通过约束gadget必须在标记间接可调用函数开始的着陆板指令之前，程序可以显著减少可用的gadget空间。第二种标签生成形式可以生成签名，例如使用函数原型的MAC。使用此方法的程序将进一步约束可从调用位置访问的gadget，仅限于与所调用函数原型匹配的间接可调用函数。另一种标签生成方法涉及分析程序的控制流图（CFG），这可以对可达gadget集合施加更严格的约束。此类程序还可以为每个函数使用多个标签，这意味着如果从两个或多个调用位置调用某个函数，该函数可以被标记为可从每个调用位置到达。例如，考虑两个调用位置A和B，其中A调用函数X和Y，B调用函数Y和Z。在单标签方案中，函数X、Y和Z需要被分配相同的标签，以便两个调用位置A和B都能调用公共函数Y。此方案将允许调用位置A也调用函数Z，调用位置B也调用函数X。然而，如果函数Y被分配了两个标签——一个对应于调用位置A，另一个对应于调用位置B，那么Y可以被两个调用位置调用，但X只能被调用位置A调用，Z只能被调用位置B调用。为了支持多标签，编译器可以为共享函数生成特定于调用位置的入口点，每个入口点有自己的着陆板指令，后跟一个到函数开头的直接分支。这将允许函数标记多个标签，每个标签对应于特定的调用位置。部分标签空间可以保留用于静态签名，其余部分可用于基于CFG的标签分配。

当Zicfilp在某个特权级别不活动或扩展未实现时，`LPAD` 指令使用定义为 `AUIPC` 操作码HINT的代码点，着陆板指令作为无操作执行。因此，使用 `LPAD` 指令构建的程序可以在不支持Zicfilp扩展或Zicfilp扩展未激活的处理器上继续正确运行，但没有前向边控制流完整性。

编译器和链接器应提供属性标志来指示程序是否已使用Zicfilp扩展编译，并使用该标志来确定是否应激活Zicfilp扩展。动态加载器应仅在应用程序使用的所有可执行文件（应用程序和依赖的动态链接库）都使用Zicfilp扩展时，才为应用程序激活Zicfilp扩展。

当Zicfilp扩展未激活或未实现时，hart不需要在间接调用/跳转的目标处有着陆板指令，着陆板指令恢复为无操作。这允许使用着陆板指令编译的程序正确运行，但没有前向边控制流完整性。

Zicfilp扩展可以单独且独立地为每个特权模式激活使用。

Zicfilp扩展依赖于Zicsr扩展。

## 34.1.1. 着陆板强制执行

为了强制间接调用或间接跳转的目标必须是有效的着陆板指令，hart维护一个预期着陆板（`ELP`）状态，以确定在间接调用或间接跳转的目标处是否需要着陆板指令。`ELP` 状态可以是以下之一：

- 0 - `NO_LP_EXPECTED`
- 1 - `LP_EXPECTED`

`ELP` 状态在复位时由hart初始化为 `NO_LP_EXPECTED`。

当Zicfilp扩展启用时，它确定间接调用或间接跳转是否必须落在着陆板上，如清单4所述。如果 `is_lp_expected` 为1，则hart将 `ELP` 更新为 `LP_EXPECTED`。

```
  is_lp_expected = ( (JALR || C.JR || C.JALR) &&
                     (rs1 != x1) && (rs1 != x5) && (rs1 != x7) ) ? 1 : 0;
```

_清单4. 着陆板预期判断_

使用 `JALR`、`C.JALR` 或 `C.JR` 且 `rs1` 为 `x7` 的间接分支称为软件保护分支。此类分支不需要落在 `LPAD` 指令上，因此不会将 `ELP` 设置为 `LP_EXPECTED`。

_当寄存器源是链接寄存器且寄存器目的地是 `x0` 时，则是从过程返回，不需要在目标处有着陆板。_

_当寄存器源和寄存器目的地都是链接寄存器时，则为语义直接调用。例如，`call offset` 伪指令可能展开为由 `lui ra, imm20` 或 `auipc ra, imm20` 指令后跟 `jalr ra, imm12(ra)` 指令组成的两条指令序列，其中 `ra` 是链接寄存器（`x1` 或 `x5`）。由于过程地址未被显式获取，且计算出的地址不从可变内存中获取，因此此类语义直接调用不需要在目标处放置着陆板。编译器和JIT引擎必须仅在 `rs1` 作为PC相对或绝对偏移量计算得出时才使用语义直接调用。_

_用于远距离过程尾调用的 `tail offset` 伪指令也可以展开为由 `lui x7, imm20` 或 `auipc x7, imm20` 后跟 `jalr x0, x7` 组成的两条指令序列。由于过程地址未被显式获取且计算出的地址不从可变内存获取，此类语义直接尾调用不需要在目标处放置着陆板。_

_编译器也可以使用软件保护分支来生成诸如switch-case结构的代码。使用软件保护分支时，编译器需要确保它对可能的跳转目标有完全控制（例如，通过从内存中的只读表获取目标并对表索引进行边界检查等）。_

着陆板可以带有标签。Zicfilp扩展指定寄存器 `x7` 用作着陆板标签寄存器。为了支持带标签的着陆板，间接调用/跳转位置在 `x7` 寄存器的位31:12中建立预期着陆板标签（例如使用 `LUI` 指令）。`LPAD` 指令编码有一个20位立即数值，称为着陆板标签（`LPL`），该值与预期着陆板标签匹配。当 `LPL` 编码为零时，`LPAD` 指令不执行标签检查，在使用此单标签操作模式构建的程序中，间接调用/跳转位置不需要在 `x7` 中建立预期着陆板标签值。

当 `ELP` 设置为 `LP_EXPECTED` 时，如果指令流中的下一条指令不是4字节对齐的，或不是 `LPAD`，或 `LPAD` 中编码的着陆板标签不为零且与 `x7` 寄存器位31:12中的预期着陆板标签不匹配，则引发软件检查异常（cause=18），_`x`_ `tval` 设置为"着陆板故障（landing pad fault，code=2）"，否则 `ELP` 更新为 `NO_LP_EXPECTED`。

_对 `ELP` 的跟踪以及要求间接调用和跳转目标处有着陆板指令，使处理器实现能够显著减少或阻止对非着陆板指令的推测。使用此技术约束推测极大地减少了gadget空间，并增加了使用诸如分支目标注入（也称为Spectre变体2）等技术的难度，这些技术使用推测执行通过侧信道泄露数据。_

_`LPAD` 要求4字节对齐是为了解决程序中两条指令 `A` 和 `B` 意外拼接形成非预期着陆板的问题。例如，考虑一条32位指令，其字节3和2的模式为 `?017h`（例如 `LUI`、`AUIPC` 或 `JAL` 指令的立即数字段），后跟一条16位或32位指令。当检测到可能意外形成有效着陆板的模式时，汇编器或链接器可以强制指令 `A` 对齐到4字节边界，使非预期的 `LPAD` 模式变为未对齐从而不是有效着陆板，或者可以使用替代寄存器分配来阻止意外着陆板。_

## 34.1.2. 着陆板指令

当Zicfilp启用时，`LPAD` 是唯一允许在 `ELP` 状态为 `LP_EXPECTED` 时执行的指令。如果Zicfilp未启用，则该指令为无操作。如果Zicfilp启用，`LPAD` 指令在以下任何条件为真时引发软件检查异常，_`x`_ `tval` 设置为"着陆板故障（code=2）"：

- `pc` 不是4字节对齐的且 `ELP` 为 `LP_EXPECTED`。
- `ELP` 为 `LP_EXPECTED` 且 `LPL` 不为零且 `LPL` 与 `x7` 寄存器位31:12中的预期着陆板标签不匹配。

如果未引发软件检查异常，则 `ELP` 更新为 `NO_LP_EXPECTED`。

```
31 12 11 7 6 0
LPL rd opcode
00000 AUIPC
```

`LPAD` 指令的操作如下：

```
if (xLPE == 1 && ELP == LP_EXPECTED)
    // 如果PC不是4字节对齐，则引发软件检查异常
    if pc[1:0] != 0
        raise software-check exception
    // 如果着陆板标签不匹配 -> 软件检查异常
    else if (inst.LPL != x7[31:12] && inst.LPL != 0)
        raise software-check exception
    else
        ELP = NO_LP_EXPECTED
else
    no-op
endif
```

## 34.2. 影子栈（Zicfiss）

Zicfiss扩展引入影子栈来强制后向边控制流完整性。影子栈是第二个栈，用于存储链接寄存器中返回地址的影子副本（如果需要溢出）。

影子栈旨在为使用 _返回_ 执行的控制转移提供完整性，其中返回可能来自通过间接调用或直接调用调用的过程，这被称为后向边保护。

使用后向边控制流完整性的程序有两个栈：常规栈和影子栈。影子栈用于在非叶函数需要时溢出链接寄存器。架构中引入了一个额外的寄存器——影子栈指针（`ssp`），用于保存活动影子栈顶部的地址。

影子栈与常规栈类似，向下增长，从较高地址到较低地址。影子栈上的每个条目宽度为 `XLEN`，保存链接寄存器值。`ssp` 指向影子栈的顶部，即存储在影子栈上的最后一个元素的地址。

影子栈在架构上受到保护，防止意外损坏和修改，详见特权规范。

Zicfiss扩展提供了将链接寄存器存储/加载到/从影子栈以及检查返回地址完整性的指令。该扩展提供了支持常见栈维护操作（如栈展开和栈切换）的指令。

当Zicfiss启用时，每个需要溢出链接寄存器的函数（通常是非叶函数）在进入函数时（序言）将链接寄存器值存储到常规栈，并将链接寄存器值的影子副本存储到影子栈。当此类函数返回时（尾声），函数从常规栈加载链接寄存器，并从影子栈加载链接寄存器的影子副本。然后比较来自常规栈的链接寄存器值和来自影子栈的影子链接寄存器值。两个值不匹配表明返回地址控制变量被破坏，并引发软件检查异常。

除 `SSAMOSWAP.W/D` 外，Zicfiss指令使用由Zimop和Zcmop扩展定义的May-Be-Operation指令的子集进行编码。当Zicfiss扩展未实现或扩展未激活时，这些指令子集恢复为其Zimop/Zcmop定义的行为。因此，使用Zicfiss指令构建的程序可以在不支持Zicfiss扩展或Zicfiss扩展未激活的处理器上继续正确运行，但没有后向边控制流完整性。Zicfiss扩展可以单独且独立地为每个特权模式激活使用。

编译器应标记每个目标文件（例如使用ELF属性中的标志）以指示目标文件是否已使用Zicfiss指令编译。链接器应仅在链接的所有目标文件具有相同的Zicfiss属性时标记生成的二进制/可执行文件（例如使用ELF属性中的标志）为使用Zicfiss指令编译的。

动态加载器应仅在应用程序使用的所有可执行文件（应用程序和依赖的动态链接库）都使用Zicfiss扩展时，才为应用程序激活Zicfiss扩展。

Zicfiss扩展处于活动状态的应用程序可以在运行时请求动态加载器加载新的动态共享对象（例如使用dlopen()）。如果请求的对象没有Zicfiss属性，则动态加载器可以根据其策略（例如由操作系统或管理员建立）配置，要么拒绝请求，要么为应用程序停用Zicfiss扩展。强烈建议策略强制执行严格的安全态势并拒绝请求。

Zicfiss扩展依赖于Zicsr、Zimop和Zaamo扩展。此外，如果实现了Zcmop扩展，Zicfiss扩展还提供 `C.SSPUSH` 和 `C.SSPOPCHK` 指令。此外，在U-mode中使用Zicfiss需要实现S-mode。不支持在M-mode中使用Zicfiss。

## 34.2.1. Zicfiss指令摘要

Zicfiss扩展引入以下指令：

- 推入影子栈（参见第34.2.4节）
  - `SSPUSH x1` 和 `SSPUSH x5` — 使用 `MOP.RR.7` 编码
  - `C.SSPUSH x1` — 使用 `C.MOP.1` 编码

- 从影子栈弹出（参见第34.2.5节）
  - `SSPOPCHK x1` 和 `SSPOPCHK x5` — 使用 `MOP.R.28` 编码
  - `C.SSPOPCHK x5` — 使用 `C.MOP.5` 编码

- 将 `ssp` 的值读入寄存器（参见第34.2.6节）
  - `SSRDP` — 使用 `MOP.R.28` 编码

- 从影子栈位置执行原子交换（参见第34.2.7节）
  - `SSAMOSWAP.W` 和 `SSAMOSWAP.D`

Zicfiss不使用 `MOP.RR.7` 或 `MOP.R.28` 的所有编码。当 `MOP.RR.7` 或 `MOP.R.28` 编码未被Zicfiss扩展使用时，相应指令遵守其Zimop定义的行为，除非被另一个扩展重新定义。

## 34.2.2. 影子栈指针（`ssp`）

`ssp` CSR是一个非特权读写（URW）CSR，读写影子栈指针（`ssp`）的 `XLEN` 低阶位。CSR地址为0x011。没有定义高CSR，因为 `ssp` 始终与当前特权模式的 `XLEN` 一样宽。`ssp` 的位1:0是只读零。如果UXLEN或SXLEN可能永远不是32，则位2也是只读零。

## 34.2.4. 推入影子栈

影子栈推入操作定义为 `ssp` 减去 `XLEN/8`，然后将链接寄存器中的值存储到新影子栈顶部的内存中。

只有 `x1` 和 `x5` 寄存器被支持作为 `SSPOPCHK` 的 `rs1`。Zicfiss使用Zcmop定义的 `C.MOP.5` 编码提供 `SSPOPCHK x5` 的16位版本。`C.SSPOPCHK x5` 展开为 `SSPOPCHK x5`。

使用影子栈的程序在非叶函数的序言中将返回地址推入常规栈以及影子栈。当从这些非叶函数返回时，此类程序从常规栈弹出链接寄存器，并从影子栈弹出链接寄存器的影子副本。然后比较两个值。如果值不匹配，表明常规栈上的返回地址变量被破坏。

`SSPOPCHK` 指令及其压缩形式 `C.SSPOPCHK` 可用于从影子栈弹出影子返回地址值，并检查该值是否与链接寄存器的内容匹配，如果不匹配，则引发软件检查异常，_`x`_ `tval` 设置为"影子栈故障（shadow stack fault，code=3）"。

虽然任何寄存器都可以用作链接寄存器，但按照约定使用 `x1` 或 `x5` 寄存器。影子栈指令设计为使 `x1` 和 `x5` 寄存器用作链接寄存器时最为高效。

_返回地址预测栈是高性能指令获取单元的常见特性，但需要准确检测用于过程调用和返回的指令才能有效。对于RISC-V，使用指令的提示通过所使用的寄存器号隐式编码。RAS操作（弹出和/或推入）在表3中规定。_

_使用 `x1` 或 `x5` 作为链接寄存器使程序能够受益于返回地址预测栈。此外，由于影子栈指令是围绕使用 `x1` 或 `x5` 作为链接寄存器设计的，使用任何其他寄存器作为链接寄存器将产生额外的寄存器移动成本。_

_编译器在生成具有后向边CFI的代码时，必须保护链接寄存器（例如 `x1` 和/或 `x5`）免受任意修改，不得发出不安全的代码序列。_

_在两个栈上都存储返回地址保留了调用栈布局和ABI，同时也允许检测常规栈上返回地址的损坏。使用影子栈的非叶函数的序言和尾声如下：_

```
    function_entry:
        addi sp,sp,-8  # 将链接寄存器x1推入
        sd x1,(sp)     # 常规栈
        sspush x1      # 将链接寄存器x1推入影子栈
         :
        ld x1,(sp)     # 从常规栈弹出链接寄存器x1
        addi sp,sp,8
        sspopchk x1    # 如果x1不等于影子返回地址则故障
                       # 
        ret
```

_此示例说明了使用 `x1` 寄存器作为链接寄存器。或者，`x5` 寄存器也可以用作链接寄存器。_

_叶函数（本身不进行函数调用的函数）不需要溢出链接寄存器。因此，返回值可以在叶函数执行期间一直保存在链接寄存器本身中。_

`C.SSPOPCHK` 和 `SSPOPCHK` 指令执行加载操作，与现有加载指令相同，区别在于基址隐式为 `ssp`，宽度隐式为 `XLEN`。

`SSPOPCHK` 和 `C.SSPOPCHK` 指令的操作如下：

```
if (xSSE == 1)
    temp = mem[ssp]            # 从ssp中的地址加载temp
    if temp != X(src)          # 将temp与src中的值比较，
                               # 如果它们不是按位相等的则引发软件检查异常。
                               # 只有x1和x5可以用作src
       raise software-check exception
    else
       ssp = ssp + (XLEN/8)    # ssp增加XLEN/8。
    endif
endif
```

_清单7. `SSPOPCHK` 和 `C.SSPOPCHK` 操作_

如果从 `ssp` 中的地址加载的值与 `rs1` 中的值不匹配，则引发软件检查异常（cause=18），_`x`_ `tval` 设置为"影子栈故障（code=3）"。由 `SSPOPCHK` / `C.SSPOPCHK` 引起的软件检查异常优先级低于加载/存储/AMO访问故障异常。

仅当从影子栈的加载成功完成且未引发软件检查异常时，`ssp` 才被 `SSPOPCHK` 和 `C.SSPOPCHK` 递增。

_当ABI使用 `x1` 作为链接寄存器时，使用压缩指令 `C.SSPUSH x1` 推入影子栈最为高效，因为链接寄存器可以在函数序言中不需要寄存器间移动即可推入。要使用压缩指令 `C.SSPOPCHK x5`，函数应将返回地址从常规栈弹出到备用链接寄存器 `x5` 中，并使用 `C.SSPOPCHK x5` 将返回地址与存储在影子栈上的影子副本进行比较。然后函数使用 `C.JR x5` 跳转到返回地址。_

```
    function_entry:
        c.addi sp,sp,-8  # 将链接寄存器x1推入
        c.sd x1,(sp)     # 常规栈
        c.sspush x1      # 将链接寄存器x1推入影子栈
         :
        c.ld x5,(sp)     # 从常规栈弹出链接寄存器x5
        c.addi sp,sp,8
        c.sspopchk x5    # 如果x5不等于影子返回地址则故障
        c.jr x5
```

_存储到加载转发是高性能处理器实现采用的一种常见技术。Zicfiss实现可以阻止从非影子栈存储到 `SSPOPCHK` 或 `C.SSPOPCHK` 指令的转发。对映射为影子栈的页面进行的非影子栈存储会导致故障。然而，此类确定可能延迟到PTE被检查之后，因此可能用于将此数据从此类存储瞬时转发到 `SSPOPCHK` 或 `C.SSPOPCHK`。_

_清单8. `SSRDP` 操作_

_当使用Zimop的扩展未实现或未激活时，Zimop将0写入 `rd` 的特性可用于确定Zicfiss扩展是否处于活动状态。例如，展开影子栈的函数可以通过动态检测Zicfiss扩展是否处于活动状态来跳过展开操作。_

_可以使用如下示例序列：_

```
    ssrdp t0                      # 将ssp移动到t0
    beqz t0, zicfiss_not_active   # 零按约定不是有效的影子
                                  #   栈指针
    # Zicfiss处于活动状态
     :
     :
zicfiss_not_active:
```

_为了协助使用此类代码序列，操作系统和运行时不得将影子栈定位在地址0。_

_对栈执行的常见操作是展开它们以支持诸如 `setjmp` / `longjmp`、C++异常处理等构造。使用影子栈的程序必须除了用于存储数据的栈之外还展开影子栈。展开函数必须验证它不会意外展开超出影子栈的边界。影子栈预期使用保护页在两端进行边界限制。栈的保护页是该栈所属进程不可访问的页面。为了检测展开是否超出影子栈的边界，展开可以以最大4 KiB的增量进行，测试 `ssp` 是否仍然指向影子栈页面还是已经展开到保护页中。以下示例说明了使用影子栈指令展开影子栈的用法。此示例假设 `setjmp` 函数本身不向影子栈推入（作为叶函数，不需要推入）。_

```
setjmp() {
     :
     :
// 读取并保存影子栈指针到jmp_buf
    asm("ssrdp %0" : "=r"(cur_ssp):);
jmp_buf->saved_ssp = cur_ssp;
     :
     :
}
longjmp() {
     :
// 读取当前影子栈指针并
// 计算要展开的调用帧数量
    asm("ssrdp %0" : "=r"(cur_ssp):);
// 如果后向边CFI未激活则跳过展开
    asm("beqz %0, back_cfi_not_active" : "=r"(cur_ssp):);
// 在循环中展开帧
while ( jmp_buf->saved_ssp > cur_ssp ) {
// 每次最多前进4K以避免
// 展开超出影子栈边界
        cur_ssp = ( (jmp_buf->saved_ssp - cur_ssp) >= 4096 ) ?
                  (cur_ssp + 4096) : jmp_buf->saved_ssp;
        asm("csrw ssp, %0" : :  "r" (cur_ssp));
// 测试是否展开超出影子栈边界
        asm("sspush x5");
        asm("sspopchk x5");
    }
back_cfi_not_active:
     :
}
```

对于RV32，`SSAMOSWAP.W` 从 `rs1` 中影子栈位置的地址原子加载32位数据值，将加载的值放入寄存器 `rd`，并将 `rs2` 中保存的32位值存储到 `rs1` 中的原始地址。`SSAMOSWAP.D`（仅限RV64）与 `SSAMOSWAP.W` 类似，但操作64位数据值。

      raise illegal-instruction exception

_清单9. 用于RV32的 `SSAMOSWAP.W` 和用于RV64的 `SSAMOSWAP.D` 操作_

对于RV64，`SSAMOSWAP.W` 从 `rs1` 中影子栈位置的地址原子加载32位数据值，对加载的值进行符号扩展并将其放入 `rd`，并将 `rs2` 中值的低32位存储到 `rs1` 中的原始地址。

```
  if privilege_mode != M && menvcfg.SSE == 0
      raise illegal-instruction exception
  else if S-mode not implemented
      raise illegal-instruction exception
  else if privilege_mode == U && senvcfg.SSE == 0
      raise illegal-instruction exception
  else if privilege_mode == VS && henvcfg.SSE == 0
      raise virtual-instruction  exception
  else if privilege_mode == VU && senvcfg.SSE == 0
      raise virtual-instruction  exception

      temp[31:0] = mem[X(rs1)]
      X(rd) = SignExtend(temp[31:0])
      mem[X(rs1)] = X(rs2)[31:0]
  endif
```

_清单10. 用于RV64的 `SSAMOSWAP.W`_

与A扩展中的AMO一样，`SSAMOSWAP.W/D` 要求 `rs1` 中保存的地址与操作数大小自然对齐（即对于 _双字_ 为八字节对齐，对于 _字_ 为四字节对齐）。

如果地址未自然对齐，则适用相同的异常选项。

与A扩展中的AMO一样，`SSAMOSWAP.W/D` 可选地提供释放一致性语义，使用 `aq` 和 `rl` 位来帮助实现多处理器同步。如果 `aq=1`，`SSAMOSWAP.W/D` 操作具有获取语义，如果 `rl=1`，则具有释放语义。

_栈切换是用户程序和超级用户程序中的常见操作。执行栈切换时，当前活动栈的栈指针被保存到上下文数据结构中，并通过从上下文数据结构加载新栈指针使新栈变为活动状态。_

_当程序启用了影子栈时，程序需要额外切换影子栈指针。如果已停用影子栈顶部的指针保存在上下文数据结构中，则它可能容易受到内存损坏漏洞的影响。为了保护指针值，程序可以将其存储在已停用影子栈本身的顶部，从而创建一个检查点。合法检查点定义为保存值 `X` 的检查点，其中 `X` 是检查点位于影子栈上的地址。_

_从新影子栈恢复影子栈指针并将旧影子栈指针保存到旧影子栈上的示例序列如下：_

```
# a0保存要切换到的新影子栈顶部指针
stack_switch:
   ssrdp ra
   beqz ra, 2f                    # 如果Zicfiss未激活则跳过
   ssamoswap.d ra, x0,  (a0)      # ra=*[a0] 且 *[a0]=0
   beq         ra, a0,  1f        # [a0] 必须等于 [ra]
   unimp                          # 否则崩溃
1: addi        ra, ra,  XLEN/8    # 弹出检查点
   csrrw       ra, ssp, ra        # 交换ssp: ra=ssp, ssp=ra
   addi        ra, ra,  -(XLEN/8) # checkpoint = "old ssp - XLEN/8"
   ssamoswap.d x0, ra,  (ra)      # 将检查点保存在 "old ssp - XLEN/8"
2:
```

_此序列使用 `ra` 寄存器。如果执行此序列的特权模式可以被中断，则陷阱处理程序应将 `ra` 保存在影子栈本身上。在那里它受到防篡改保护，并且可以在从陷阱返回之前恢复。_

_当超级用户创建新的影子栈时，它需要在该栈的最高地址存储一个检查点。这使得可以使用本说明中概述的过程切换影子栈指针。`SSAMOSWAP.W/D` 指令可用于存储此检查点。当 `SSAMOSWAP.W/D` 操作的内存位置处的旧值不需要时，可以将 `rd` 设置为 `x0`。_
