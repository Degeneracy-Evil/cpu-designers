## 第1章 引言

RISC-V（读作 "risk-five"）是一种新的指令集架构（ISA），最初旨在支持计算机体系结构研究与教育，但现在我们希望它也能成为工业实现的标准自由开放架构。我们定义 RISC-V 的目标包括：

- 一个完全*开放*的 ISA，可供学术界和工业界自由使用。

- 一个*真正*的 ISA，适用于直接的本地硬件实现，而不仅仅是仿真或二进制翻译。

- 一个避免针对特定微架构风格（如微码、顺序执行、解耦、乱序执行）或实现技术（如全定制、ASIC、FPGA）"过度架构化"的 ISA，但允许在任何这些方式中高效实现。

- 一个分离为*小型*基本整数 ISA 的 ISA，可单独作为定制加速器或教育目的的基础，并提供可选的标准扩展以支持通用软件开发。

- 支持修订后的 2008 IEEE-754 浮点标准。（*ANSI/IEEE Std 754-2008, IEEE 浮点算术标准*，2008）

- 一个支持广泛 ISA 扩展和专用变体的 ISA。

- 为应用程序、操作系统内核和硬件实现提供 32 位和 64 位地址空间变体。

- 一个支持高度并行多核或众核实现的 ISA，包括异构多处理器。

- 可选的*变长指令*，既扩展可用的指令编码空间，又支持可选的*密集指令编码*以提高性能、减小静态代码尺寸和提升能效。

- 一个完全可虚拟化的 ISA，以简化虚拟机管理程序开发。

- 一个简化新特权架构设计实验的 ISA。

**评论：** *关于我们设计决策的评论以此段落格式呈现。如果读者只对规范本身感兴趣，可以跳过这些非规范性文本。*

**评论：** *RISC-V 这个名字被选为代表加州大学伯克利分校第五个主要 RISC ISA 设计（RISC-I (Patterson & Séquin, 1981)，RISC-II (Katevenis et al., 1983)，SOAR (Ungar et al., 1984) 和 SPUR (Lee et al., 1989) 是前四个）。我们还用罗马数字 "V" 来双关表示"变体"（variations）和"向量"（vectors），因为支持包括各种数据并行加速器在内的一系列体系结构研究是 ISA 设计的一个明确目标。*

RISC-V ISA 的定义尽可能避免实现细节（尽管包含了关于受实现驱动的决策的评论），应将其解读为对各种实现的软件可见接口，而非特定硬件器件的设计。RISC-V 手册分为两卷。本卷涵盖基本*非特权*指令的设计，包括可选的非特权 ISA 扩展。非特权指令是指通常在所有特权架构的所有特权模式下都可用的指令，尽管其行为可能因特权模式和特权架构而异。第二卷提供了第一个（"经典"）特权架构的设计。手册使用 IEC 80000-13:2008 约定，一个字节为 8 位。

**评论：** *在非特权 ISA 设计中，我们试图消除对特定微架构特征（如缓存行大小）或特权架构细节（如页翻译）的任何依赖。这既是为了简单性，也是为了允许替代微架构或替代特权架构的最大灵活性。*

## 1.1. RISC-V 硬件平台术语

一个 RISC-V 硬件平台可以包含一个或多个 RISC-V 兼容的处理核心，以及其他的非 RISC-V 兼容核心、固定功能加速器、各种物理内存结构、I/O 设备，以及允许各组件通信的互连结构。

如果一个组件包含独立的指令取指单元，则称之为*核心*（core）。一个 RISC-V 兼容核心可以通过多线程技术支持多个 RISC-V 兼容硬件线程（称为 *hart*）。

一个 RISC-V 核心可能具有额外的专用指令集扩展或附加的*协处理器*（coprocessor）。我们使用术语*协处理器*来指代连接到 RISC-V 核心并主要由 RISC-V 指令流驱动的单元，但它包含额外的架构状态和指令集扩展，并且可能具有相对于主 RISC-V 指令流的某种有限的自主性。

我们使用术语*加速器*（accelerator）来指代不可编程的固定功能单元或可以自主运行但专用于某些任务的核心。在 RISC-V 系统中，我们期望许多可编程加速器将是带有专用指令集扩展和/或定制协处理器的基于 RISC-V 的核心。一个重要的 RISC-V 加速器类别是 I/O 加速器，它们从主应用核心卸载 I/O 处理任务。

RISC-V 硬件平台的系统级组织可以从单核微控制器到包含数千个节点的共享内存众核服务器节点集群。即使是小型片上系统也可能被构造为多计算机和/或多处理器的层次结构，以模块化开发工作或提供子系统之间的安全隔离。

## 1.2. RISC-V 软件执行环境与 Hart

一个 RISC-V 程序的行为取决于其运行的执行环境。RISC-V 执行环境接口（EEI）定义了程序的初始状态、环境中 hart 的数量和类型（包括 hart 支持的特权模式）、内存和 I/O 区域的可访问性和属性、每个 hart 上执行的所有合法指令的行为（即 ISA 是 EEI 的一个组成部分），以及在执行期间引发的任何中断或异常的处理（包括环境调用）。EEI 的示例包括 Linux 应用程序二进制接口（ABI），或 RISC-V 超级用户二进制接口（SBI）。RISC-V 执行环境的实现可以是纯硬件、纯软件，或硬件与软件的组合。例如，操作码自陷和软件仿真可用于实现硬件未提供的功能。执行环境实现的示例包括：

- "裸机"硬件平台，其中 hart 直接由物理处理器线程实现，指令具有对物理地址空间的完全访问权限。硬件平台定义了一个从上电复位开始的执行环境。

- RISC-V 操作系统，通过将用户级 hart 多路复用到可用的物理处理器线程上，并通过虚拟内存控制对内存的访问，提供多个用户级执行环境。

- RISC-V 虚拟机管理程序，为客户操作系统提供多个超级用户级执行环境。

- RISC-V 仿真器，如 Spike、QEMU 或 rv8，它们在底层的 x86 系统上仿真 RISC-V hart，可以提供用户级或超级用户级执行环境。

**评论：** *裸硬件平台可以被视为定义了一个 EEI，其中可访问的 hart、内存和其他设备构成了环境，初始状态是上电复位的状态。通常，大多数软件被设计为使用对硬件更抽象的接口，因为更抽象的 EEI 在不同硬件平台上提供更大的可移植性。通常 EEI 是分层叠加的，其中一个较高级别的 EEI 使用另一个较低级别的 EEI。*

从在给定执行环境中运行的软件的角度来看，hart 是一种资源，它在该执行环境中自主地取指和执行 RISC-V 指令。在这方面，hart 的行为类似于硬件线程资源，即使被执行环境时分复用到真实硬件上。一些 EEI 支持创建和销毁额外的 hart，例如通过环境调用分叉新的 hart。

执行环境负责确保其每个 hart 的最终前向进展。对于给定的 hart，当该 hart 正在使用明确等待事件的机制时（例如本规范第二卷中定义的等待中断指令），该责任暂停；如果 hart 被终止，该责任结束。以下事件构成前向进展：

- 一条指令的退役。

- 一个自陷（trap），如第 1.6 节所定义。

- 由扩展定义的构成前向进展的任何其他事件。

**评论：** *术语 hart 是在 Lithe (Pan et al., 2009) 和 (Pan et al., 2010) 的工作中引入的，用于提供一个表示抽象执行资源的术语，而不是软件线程编程抽象。*

**评论：** *硬件线程（hart）和软件线程上下文之间的重要区别在于，在执行环境内部运行的软件不负责使其每个 hart 取得进展；那是外部执行环境的责任。因此，从执行环境内部软件的角度来看，环境的 hart 像硬件线程一样运行。*

**评论：** *一个执行环境实现可以将一组客户 hart 时分多路复用到其自身执行环境提供的更少的主机 hart 上，但必须以客户 hart 像独立硬件线程一样运行的方式进行。特别是，如果客户 hart 多于主机 hart，则执行环境必须能够抢占客户 hart，且不能无限期等待客户 hart 上的客户软件"让出"对客户 hart 的控制。*

## 1.3. RISC-V ISA 概述

一个 RISC-V ISA 被定义为基本整数 ISA（必须在任何实现中存在），加上基本 ISA 的可选扩展。基本整数 ISA 与早期 RISC 处理器非常相似，但没有分支延迟槽，并且支持可选的变长指令编码。基本 ISA 被仔细限制为一组最小指令集，足以为编译器、汇编器、链接器和操作系统（带有额外的特权操作）提供合理的目标，因此它提供了一个方便的 ISA 和软件工具链"骨架"，围绕它可以构建更多定制处理器 ISA。

虽然方便说 *RISC-V ISA*，但 RISC-V 实际上是一个相关 ISA 的家族，目前有四个基本 ISA。每个基本整数指令集的特征在于整数寄存器的宽度和相应的地址空间大小，以及整数寄存器的数量。有两个主要的基本整数变体，RV32I 和 RV64I，分别在 第 2 章 和 第 4 章 中描述，它们分别提供 32 位或 64 位地址空间。我们使用术语 XLEN 来指代整数寄存器的位宽（32 或 64）。第 3 章 描述了 RV32E 和 RV64E 子集变体，它们分别是 RV32I 或 RV64I 基本指令集的缩减版本，已添加以支持小型微控制器，并且具有整数寄存器数量的一半。基本整数指令集对带符号整数值使用二进制补码表示。

**评论：** *虽然 64 位地址空间是大型系统的要求，但我们认为 32 位地址空间在未来几十年内对于许多嵌入式和客户端设备仍然是足够的，并且对于降低内存流量和能耗是可取的。此外，32 位地址空间对于教育目的是足够的。更大的平坦 128 位地址空间最终可能需要，并可以在现有 RISC-V ISA 框架内容纳一个新的 RV128I 基本 ISA。*

**评论：** *RISC-V 中的四个基本 ISA 被视为不同的基本 ISA。一个常见的问题是为什么没有单一的 ISA，特别是为什么 RV32I 不是 RV64I 的严格子集？一些早期的 ISA 设计（SPARC、MIPS）在增加地址空间大小时采用严格超集策略，以支持在新的 64 位硬件上运行现有的 32 位二进制文件。*

**评论：** *明确分离基本 ISA 的主要优势在于每个基本 ISA 都可以针对其需求进行优化，而不需要支持其他基本 ISA 所需的所有操作。例如，RV64I 可以省略仅在 RV32I 中需要处理较窄寄存器的指令和 CSR。RV32I 变体可以使用原本为较宽地址空间变体所需的指令保留的编码空间。*

**评论：** *不将设计视为单一 ISA 的主要缺点是它复杂化了在一个基本 ISA 上仿真另一个基本 ISA 所需的硬件（例如，在 RV64I 上仿真 RV32I）。然而，寻址和非法指令自陷的差异通常意味着即使在完全超集指令编码下，无论如何也需要某种模式切换，而不同的 RISC-V 基本 ISA 足够相似，使得支持多个版本的成本相对较低。虽然有人提出严格超集设计将允许传统的 32 位库与 64 位代码链接，但即使在兼容编码的情况下，由于软件调用约定和系统调用接口的差异，这在实践中也是不可行的。*

**评论：** *RISC-V 特权架构在 `misa` 中提供了控制每个级别非特权 ISA 的字段，以支持在同一硬件上仿真不同的基本 ISA。我们注意到，较新的 SPARC 和 MIPS ISA 修订版已弃用在 64 位系统上不变地运行 32 位代码的支持。*

**评论：** *一个相关的问题是为什么 RV32I 中的 32 位加法（ADD）和 RV64I 中的 32 位加法（ADDW）使用不同的编码？ADDW 操作码可以用于 RV32I 中的 32 位加法，ADDD 用于 RV64I 中的 64 位加法，而不是现有的设计——即将相同的操作码 ADD 用于 RV32I 中的 32 位加法和 RV64I 中的 64 位加法，并用不同的操作码 ADDW 用于 RV64I 中的 32 位加法。这也将与在 RV32I 和 RV64I 中使用相同的 LW 操作码进行 32 位加载的做法更一致。最早的 RISC-V ISA 版本确实有这种替代设计的变体，但 RISC-V 设计在 2011 年 1 月更改为当前的选择。我们的重点是在 64 位 ISA 中支持 32 位整数，而不是提供与 32 位 ISA 的兼容性，其动机是消除因并非 RV32I 中的所有操作码都有 *W 后缀而产生的不对称性（例如，ADDW，但 AND 没有 ANDW）。回想起来，这可能没有充分论证，且是同时设计两个 ISA 而不是稍后添加一个坐在另一个之上的结果，也是我们认为必须将平台要求纳入 ISA 规范的信念所致，这意味着所有 RV32I 指令在 RV64I 中都是必需的。现在更改编码为时已晚，但由于上述原因，这也几乎没有实际影响。*

**评论：** *已经指出，我们可以将 *W 变体作为 RV32I 系统的扩展来启用，以提供跨越 RV64I 和未来 RV32 变体的通用编码。*

RISC-V 旨在支持广泛的定制和专业化。每个基本整数 ISA 可以通过一个或多个可选的指令集扩展进行扩展。扩展可以被分类为标准、定制或非兼容。为此，我们将每个 RISC-V 指令集编码空间（以及相关的编码空间，如 CSR）划分为三个不相交的类别：*标准*（standard）、*保留*（reserved）和*定制*（custom）。标准扩展和编码由 RISC-V International 定义；任何未经 RISC-V International 定义的扩展都是*非标准*的。每个基本 ISA 及其标准扩展仅使用标准编码，并且在使用这些编码时不应相互冲突。保留编码目前未定义，但为未来的标准扩展保留；一旦被使用，它们就成为标准编码。定制编码绝不能用于标准扩展，可用于供应商特定的非标准扩展。非标准扩展要么是仅使用定制编码的*定制*扩展，要么是使用任何标准或保留编码的*非兼容*扩展。指令集扩展通常是共享的，但可能根据基本 ISA 提供略有不同的功能。我们还为 RISC-V 基本指令和指令集扩展开发了命名约定，详见 第 37 章。

为支持更通用的软件开发，定义了一组标准扩展以提供整数乘除法、原子操作以及单精度和双精度浮点算术。基本整数 ISA 被命名为 "I"（根据整数寄存器宽度前缀 RV32 或 RV64），包含整数计算指令、整数加载、整数存储和控制流指令。标准整数乘除法扩展被命名为 "M"，添加了用于乘除整数寄存器中值的指令。标准原子指令扩展，记为 "A"，添加了用于处理器间同步的原子读、修改、写内存指令。标准单精度浮点扩展，记为 "F"，添加了浮点寄存器、单精度计算指令以及单精度加载和存储。标准双精度浮点扩展，记为 "D"，扩展了浮点寄存器，并添加了双精度计算指令、加载和存储。标准 "C" 压缩指令扩展提供了常见指令的更窄 16 位形式。

在基本整数 ISA 和这些标准扩展之外，我们认为很少有一条新指令会为所有应用提供显著的好处，尽管它可能对某个特定领域非常有益。随着能效问题迫使更强的专业化，我们认为简化 ISA 规范中必需的部分非常重要。其他架构通常将其 ISA 视为单一实体，随着时间推移添加指令后会变更到新版本，而 RISC-V 将努力保持基本 ISA 和每个标准扩展随时间不变，并将新指令作为进一步的可选扩展分层。例如，基本整数 ISA 将继续作为完全支持的独立 ISA，无论后续有任何扩展。

## 1.4. 内存

一个 RISC-V hart 对于所有内存访问拥有一个单一的字节可寻址的地址空间，大小为 2 的 XLEN 次方字节。一个内存*字*（word）定义为 32 位（4 字节）。相应的，一个*半字*（halfword）为 16 位（2 字节），一个*双字*（doubleword）为 64 位（8 字节），一个*四字*（quadword）为 128 位（16 字节）。内存地址空间是循环的，因此地址 2 的 XLEN 次方减 1 处的字节与地址零处的字节相邻。因此，硬件进行的内存地址计算忽略溢出，而是以 2 的 XLEN 次方为模环绕。

执行环境确定硬件资源到 hart 地址空间的映射。一个 hart 地址空间的不同地址范围可以（1）包含*主内存*，或（2）包含一个或多个*I/O 设备*。对 I/O 设备的读写可能有可见的副作用，但对主内存的访问不可以。空置的地址范围不是一个单独的类别，但可以表示为不可访问的主内存或 I/O 区域。虽然执行环境可以将 hart 地址空间中的所有内容都称为 I/O 设备，但通常期望某些部分将被指定为主内存。

当一个 RISC-V 平台有多个 hart 时，任何两个 hart 的地址空间可以完全相同，或完全不同，或部分不同但共享某些资源子集（映射到相同或不同的地址范围）。

**评论：** *对于纯粹的"裸机"环境，所有 hart 可能看到相同的地址空间，完全通过物理地址访问。然而，当执行环境包括一个采用地址翻译的操作系统时，通常每个 hart 都会被赋予一个大部分或完全属于自己的虚拟地址空间。*

执行每条 RISC-V 机器指令需要一次或多次内存访问，细分为*隐式*和*显式*访问。对于执行的每条指令，进行一次*隐式*内存读取（指令取指）以获取要执行的编码指令。许多 RISC-V 指令在指令取指之外不执行进一步的内存访问。特定的加载和存储指令在由指令确定的地址执行*显式*的内存读或写。执行环境可能规定指令执行执行其他*隐式*内存访问（例如实现地址翻译），超出非特权 ISA 所记载的范围。

执行环境确定对于每种内存访问类型，地址空间的哪些部分是可访问的。例如，可以隐式读取用于指令取指的位置集合可能与可以通过加载指令显式读取的位置集合有任何重叠，也可能没有；而可以通过存储指令显式写入的位置集合可能只是可以读取的位置的子集。通常情况下，如果一条指令尝试访问一个不可访问的地址，会为该指令引发异常。

除非另有规定，不会引发异常且没有副作用的隐式读取可以任意早期和推测性地发生，甚至在机器可能证明该读取是需要的之前。例如，一个有效的实现可以在最早的时机尝试读取所有主内存，尽可能多地缓存可供后续指令取指的可获取（可执行）字节，并再也不为主内存的指令取指读取主内存。为确保某些隐式读取仅在对相同内存位置的写入之后才排序，软件必须执行为此目的定义的具体 fence 或缓存控制指令（例如 第 5 章 中定义的 FENCE.I 指令）。

一个 hart 进行的内存访问（隐式或显式）在其他 hart 或任何可以访问相同内存的其他代理看来可能以不同的顺序发生。然而，这种感知到的内存访问重排序总是受适用的内存一致性模型约束。RISC-V 的默认内存一致性模型是 RISC-V 弱内存排序（RVWMO），在 第 18 章 及附录中定义。可选地，一个实现可以采用更强的全存储排序模型，如 第 19 章 所定义。执行环境还可以添加进一步限制内存访问感知重排序的约束。由于 RVWMO 模型是任何 RISC-V 实现允许的最弱模型，为此模型编写的软件与所有 RISC-V 实现的实际内存一致性规则兼容。与隐式读取一样，软件必须执行 fence 或缓存控制指令，以确保特定的内存访问排序超出假设的内存一致性模型和执行环境的要求。

## 1.5. 基本指令长度编码

基本 RISC-V ISA 具有固定长度的 32 位指令，必须在 32 位边界上自然对齐。然而，标准的 RISC-V 编码方案旨在支持具有变长指令的 ISA 扩展，其中每条指令可以是任意数量的 16 位指令*片段*（parcels）长度，并且片段在 16 位边界上自然对齐。第 28 章 中描述的标准压缩 ISA 扩展通过提供压缩的 16 位指令来减少代码大小，并放宽对齐约束以允许所有指令（16 位和 32 位）在任何 16 位边界上对齐，以提高代码密度。

我们使用术语 IALIGN（以位为单位）来指代实现强制执行的指令地址对齐约束。IALIGN 在基本 ISA 中为 32 位，但一些 ISA 扩展（包括压缩 ISA 扩展）将 IALIGN 放宽到 16 位。IALIGN 不能取 16 或 32 以外的任何值。

我们使用术语 ILEN（以位为单位）来指代实现支持的最大指令长度，它始终是 IALIGN 的倍数。对于仅支持基本指令集的实现，ILEN 为 32 位。支持更长指令的实现具有更大的 ILEN 值。

基本 ISA 中的所有 32 位指令的最低两位设置为 `11`。可选的压缩 16 位指令集扩展的最低两位等于 `00`、`01` 或 `10`。

**评论：** *鉴于压缩格式的代码大小和能量节省，我们希望将对压缩格式的支持内置到 ISA 编码方案中，而不是事后添加，但为了允许更简单的实现，我们不想使压缩格式成为强制性的。我们还希望可选地允许更长的指令以支持实验和更大的指令集扩展。尽管我们的编码约定要求对核心 RISC-V ISA 进行更严格的编码，但这有几个有益的效果。*

**评论：** *标准 IMAFD ISA 的实现只需要在指令缓存中保存最高的 30 位（节省 6.25%）。在指令缓存重填充时，遇到任何低位清零的指令应在存储到缓存之前重新编码为非法 30 位指令，以保持非法指令异常行为。*

**评论：** *可能更重要的是，通过将我们的基本 ISA 压缩到 32 位指令字的一个子集中，我们为非标准和定制扩展留下了更多可用空间。特别是，基本 RV32I ISA 使用了 32 位指令字中不到八分之一的编码空间。一个不需要支持标准压缩指令扩展的实现可以将 3 个额外的非兼容 30 位指令空间映射到 32 位固定宽度格式中，同时保留对标准 ≥32 位指令集扩展的支持。*

位 [15:0] 全部为零的编码被定义为非法指令。这些指令被认为具有最小长度：如果存在任何 16 位指令集扩展则为 16 位，否则为 32 位。位 [ILEN-1:0] 全部为 1 的编码也是非法的；此指令被认为长度为 ILEN 位。

**评论：** *我们认为包含全零位的任何长度的指令都不合法这一特性是有益的，因为这会快速自陷到零填充内存区域的错误跳转。类似地，我们也保留包含全 1 的指令编码为非法指令，以捕捉在未编程的非易失性存储器设备、断开连接的内存总线或损坏的内存设备中观察到的另一种常见模式。*

**评论：** *软件可以依赖一个自然对齐的包含零的 32 位字在所有 RISC-V 实现上作为非法指令，供明确需要非法指令的软件使用。由于变长编码，为全 1 定义一个相应的已知非法值更加困难。软件通常不能使用 ILEN 位的全 1 非法值，因为软件可能不知道最终目标机器的 ILEN（例如，如果软件编译为标准二进制库，被许多不同的机器使用）。也曾考虑将 32 位全 1 的字定义为非法，因为所有机器必须支持 32 位指令大小，但这要求 ILEN > 32 的机器上的指令取指单元在此类指令跨越保护边界时报告非法指令异常而非访问故障异常，这使变长指令取指和解码复杂化。*

RISC-V 基本 ISA 具有小端或大端内存系统，特权架构进一步定义了双端操作。指令在内存中作为 16 位小端片段的序列存储，无论内存系统的端序如何。组成一条指令的片段按递增的半字地址存储，最低地址的片段保存指令规范中最低编号的位。

**评论：** *我们最初为 RISC-V 内存系统选择小端字节序，因为小端系统目前在商业上占主导地位（所有 x86 系统；iOS、Android 和 Windows for ARM）。一个次要的观点是，我们还发现小端内存系统对硬件设计者来说更自然。然而，某些应用领域（如 IP 网络）在大端数据结构上运行，某些遗留代码库是基于大端处理器构建的，因此我们定义了大端和双端的 RISC-V 变体。*

**评论：** *我们必须固定指令片段在内存中存储的顺序，独立于内存系统端序，以确保长度编码位始终按半字地址顺序首先出现。这允许指令取指单元仅通过检查第一个 16 位指令片段的前几位来快速确定变长指令的长度。*

**评论：** *我们进一步将指令片段本身设为小端，以将指令编码与内存系统端序完全解耦。这种设计既有利于软件工具，也有利于双端硬件。否则，例如，RISC-V 汇编器或反汇编器总是需要知道所意图的活动端序，尽管在双端系统中，端序模式可能在执行期间动态改变。相反，通过给指令固定的端序，精心编写的软件有时即使在二进制形式中也可以端序无关，很像位置无关代码。*

**评论：** *选择指令仅为小端确实会产生后果，然而，对于编码或解码机器指令的 RISC-V 软件。例如，大端 JIT 编译器在存储到指令内存时必须交换字节顺序。*

**评论：** *一旦我们决定固定小端指令编码，这自然导致将长度编码位放在指令格式的 LSB 位置，以避免拆分操作码字段。*

## 1.6. 异常、自陷和中断

我们使用术语*异常*（exception）来指代在当前 RISC-V hart 中与指令相关的运行时发生的异常状况。我们使用术语*中断*（interrupt）来指代可能导致 RISC-V hart 经历意外控制转移的外部异步事件。我们使用术语*自陷*（trap）来指代由异常或中断引起的到自陷处理程序的控制转移。

后续章节中的指令描述描述了在执行过程中可能引发异常的条件。大多数 RISC-V EEI 的一般行为是，当在某条指令上发出异常信号时，会发生到某个处理程序的自陷（除了浮点异常，在标准浮点扩展中，浮点异常不会导致自陷）。中断的生成、路由到以及由 hart 使能的方式取决于 EEI。

**评论：** *我们对"异常"和"自陷"的使用与 IEEE-754 浮点标准中的用法兼容。*

如何将自陷处理并使其对 hart 上运行的软件可见，取决于外围的执行环境。从执行环境内部运行的软件的角度来看，hart 在运行时遇到的自陷可以有四种不同的效果：

### 包含型自陷（Contained Trap）

自陷对执行环境内部运行的软件可见并由其处理。例如，在一个在 hart 上同时提供超级用户和用户模式的 EEI 中，用户模式 hart 的 ECALL 通常会导致到在同一 hart 上运行的超级用户模式处理程序的控制转移。类似地，在同一环境中，当 hart 被中断时，将在该 hart 上以超级用户模式运行中断处理程序。

### 请求型自陷（Requested Trap）

自陷是一种同步异常，它是执行环境的显式调用，代表执行环境内部的软件请求一个操作。一个例子是系统调用。在这种情况下，执行环境采取所请求的操作后，hart 上可能恢复执行，也可能不恢复。例如，系统调用可以移除 hart 或导致整个执行环境的有序终止。

### 不可见自陷（Invisible Trap）

自陷由执行环境透明地处理，在自陷处理后正常恢复执行。示例包括仿真缺失的指令、处理按需调页虚拟内存系统中的非驻留页故障，或在多程序机器中为不同的作业处理设备中断。在这些情况下，执行环境内部运行的软件不知道发生了自陷（我们在这些定义中忽略时序影响）。

### 致命型自陷（Fatal Trap）

自陷表示致命故障，并导致执行环境终止执行。示例包括虚拟内存页保护检查失败，或允许看门狗定时器到期。每个 EEI 应定义如何终止执行并向外部环境报告。

表 1 显示了每种自陷的特征。

*表 1. 自陷的特征*

||包含型|请求型|不可见|致命型|
|---|---|---|---|---|
|执行终止|否|否（注1）|否|是|
|软件无感知|否|否|是|是（注2）|
|由环境处理|否|是|是|是|

- 注1：可能请求终止
- 注2：不精确的致命自陷可能被软件观察到

EEI 为每个自陷定义它是否被精确处理，尽管建议在可能的情况下保持精确性。包含型和请求型自陷可以被执行环境内部的软件观察到不精确。根据定义，不可见自陷不能被执行环境内部运行的软件观察到精确或不精确。如果已知错误的指令不会导致立即终止，致命型自陷可以被执行环境内部运行的软件观察到不精确。

由于本文档描述非特权指令，很少提到自陷。处理包含型自陷的架构手段在特权架构手册中定义，以及支持更丰富 EEI 的其他特性。仅为引起请求型自陷而定义的非特权指令在此记录。由于其性质，不可见自陷超出了本文档的范围。未在此定义且未通过其他方式定义的指令编码可能导致致命自陷。

## 1.7. UNSPECIFIED 行为与值

该架构充分描述了实现必须做什么以及它们可能做什么的任何约束。在架构有意不约束实现的情况下，明确使用术语 UNSPECIFIED。

术语 UNSPECIFIED 指一个行为或值被有意不加约束。这些行为或值的定义对扩展、平台标准或实现开放。扩展、平台标准或实现文档可以提供规范性内容，以进一步约束基本架构定义为 UNSPECIFIED 的情况。

与基本架构一样，扩展应充分描述允许的行为和值，并使用术语 UNSPECIFIED 来表示有意不加约束的情况。这些情况可能被其他扩展、平台标准或实现所约束或定义。
