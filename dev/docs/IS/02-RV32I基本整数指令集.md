**评论：** *RV32I 被设计为足以为编译器目标提供基础，并支持现代操作系统环境。该 ISA 也被设计为减少最小实现所需的硬件。RV32I 包含 40 条唯一指令，尽管一个简单的实现可能将 ECALL/EBREAK 指令用一个始终自陷的单个 SYSTEM 硬件指令覆盖，并可能将 FENCE 指令实现为 NOP，从而将基本指令数减少到总共 38 条。RV32I 几乎可以仿真任何其他的 ISA 扩展（除了需要额外硬件支持原子性的 A 扩展）。*

**评论：** *在实践中，包含机器模式特权架构的硬件实现还需要 6 条 CSR 指令。*

**评论：** *基本整数 ISA 的子集可能对教学目的有用，但基本 ISA 的定义方式使得除了省略对未对齐内存访问的支持和将所有 SYSTEM 指令视为单个自陷外，几乎没有动机去子集化真正的硬件实现。*

**评论：** *标准 RISC-V 汇编语言语法在《汇编程序员手册》中记录。*

**评论：** *RV32I 的大部分评论也适用于 RV64I 基本 ISA。*

## 2.1. 基本整数 ISA 程序员模型

**评论：** *在基本整数 ISA 中没有专用的栈指针或子程序返回地址链接寄存器；指令编码允许任何 `x` 寄存器用于这些目的。然而，标准软件调用约定使用寄存器 `x1` 保存调用的返回地址，寄存器 `x5` 可作为备选链接寄存器。标准调用约定使用寄存器 `x2` 作为栈指针。*

**评论：** *硬件可以选择加速使用 `x1` 或 `x5` 的函数调用和返回。参见 JAL 和 JALR 指令的描述。*

**评论：** *可选的压缩 16 位指令格式是在假设 `x1` 是返回地址寄存器和 `x2` 是栈指针的前提下设计的。使用其他约定的软件将正确运行，但可能具有更大的代码尺寸。*

**评论：** *可用架构寄存器的数量会对代码大小、性能和能耗产生很大影响。虽然 16 个寄存器对于运行编译代码的整数 ISA 来说可能勉强足够，但无法在 16 位指令中使用三地址格式编码一个具有 16 个寄存器的完整 ISA。虽然两地址格式是可能的，但它会增加指令计数并降低效率。我们希望避免中间指令大小（如 Xtensa 的 24 位指令）以简化基本硬件实现，而一旦采用 32 位指令大小，支持 32 个整数寄存器就很容易了。更多的整数寄存器数量也有助于提高高性能代码上的性能，那里可能有循环展开、软件流水线化和缓存平铺的广泛使用。*

**评论：** *基于这些原因，我们为 RV32I 选择了传统的 32 个整数寄存器大小。动态寄存器使用往往由几个频繁访问的寄存器主导，寄存器文件实现可以被优化以减少频繁访问寄存器的访问能量 (Tseng & Asanović, 2000)。可选的压缩 16 位指令格式主要只访问 8 个寄存器，因此可以提供密集的指令编码，而额外的指令集扩展可以支持更大的寄存器空间（扁平的或层次的），如果需要的话。*

**评论：** *对于资源受限的嵌入式应用，我们定义了 RV32E 子集，仅有 16 个寄存器（第 3 章）。*

## 2.2. 基本指令格式

在基本 RV32I ISA 中，有四种核心指令格式（R/I/S/U），如基本指令格式所示。所有指令固定为 32 位长度。基本 ISA 具有 `IALIGN=32`，意味着指令必须在内存中对齐于四字节边界。对于已采纳的分支或无条件跳转，如果目标地址不是 `IALIGN-bit` 对齐的，则生成指令地址未对齐异常。此异常在分支或跳转指令上报告，而不是在目标指令上。对于未采纳的条件分支，不生成指令地址未对齐异常。

**评论：** *当添加具有 16 位长度或 16 位长度的其他奇倍数的指令扩展时（即 IALIGN=16），基本 ISA 指令的对齐约束放宽到两字节边界。*

**评论：** *指令地址未对齐异常在会导致指令未对齐的分支或跳转上报告，以帮助调试，并简化 IALIGN=32 系统的硬件设计，其中这些是唯一可能发生未对齐的地方。*

解码保留指令的行为是 UNSPECIFIED。

**评论：** *某些平台可能要求保留供标准使用的操作码引发非法指令异常。其他平台可能允许保留的操作码空间用于非兼容扩展。*

RISC-V ISA 在所有格式中将源寄存器（*rs1* 和 *rs2*）和目标寄存器（*rd*）保持在同一位置以简化解码。除了 CSR 指令中使用的 5 位立即数（第 6 章）外，立即数始终是符号扩展的，并且通常被打包在指令中最左侧的可用位中，并被分配以减少硬件复杂性。特别是，所有立即数的符号位始终在指令的第 31 位，以加速符号扩展电路。

RISC-V 基本指令格式。每个立即数子域标记了正在生成的立即数值中的位位置（imm[x]），而不是像通常所做的那样标记指令立即数域内的位位置。

**评论：** *解码寄存器说明符通常是实现中的关键路径，因此指令格式被选择为在牺牲跨格式移动立即数位的情况下将所有寄存器说明符在所有格式中保持在同一位置（这是与 RISC-IV aka. SPUR (Lee et al., 1989) 共享的属性）。*

**评论：** *在实践中，大多数立即数要么很小，要么需要所有 XLEN 位。我们选择了一个不对称的立即数分割（常规指令中 12 位加上一个特殊的加载高位立即数指令 20 位）以增加常规指令可用的操作码空间。*

**评论：** *立即数是符号扩展的，因为我们没有观察到像 MIPS ISA 那样对某些立即数使用零扩展的好处，并希望保持 ISA 尽可能简单。*

**评论：** *符号扩展是立即数上最关键的运算之一（特别是对于 XLEN>32），在 RISC-V 中，所有立即数的符号位始终保存在指令的第 31 位，以允许符号扩展与指令解码并行进行。*

**评论：** *虽然更复杂的实现可能有独立的分支和跳转加法器，因此不会从保持立即数位在不同指令类型间位置不变中受益，但我们希望降低最简单实现的硬件成本。通过在 B 和 J 立即数的指令编码中旋转位，而不是使用动态硬件多路复用器将立即数乘以 2，我们将指令信号扇出和立即数多路复用器成本降低了大约 2 倍。打乱的立即数编码将为静态或提前编译增加可忽略的时间。对于指令的动态生成，有一些小的额外开销，但最常见的短前向分支具有直观的立即数编码。*

## 2.4. 整数计算指令

大多数整数计算指令对整数寄存器文件中保存的 `XLEN` 位的值进行操作。整数计算指令要么使用 I-type 格式编码为寄存器-立即数操作，要么使用 R-type 格式编码为寄存器-寄存器操作。对于寄存器-立即数和寄存器-寄存器指令，目标均为寄存器 *rd*。没有任何整数计算指令会导致算术异常。

**评论：** *我们没有在基本指令集中为整数算术运算的溢出检查包含特殊的指令集支持，因为许多溢出检查可以使用 RISC-V 分支以低成本实现。无符号加法的溢出检查仅需要在加法后增加一条额外的分支指令：`add t0, t1, t2; bltu t0, t1, overflow`。*

**评论：** *对于带符号加法，如果一个操作数的符号已知，溢出检查仅需要在加法后增加一条分支：`addi t0, t1, +imm; blt t0, t1, overflow`。这涵盖了带立即数操作数的常见加法情况。*

**评论：** *对于一般的带符号加法，需要在加法后增加三条额外的指令，利用这样一个观察：和应小于其中一个操作数当且仅当另一个操作数为负数时。*

```
         add t0, t1, t2
         slti t3, t2, 0
         slt t4, t0, t1
```

```
         bne t3, t4, overflow
```

**评论：** *在 RV64I 中，32 位带符号加法的检查可以通过比较操作数上 ADD 和 ADDW 的结果进一步优化。*

**评论：** *可以通过将 U-立即数设置为 0 来获取当前 PC。虽然 JAL +4 指令也可以用于获取局部 PC（JAL 之后的指令的 PC），但它可能在更简单的微架构中导致流水线中断，或在更复杂的微架构中污染 BTB 结构。*

## 2.5. 控制转移指令

RV32I 提供两种类型的控制转移指令：无条件跳转和条件分支。RV32I 中的控制转移指令*没有*架构可见的延迟槽。

如果跳转或已采纳分支的目标上发生指令访问故障或指令页故障异常，该异常在目标指令上报告，而不是在跳转或分支指令上。

## 2.5.1. 无条件跳转

跳转并链接（JAL）指令使用 J-type 格式，其中 J-立即数编码以 2 字节为倍数的带符号偏移量。该偏移量被符号扩展并加到跳转指令的地址上以形成跳转目标地址。因此跳转可以瞄准 ±1 MiB 的范围。JAL 将跳转之后指令的地址（'pc'+4）存储到寄存器 *rd* 中。标准软件调用约定使用 'x1' 作为返回地址寄存器，'x5' 作为备选链接寄存器。

**评论：** *备选链接寄存器支持调用毫码例程（例如，在压缩代码中用于保存和恢复寄存器），同时保留常规返回地址寄存器。寄存器 `x5` 被选为备选链接寄存器，因为它映射到标准调用约定中的临时寄存器，且编码仅与常规链接寄存器有一个位不同。*

普通无条件跳转（汇编伪指令 J）编码为 *rd* = `x0` 的 JAL。

**评论：** *注意 JALR 指令不将 12 位立即数视为 2 字节的倍数，这与条件分支指令不同。这在硬件中避免了一种更多的立即数格式。在实践中，JALR 的大多数使用将具有零立即数或与 LUI 或 AUIPC 配对，因此范围的轻微减小并不显著。*

**评论：** *在计算 JALR 目标地址时清除最低有效位既稍微简化了硬件，也允许使用函数指针的低位存储辅助信息。尽管在这种情况下可能略微损失错误检查，但在实践中，跳转到错误指令地址通常会很快引发异常。*

分支指令比较两个寄存器。BEQ 和 BNE 分别在寄存器 *rs1* 和 *rs2* 相等或不相等时采用分支。BLT 和 BLTU 在 *rs1* 小于 *rs2* 时采用分支，分别使用带符号和无符号比较。BGE 和 BGEU 在 *rs1* 大于或等于 *rs2* 时采用分支，分别使用带符号和无符号比较。注意，BGT、BGTU、BLE 和 BLEU 可以通过颠倒到 BLT、BLTU、BGE 和 BGEU 的操作数来合成。

**评论：** *带符号数组边界可以用单条 BLTU 指令检查，因为任何负的索引将比任何非负的边界更大。*

软件应被优化，使得顺序代码路径是最常见的路径，不太常见的被采纳代码路径放在行外。软件还应假设后向分支将被预测为采纳，前向分支预测为不采纳，至少在它们首次遇到时。动态预测器应快速学习任何可预测的分支行为。

与其他一些架构不同，RISC-V 跳转（*rd* = `x0` 的 JAL）指令应始终用于无条件分支，而不是带有始终为真条件的分支指令。RISC-V 跳转也是 PC 相对的，并支持比分支持大得多的偏移量范围，且不会污染条件分支预测表。

**评论：** *条件分支被设计为包含两个寄存器之间的算术比较操作（如 PA-RISC、Xtensa 和 MIPS R6 中所做的），而不是使用条件码（x86、ARM、SPARC、PowerPC），或仅将一个寄存器与零比较（Alpha、MIPS），或仅比较两个寄存器是否相等（MIPS）。这种设计的动机源于观察到合并的比较与分支指令适合常规流水线，避免了额外的条件码状态或使用临时寄存器，并减少了静态代码大小和动态指令获取流量。另一点是，与零的比较需要非平凡的电路延迟（特别是在先进工艺转向静态逻辑后），因此几乎与算术幅度比较一样昂贵。融合比较与分支指令的另一个优势是分支在流水线前端更早被观察到，因此可以更早被预测。对于可以基于相同条件码采用多个分支的条件码设计，可能有一个优势，但我们认为这种情况相对罕见。*

**评论：** *我们考虑但未在指令编码中包含静态分支提示。这些可以减少动态预测器的压力，但需要更多的指令编码空间和软件剖析来获得最佳结果，并且如果生产运行与剖析运行不匹配可能导致性能不佳。*

**评论：** *我们考虑但未包含条件移动或谓词指令，它们可以有效地替代不可预测的短前向分支。条件移动是两者中更简单的，但难以与可能导致异常的代码（内存访问和浮点操作）一起使用。谓词化向系统添加额外的标志状态、设置和清除标志的额外指令，以及每条指令上的额外编码开销。条件移动和谓词指令都为乱序微架构增加了复杂性，因为如果谓词为假，需要将目标架构寄存器的原始值复制到重命名的目标物理寄存器，从而增加了隐式的第三个源操作数。此外，使用谓词化而不是分支的静态编译时决策可能导致在编译器训练集中不包含的输入上性能更低，特别是考虑到不可预测的分支很少见，并随着分支预测技术的改进而变得越来越罕见。*

**评论：** *我们注意到存在各种微架构技术来动态地将不可预测的短前向分支转换为内部谓词化的代码，以避免在分支预测错误时刷新流水线的成本 (Heil & Smith, 1996), (Klauser et al., 1998), (Kim et al., 2005)，并且已在商用处理器中实现 (Sinharoy et al., 2011)。最简单的技术仅通过刷新分支阴影中的指令（而不是整个取指流水线），或通过使用宽指令取指或空闲指令取指槽从两侧取指来减少从误预测短前向分支恢复的代价。更复杂的技术（用于乱序核心）在分支阴影中的指令上添加内部谓词，内部谓词值由分支指令写入，允许分支和后续指令相对于其他代码被推测性地和乱序地执行。*

## 2.6. 加载和存储指令

RV32I 是加载-存储架构，其中只有加载和存储指令访问内存，算术指令仅在 CPU 寄存器上操作。RV32I 提供 32 位、字节寻址的地址空间。EEI 将定义地址空间的哪些部分可以用哪些指令合法访问（例如，某些地址可能只读，或仅支持字访问）。目标为 `x0` 的加载指令即使加载值被丢弃，也必须仍引发任何异常并导致任何其他副作用。

EEI 将定义内存系统是小端还是大端。在 RISC-V 中，端序是字节地址不变的。

**评论：** *在一个端序为字节地址不变的系统中，以下属性成立：如果在某个端序下将某个字节以某个地址存储到内存，那么以任何端序从该地址进行字节大小的加载将返回存储的值。*

**评论：** *在小端配置中，多字节存储将最低有效寄存器字节写入最低的内存字节地址，然后按字节有效位递增的顺序写入其他寄存器字节。加载类似地将较低内存字节地址的内容传输到较低有效位的寄存器字节。*

**评论：** *在大端配置中，多字节存储将最高有效寄存器字节写入最低的内存字节地址，然后按字节有效位递减的顺序写入其他寄存器字节。加载类似地将较高内存字节地址的内容传输到较低有效位的寄存器字节。*

加载和存储指令在寄存器和内存之间传输值。加载用 I-type 格式编码，存储用 S-type 格式。有效地址通过将寄存器 *rs1* 与符号扩展的 12 位偏移量相加获得。加载将值从内存复制到寄存器 *rd*。存储将寄存器 *rs2* 中的值复制到内存。

LW 指令从内存加载 32 位值到 *rd*。LH 从内存加载 16 位值，然后在存储到 *rd* 之前符号扩展到 32 位。LHU 从内存加载 16 位值，但然后在存储到 *rd* 之前零扩展到 32 位。LB 和 LBU 类似地定义了 8 位值。SW、SH 和 SB 指令分别将 32 位、16 位和 8 位值从寄存器 *rs2* 的低位存储到内存。

无论 EEI 如何，有效地址自然对齐的加载和存储不应引发地址未对齐异常。有效地址未自然对齐于所引用数据类型（即有效地址不能被访问的字节大小整除）的加载和存储的行为取决于 EEI。

一个 EEI 可以保证未对齐的加载和存储被完全支持，因此执行环境内部运行的软件永远不会遇到包含型或致命型地址未对齐自陷。在这种情况下，未对齐的加载和存储可以在硬件中处理，或通过不可见的自陷进入执行环境实现来处理，或者根据地址可能是硬件和不可见自陷的组合。

一个 EEI 可能不保证未对齐的加载和存储被不可见地处理。在这种情况下，未自然对齐的加载和存储可能要么成功完成执行，要么引发异常。引发的异常可以是地址未对齐异常或访问故障异常。对于除了未对齐外本来能够完成的内存访问，如果未对齐的访问不应被仿真（例如，如果对该内存区域的访问有副作用），可以引发访问故障异常而不是地址未对齐异常。当 EEI 不保证未对齐的加载和存储被不可见地处理时，EEI 必须定义由地址未对齐导致的异常是导致包含型自陷（允许执行环境内部运行的软件处理自陷）还是致命型自陷（终止执行）。

**评论：** *未对齐的访问在移植遗留代码时偶尔需要，并在使用任何形式的打包 SIMD 扩展或处理外部打包数据结构时有助于应用性能。我们允许 EEI 选择通过常规加载和存储指令支持未对齐访问的理由是简化添加未对齐硬件支持。一种选择本可以是在基本 ISA 中不允许未对齐访问，然后为未对齐访问提供一些单独的 ISA 支持，要么是帮助软件处理未对齐访问的特殊指令，要么是用于未对齐访问的新硬件寻址模式。特殊指令难以使用，使 ISA 复杂化，并通常添加新的处理器状态（例如，SPARC VIS 对齐地址偏移量寄存器）或使访问现有处理器状态复杂化（例如，MIPS LWL/LWR 部分寄存器写入）。此外，对于面向循环的打包 SIMD 代码，操作数未对齐时的额外开销促使软件提供取决于操作数对齐的多种循环形式，这使代码生成复杂化并增加了循环启动开销。新的未对齐硬件寻址模式占用指令编码中相当大的空间，或需要非常简化的寻址模式（例如，仅寄存器间接）。*

即使未对齐的加载和存储成功完成，这些访问也可能根据实现而运行得非常慢（例如，当通过不可见自陷实现时）。此外，虽然自然对齐的加载和存储保证原子地执行，未对齐的加载和存储可能不保证，因此需要额外的同步来确保原子性。

**评论：** *我们不强制要求未对齐访问的原子性，以便执行环境实现可以使用不可见的机器自陷和软件处理程序来处理某些或所有未对齐访问。如果提供了硬件未对齐支持，软件可以通过简单地使用常规加载和存储指令来利用这一点。然后硬件可以根据运行时地址是否对齐自动优化访问。*

## 2.7. 内存排序指令

**==> picture [500 x 54] intentionally omitted <==**

FENCE 指令用于对其他 RISC-V hart 和外部设备或协处理器所看到的设备 I/O 和内存访问进行排序。设备输入（I）、设备输出（O）、内存读取（R）和内存写入（W）的任何组合可以相对于同样的任何组合进行排序。通俗地说，在 FENCE 之前的*前驱*集合中的任何操作之后，没有其他 RISC-V hart 或外部设备可以观察到 FENCE 之后的*后继*集合中的任何操作。第 18 章 提供了 RISC-V 内存一致性模型的精确描述。

FENCE 指令还对 hart 进行的内存读写与外部设备进行的内存读写所观察到的情况进行排序。然而，FENCE 指令不对外部设备使用任何其他信号机制观察到的事件进行排序。

**评论：** *一个设备可能通过某种外部通信机制观察到对某个内存位置的访问，例如一个内存映射的控制寄存器，它驱动中断信号到中断控制器。这种通信超出了 FENCE 排序机制的范围，因此 FENCE 指令无法保证中断信号的变化何时对中断控制器可见。特定设备可能提供额外的排序保证以减少软件开销，但这些超出了 RISC-V 内存模型的范围。*

EEI 将定义哪些 I/O 操作是可能的，特别是哪些内存地址在通过加载和存储指令访问时将被分别视为设备输入和设备输出操作（而不是内存读写）。例如，内存映射的 I/O 设备通常将通过使用 I 和 O 位排序的非缓存加载和存储来访问，而不是使用 R 和 W 位。指令集扩展也可能描述新的 I/O 指令，这些指令也将使用 FENCE 指令中的 I 和 O 位进行排序。

FENCE 模式域 *fm* 定义了 FENCE 指令的语义。`FENCE`（*fm* = `0000`）将其前驱集合中的所有内存操作排序在其后继集合中的所有内存操作之前。

`FENCE.TSO` 指令编码为 *fm* = `1000`、*predecessor* = `RW`、*successor* = `RW` 的 FENCE 指令。`FENCE.TSO` 将其前驱集合中的所有加载操作排序在其后继集合中的所有内存操作之前，并将其前驱集合中的所有存储操作排序在其后继集合中的所有存储操作之前。这使得 `FENCE.TSO` 前驱集合中的 `非-AMO` 存储操作与其后继集合中的 `非-AMO` 加载操作之间无序。

**评论：** *因为 `FENCE RW,RW` 施加了 `FENCE.TSO` 所施加排序的超集，所以忽略 fm 域并将 `FENCE.TSO` 实现为 `FENCE RW,RW` 是正确的。*

FENCE 指令中未使用的域——*rs1* 和 *rd*——保留用于未来扩展中的更细粒度 fence。为前向兼容，基本实现应忽略这些域，标准软件应将这些域设为零。同样，许多 *fm* 和前驱/后继集合设置也保留供未来使用。基本实现应将所有此类保留配置视为 `FENCE` 指令（*fm* = `0000`），标准软件应仅使用非保留配置。

**评论：** *我们选择了一个宽松的内存模型，以允许从简单的机器实现和可能的未来协处理器或加速器扩展中获得高性能。我们将 I/O 排序与内存 R/W 排序分开，以避免在设备驱动 hart 内的不必要串行化，并支持控制添加的协处理器或 I/O 设备的替代非内存路径。简单实现可以额外忽略前驱和后继域，并始终在所有操作上执行保守的 FENCE。*

## 2.9. HINT 指令

RV32I 为 HINT 指令保留了大量编码空间，HINT 指令通常用于向微架构传达性能提示。与 NOP 指令一样，HINT 不改变任何架构可见状态，除了推进 `pc` 和任何适用的性能计数器。实现始终被允许忽略编码的提示。

大多数 RV32I HINT 被编码为 *rd* = `x0` 的整数计算指令。其他 RV32I HINT 被编码为带有空前驱或后继集合且 *fm* = 0 的 FENCE 指令。

**评论：** *这些 HINT 编码被选择为使得简单实现可以完全忽略 HINT，而是将 HINT 作为恰好不改变架构状态的常规指令执行。例如，如果目标寄存器是 `x0`，ADD 就是一个 HINT；5 位的 rs1 和 rs2 域编码 HINT 的参数。然而，一个简单实现可以简单地将 HINT 作为对 rs1 和 rs2 执行 ADD 并写入 `x0`，这在架构上没有可见的效果。*

**评论：** *作为另一个例子，具有零 pred 域和零 fm 域的 FENCE 指令是一个 HINT；succ、rs1 和 rd 域编码 HINT 的参数。一个简单实现可以简单地将 HINT 作为 FENCE 执行，该 FENCE 将空集的前驱内存访问排序在 succ 域中编码的任何后续内存访问之前。由于前驱和后继集合的交集为空，该指令不施加任何内存排序，因此在架构上没有可见的效果。*

**评论：** *我们预期标准提示最终将包括内存系统空间和时间局部性提示、分支预测提示、线程调度提示、安全标签和用于仿真/仿真的仪器化标志。*
