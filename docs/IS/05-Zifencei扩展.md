# 第5章 "Zifencei" 指令-获取栅栏扩展，版本 2.0

本章定义了 "Zifencei" 扩展，该扩展包含 FENCE.I 指令，用于在同一硬件线程上的指令存储器写入与指令获取之间提供显式的同步。目前，该指令是确保一个硬件线程可见的存储器写入对其指令获取也可见的唯一标准机制。

_我们曾考虑但未纳入一条 "store instruction word" 指令，如 (Tremblay et al., 2000) 中所述。JIT 编译器可能在单条 FENCE.I 之前生成大量指令追踪，并通过将翻译后的指令写入已知不驻留在指令缓存中的内存区域来摊薄任何指令缓存侦听/无效化开销。_

_FENCE.I 指令的设计目标是支持多种多样的实现方式。一种简单的实现可以在执行 FENCE.I 时刷新本地指令缓存和指令流水线。更复杂的实现可能在每次数据缓存未命中时侦听指令缓存，或在每次指令缓存未命中时侦听数据缓存，或者使用包含式统一私有 L2 缓存在本地存储指令写入主指令缓存行时将其无效化。如果指令和数据缓存以这种方式保持一致性，或者内存系统仅由非缓存的 RAM 组成，则在 FENCE.I 处只需刷新指令流水线即可。_

_FENCE.I 指令原本是基础 I 指令集的一部分。虽然截至本文撰写时，它仍然是维护指令-获取一致性的唯一标准方法，但有两个主要问题推动将其从强制基础指令集中移出。_

_首先，人们已认识到在某些系统上，FENCE.I 的实现成本很高，内存模型任务组正在讨论替代机制。特别是对于具有非一致性指令缓存和非一致性数据缓存的设计，或者指令缓存重填不侦听一致性数据缓存的设计，在遇到 FENCE.I 指令时必须完全刷新两种缓存。当在统一缓存或外部内存系统之前存在多级 I 和 D 缓存时，此问题更为严重。_

_其次，在类 Unix 操作系统环境中，该指令的能力不足以在用户级别提供。FENCE.I 仅同步本地硬件线程，而操作系统可以在 FENCE.I 之后将用户硬件线程重调度到不同的物理硬件线程上。这将要求操作系统在每次上下文迁移时执行额外的 FENCE.I。为此，标准 Linux ABI 已从用户级移除了 FENCE.I，现在要求通过系统调用来维护指令-获取一致性，这使操作系统能够最小化当前系统上所需的 FENCE.I 执行次数，并为未来改进的指令-获取一致性机制提供向前兼容性。_

_正在讨论的未来指令-获取一致性方法包括提供更受限的 FENCE.I 版本（仅针对 rs1 中指定的地址），和/或允许软件使用依赖机器模式缓存维护操作的 ABI。_

FENCE.I 指令用于同步指令流和数据流。RISC-V 不保证对指令存储器的写入会对硬件线程的指令获取可见，直到该硬件线程执行一条 FENCE.I 指令为止。一条 FENCE.I 指令确保该 RISC-V 硬件线程上随后的指令获取将看到之前的、已对同一 RISC-V 硬件线程可见的任何数据写入。FENCE.I _不_ 确保在多处理器系统中其他 RISC-V 硬件线程的指令获取会观察到本地硬件线程的写入。若要使指令存储器的写入对所有 RISC-V 硬件线程可见，写入线程还必须执行一条数据 FENCE，然后请求所有远程 RISC-V 硬件线程执行 FENCE.I。

一条 FENCE.I 指令将按程序顺序位于该 FENCE.I 之前的所有显式内存访问排序在按程序顺序位于该 FENCE.I 之后的所有指令获取之前。

_例如，在以下 litmus 测试中，假设采用小端序 RV32IC 硬件线程，消费者硬件线程上的结果_ `a0` _=1，_ `a1` _=0 是被禁止的：_

```
Initially, flag = 0.
Producer hart:                                  Consumer hart:
la t0, patch_me                                 la t2, flag
li t1, 0x4585                                   lw a0, (t2)
sh t1, (t0)   # patch_me := c.li a1, 1          fence.i
fence w, w    # order flag write              patch_me:
la t0, flag                                     c.li a1, 0
li t1, 1
sw t1, (t0)   # flag := 1
```

_请注意，此示例仅用于说明上述排序属性。在实际的生产者-消费者代码生成方案中，消费者将在执行 FENCE.I 指令之前循环等待_ `flag` _变为 1。_

一条指令获取始终排序在该指令所产生的任何显式内存访问之前。

FENCE.I 指令中未使用的字段 _funct12_、_rs1_ 和 _rd_ 保留用于未来扩展中的更细粒度栅栏。为了向前兼容，基础实现应忽略这些字段，标准软件应将它们置零。

_由于 FENCE.I 仅将写入与硬件线程自身的指令获取进行排序，应用程序代码仅应在应用程序线程不会被迁移到不同硬件线程的前提下依赖 FENCE.I。EEI 可以提供用于高效的多处理器指令流同步机制。_
