## 第32章 密码学扩展：标量指令与熵源，版本 1.0.1

## 32.1. 引言

本文档描述了 RISC-V 的**标量**密码学扩展。此处描述的所有指令均使用通用 `X` 寄存器，并遵守 2读1写 的寄存器访问约束。这些指令设计轻量，适用于 `32` 位和 `64` 位基础架构；从嵌入式 IoT 级核心到未实现向量单元的大型应用级核心均可使用。

本文档还描述了熵源（Entropy Source）的架构接口，可用于生成密码学秘密。相关内容见第 32.4 节。

第 32.5 节还包含一种机制，允许核心实现者提供 **"常量时间执行"** 保证。

## 32.1.1. 目标受众

密码学是一个专业领域，需要不同背景的人员协作以实现安全高效的实现。在可能的情况下，我们已尽力使本规范对所有读者都能理解，但我们认识到，其中涉及的动机以及对算法和其他规范和标准的引用，对非领域专家来说可能较为陌生。

本规范预计会被不同背景的人员阅读和执行。我们试图在此描述这些背景，简要说明我们期望他们了解的内容以及与本规范的关系。我们希望这有助于人们理解规范的哪些方面与他们特别相关，哪些可以（安全地！）忽略或交给同事处理。

## 密码学家和密码学软件开发人员

这些是我们期望使用本规范中指令编写代码的人员。他们显然应该理解我们包含的指令的动机，并熟悉我们引用的大多数算法和外部标准。我们期望第 32.5 节（常量时间执行）和第 32.4 节（熵源）主要在其帮助下被理解。

## 计算机架构师

我们不期望架构师具有密码学背景。但我们期望架构师能够检查我们的指令是否存在实现问题，理解指令在上下文中如何使用，并就如何最佳地将密码学家的需求适配到 ISA 接口提出建议。

## 数字设计工程师和微架构师

这些是在核心内部实现规范的人员。同样，不假定具有密码学专业知识，但我们期望他们解读规范并预见到任何硬件实现问题，例如高频设计考虑因素或延迟/面积权衡等。特别地，他们应了解在硬件中高效实现 AES 和 SM4 SBox 的相关文献。

## 验证工程师

负责确保扩展在硬件中的正确实现。不假定具有密码学背景。我们期望他们从规范中识别出有趣的测试用例。理解其实际用途将有助于此。我们不期望此类验证工程师成为熵源设计或认证方面的专家，因为这是一个非常专业的领域。

但我们确实期望他们识别出围绕熵源接口的所有**架构级**测试用例。

这些绝非关注本规范的唯一人群，但他们是我们在编写时最着重考虑的人群。

## 32.1.2. Sail 规范

RISC-V 维护一个 ISA 规范的形式化模型，使用 Sail ISA 规范语言（ _SAIL ISA Specification Language_ ，未注明日期）实现。请注意，_Sail_ 指的是规范语言本身，而存在一个用 Sail 编写的 _RISC-V 模型_。称其为"the Sail model"是不正确的，这有歧义，因为存在许多不同 ISA 的 Sail 模型。我们将 RISC-V 的 Sail 实现称为"the RISC-V Sail model"。

密码学扩展使用来自实际模型的内联 Sail 代码片段来给出指令功能的规范描述。每条指令都附有其 Sail 表达式，并包含对辅助函数的调用，这些函数过于冗长，无法直接包含在规范中。此辅助代码列于第 32.9 节。建议阅读 Sail 手册以最佳理解代码片段。

请注意，本文档仅包含形式化模型的一个子集：完整模型请参阅形式化模型 GitHub 仓库。

## 32.1.3. 策略

在制定本提案时，我们试图遵循以下策略：

- 当需要在以下两者之间选择时：

   1. 支持某种算法的多种实现策略，或者

   2. 支持单一实现风格，其性能更高 / 成本更低；密码学扩展将选择更受限但性能更高的选项。这符合 RISC-V 规范其他部分的常见模式，其中为执行特定任务提供推荐（但非必需）的指令序列作为示例，使硬件和软件实现者都可以仅针对单一用例进行优化。

- 该扩展将被设计为良好支持**现存**的标准化密码学构造。它不会试图支持提议中的标准或仅存于学术界的密码学构造。与 RISC-V 密码学标准扩展同时或在其后确立的密码学标准，将由未来的 RISC-V 密码学标准扩展的添加或版本更新来处理。预计 NIST 轻量级密码学竞赛和 NIST 后量子密码学竞赛可能以此方式处理，具体取决于时间安排。

- 历史上曾有过一些讨论（Lee et al., 2004），关于通用计算中新支持的操作如何为密码学算法提供新的基础。本标准不会试图预测哪些新的有用的低级操作**可能**成为未来密码学构造的构建块。

- 关于侧信道对策：在相关情况下，提议的指令必须旨在消除任何时序侧信道的可能性。对于基于功耗或电磁（EM）测量值的侧信道，该扩展不会试图支持在 ISA 抽象层之上实现的对策。将在相关处给出关于微架构如何以抵抗功耗/EM 侧信道的方式实现指令的建议。

## 32.2. 扩展概述

标量密码学指令集扩展引入的扩展组列于此处。

各密码学扩展的检测使用统一的基于软件的 RISC-V 发现方法。

**评论：** _在撰写本文时，这些发现机制仍在开发中。_

_关于扩展的合理性说明_

**评论：** _专用的加密和解密指令被分离到不同的功能组，因为某些用例（例如 TLS 1.3 中的 Galois/Counter Mode）不需要解密功能。_

_NIST 和 ShangMi（商密）算法套件被分开，因为它们的用途严重依赖于设备预期运行的国家。NIST 密码是大多数标准化互联网协议的一部分，而 ShangMi 密码则需要在中国使用。_

## 描述

此指令根据 `bs` 从 `rs2` 中取出单个字节。对其应用 AES 逆 SBox 操作，并将结果与 `rs1` 进行异或。此指令必须**始终**以执行延迟不依赖于操作数据的方式实现。

## 操作

```
functionclause execute (AES32DSI (bs,rs2,rs1,rd)) = {
let shamt   : bits( 5) = bs @ 0b000; /* shamt = bs*8 */
let si      : bits( 8) = (X(rs2)[31..0] >> shamt)[7..0]; /* SBox Input */
let so      : bits(32) = 0x000000 @ aes_sbox_inv(si);
let result  : bits(32) = X(rs1)[31..0] ^ rol32(so, unsigned(shamt));
  X(rd) = EXTS(result); RETIRE_SUCCESS
}
```

## 32.4. 熵源

`seed` CSR 提供了一个符合 NIST SP 800-90B (Turan et al., 2018) 或 BSI AIS-31 (Killmann & Schindler, 2011) 的物理熵源（Entropy Source, ES）的接口。

熵源本身并不是密码学安全的随机位生成器（RBG），但可以在对称密码学的帮助下用于构建多种类型的标准（和非标准）RBG。预期用法是对熵源的输出进行调节（通常使用 SHA-2/3），并使用它来播种密码学安全的确定性随机位生成器（DRBG），例如基于 AES 的 `CTR_DRBG` (Barker & Kelsey, 2015)。熵源、调节和 DRBG 的组合可用于安全地创建随机位 (Barker et al., 2021)。关于认证和自认证程序、设计合理性的非规范性描述以及如何使用熵源输出的更详细建议，请参见第 32.7 节。

## 32.4.1. **`seed`** CSR

`seed` 是一个非特权 CSR，位于地址 `0x015`。`seed` 的 32 位内容如下：

|位|名称|描述|
|---|---|---|
|`31:30`|`OPST`|状态：`BIST`(00)、`WAIT`(01)、`ES16`(10)、`DEAD`(11)。|
|`29:24`|_保留_|供 RISC-V 规范未来使用。|
|`23:16`|_自定义_|指定用于自定义和实验用途。|
|`15: 0`|`entropy`|16 位随机性，仅在 `OPST=ES16` 时有效。|

尝试使用只读 CSR 访问指令（ `CSRRS` / `CSRRC` 且 _rs1_ = `x0` 或 `CSRRSI` / `CSRRCI` 且 _uimm_ =0）访问 `seed` CSR 会引发非法指令异常；任何其他 CSR 访问指令均可用于访问 `seed`。写入值（在 `rs1` 或 `uimm` 中）必须被实现忽略。写入的目的是信号轮询和刷新。

软件通常使用指令 `csrrw rd, seed, x0` 来读取 `seed` CSR。

`seed` CSR 还受到执行模式的访问控制，除非明确授予访问权限，否则在 M 模式外尝试读取或写入访问将引发非法指令异常。更多详情见第 32.4.3 节。

状态位 `seed[31:30]` = `OPST` 可以是 `ES16` (10)，表示轮询成功，或者是以下三种熵轮询失败状态之一：`BIST` (00)、`WAIT` (01) 或 `DEAD` (11)，将在下文讨论。

当 `OPST` = `ES16` ( `seed[31:30]` = `10` ) 时，每个返回的 `seed[15:0]` = `entropy` 值代表唯一的随机性，即使其数值与先前轮询的 `entropy` 值相同。`entropy` 位的实现要求在第 32.4.2 节中定义。当 `OPST` 不为 `ES16` 时，`entropy` 必须设置为 0。实现可以安全地将保留和自定义位设置为零。

出于安全原因，接口保证秘密 `entropy` 字不会被多次提供。因此，轮询（读取）还必须具有清除（读时擦除）`entropy` 内容并将状态更改为 `WAIT` 的副作用（除非有 `entropy` 立即可用于 `ES16`）。其他状态（ `BIST`、`WAIT` 和 `DEAD` ）可能不受轮询影响。

`seed[31:30]` = `OPST` 中返回的状态位：

- `00` - `BIST` 表示正在执行按需内置自检（BIST）测试。如果 `OPST` 从任何其他状态暂时返回到 `BIST`，这表示非致命的自检警报，除了记录外无需采取行动。此类 `BIST` 警报必须锁存，直到至少被轮询一次，以便软件记录其发生。

- `01` - `WAIT` 表示尚无可用的足量熵。这不是错误条件，实际上可能比 ES16 更频繁，因为物理熵源通常带宽较低。

- `10` - `ES16` 表示成功；低位 `seed[15:0]` 将具有 16 位随机性（ `entropy` ），无论实现如何，都保证满足某些最低熵要求。

- `11` - `DEAD` 是不可恢复的自检错误。这可能表示硬件故障、安全问题，或（极其罕见地）连续测试过程中类型 1 统计误报。在致命故障的情况下，专用安全设备中的立即锁定也可能是适当的响应。

示例。`0x8000ABCD` 是有效的 `ES16` 状态输出，`0xABCD` 是 `entropy` 值。`0xFFFFFFFF` 是无效输出（ `DEAD` ），没有 `entropy` 值。

## 32.4.2. 熵源要求

输出 `entropy`（ES16 状态下的 `seed[15:0]`）不一定是完全调节的随机性，由于较小低功耗实现的硬件和能量限制。然而，定义了最低要求。主要要求是对 256 位输入块进行 2 对 1 密码学后处理将产生 128 位"全熵"输出块。熵源用户可以做出这种保守假设，但不被禁止使用相对于期望结果熵多于两倍的种子位数。

熵源的实现应至少满足以下要求之一，才能被认为是安全的设计：

- 第 32.4.2.1 节：满足 NIST SP 800-90B (Turan et al., 2018) 标准的物理熵源，每 256 个输出位具有 192 位的评估最小熵（最小熵率 0.75）。

- 第 32.4.2.2 节：满足 AIS-31 PTG.2 (Killmann & Schindler, 2011) 标准的物理熵源，意味着平均香农熵率 0.997。源还必须满足 NIST 800-90B 最小熵率 192/256 = 0.75。

- 第 32.4.2.3 节：虚拟熵源是从物理熵源播种的 DRBG。它必须具有至少 256 位（后量子类别 5）的内部安全级别。

所有实现必须按照各自标准的要求发出初始化、测试模式和健康警报信号。这可能要求实现者以安全的方式添加非标准（自定义）测试接口，第 32.7.6 节描述了一个示例。

## 32.4.2.1. NIST SP 800-90B / FIPS 140-3 要求

必须实现 NIST SP 800-90B (Turan et al., 2018) 要求的所有组件和健康测试机制。

如果使用经过审查的调节算法（如密码学哈希）从每个 256 位（16*16 位）成功但可能不连续的 `entropy` (ES16) 输出序列中获得 128 位**全熵**，则满足熵要求。实际上，这要求最小熵率 0.75 或更高。

注意，SP 800-90B/C 评估中，128 位估计输入最小熵并不产生 128 位经调节的全熵。相反，其含义是每个 256 位序列应具有至少 128+64 = 192 位的最小熵，如 SP 800-90C (Barker et al., 2021) 中所讨论的；成功"猜测"单个 256 位输出序列的可能性不应高于 2[-192]，即使在（几乎）不受约束的熵源数据和计算能力下也是如此。

我们不是试图定义熵源必须满足的所有数学和架构属性，而是定义物理熵源必须足够强大和鲁棒，以便在 2:1 比率下进行密码学调节并以 128 位输出块通过等效的 NIST SP 800-90 全熵评估和认证。

即使要求是以 128 位全熵块定义的，我们建议使用 256 位安全性。这可以通过使用至少 512 个 `entropy` 位来初始化具有 256 位安全性的 DRBG 来实现。

## 32.4.2.2. BSI AIS-31 PTG.2 / 通用标准要求

对于替代的通用标准认证（或自认证），必须实现 AIS 31 PTG.2 类 (Killmann & Schindler, 2011)（第 4.3 节）要求的硬件组件和机制。除了 AIS-31 PTG.2 随机性要求（按该标准评估的香农熵率 0.997）外，整体最小熵要求仍然存在，如第 32.4.2.1 节所讨论。注意，800-90B 最小熵可能显著低于 AIS-31 香农熵。这两个指标不应等同或相互混淆。

## 32.4.2.3. 虚拟源：安全要求

**评论：** _虚拟源不是 ISA 合规性要求。它是为 RISC-V 安全生态系统的利益而定义的，以便虚拟系统可以具有一致的安全级别。_

虚拟源不是物理熵源，但提供额外的保护，防止在不能完全信任直接访问硬件资源的操作环境中的隐蔽信道、耗尽攻击和主机识别。尽管信任有限，实现者应尽量保证即使是这样的环境也有足够的熵可用于安全的密码学操作。

虚拟源捕获对 `seed` CSR 的访问，模拟它，或以其他方式实现它，可能无需直接访问物理熵源。输出可以是密码学安全的伪随机性而不是真实熵，但必须具有至少 256 位安全性，定义如下。虚拟源特别适用于客户操作系统、沙箱、仿真器和类似用例。

作为技术定义，针对输出的随机区分攻击应需要与对具有 256 位密钥的安全分组密码（例如 AES 256）进行穷举密钥搜索所需相当或更大的计算资源。这适用于经典和量子计算模型，但仅适用于经典信息流。虚拟源安全要求映射到后量子安全类别 5 (NIST, 2016)。

任何限制安全强度的 `seed` CSR 实现不得将其降低到 256 位以下。如果安全级别低于 256 位，则接口不得可用。

虚拟熵源不需要实现 `WAIT` 或 `BIST` 状态。如果主机 DRBG 或熵源失败且主机 DRBG 的播种材料不足，它应失败（ `DEAD` ）。

## 32.4.3. 对 **`seed`** 的访问控制

Zkr 扩展向 `mseccfg` CSR 添加了 `SSEED` 和 `USEED` 字段，用于控制从 U、S 或 HS 模式访问 `seed` CSR（参见特权 ISA 规范）。

系统应实现从较低特权模式到物理熵源的仔细考虑的访问控制策略。系统可以捕获对 `seed` 的尝试访问，并向较低特权客户端提供**虚拟熵源**数据（第 32.4.2.3 节），而不是调用 SP 800-90B（第 32.4.2.1 节）或 PTG.2（第 32.4.2.2 节）**物理熵源**。模拟的 `seed` 数据生成使用适当播种的安全软件 DRBG 完成。与直接访问熵源相关的安全考虑见第 32.7.3.5 节。

实现可以将 `mseccfg` 实现为 `[s,u]seed` 是只读常量值 `0`。软件可以通过向 `[s,u]seed` 写入 `1` 并读回结果来发现是否可以启用 U 和 S 模式访问 `seed` CSR。

## **给软件开发人员的注意事项**

**评论：** _未能防止通过直接时序信道泄漏敏感参数被视为严重的安全漏洞，通常将导致 CERT CVE 安全公告。_

## 32.5.1. 范围和目标

在程序员和 RISC-V 实现之间建立了一个"ISA 契约"，即 Zkt 指令不会通过执行延迟的差异泄露有关已处理秘密数据（明文、密钥信息或其他"敏感安全参数"——FIPS 140-3 术语）的信息。Zkt **不**定义核心中可用的指令集；它只是限制某些指令的行为（如果这些指令被实现）。

目前，本文档的范围在标量 RV32/RV64 处理器内。向量密码学指令（以及适当的向量支持指令）将在以后添加，其他希望断言无泄漏执行延迟属性的安全相关功能也将如此。

加载、存储、条件分支被排除，以及一组很少需要处理秘密数据的指令。还有由于其他 ISA 处理器的限制而在标准密码学中间件中存在变通方法的指令也被排除。

所述目标是 OpenSSL、BoringSSL（Android）、Linux 内核和类似的受信软件在 Zkt 启用的 RISC-V 目标上编译和运行时不会有直接可观察的时序侧信道。Zkt 扩展明确说明了密码学开发人员所做的许多常见延迟假设。

供应商不必实现列表中的所有指令即可符合 Zkt；但是，如果他们声称拥有 Zkt 并实现了任何列出的指令，则该指令必须具有数据无关延迟。

例如，许多简单的 RV32I 和 RV64I 核心（没有乘法、压缩、位操作或密码学扩展）在技术上是符合 Zkt 的。可以使用"位片"技术在其上实现常量时间 AES，但与使用 AES 指令的实现相比会非常慢。在没有 Zkt 证明的核心上，即使是位片密码实现（主要基于布尔逻辑指令）也不能保证安全。

遵循 Zkt 的乱序实现仍然可以自由地融合、拆分、更改甚至忽略指令序列，只要优化是确定性地应用的，而不是基于操作数数据。指导原则应是不应根据执行延迟泄露有关被操作数据的任何信息。

**评论：** _留给未来的扩展或其他技术来解决使用值预测或其他数据依赖方式的具有高级乱序能力的实现中数据无关执行的问题。_

## 32.5.2. 背景

- 时序攻击比 2010 年代之前意识到的要强大得多，这导致了当前密码学代码库中的重大缓解努力。
- 密码学开发人员使用静态和动态安全测试工具来跟踪秘密信息的处理，并检测其影响分支或用于表查找的场合。
- Zkt 的架构测试可以是务实和半形式化的；通过有意识地以避免数据依赖延迟的方式实现（相关的迭代多周期指令或由微操作组成的指令），通常可以实现针对基本时序攻击的**安全设计**。
- 实验室测试可以利用统计时序攻击泄露分析技术，如 ISO/IEC 17825 (ISO, 2016) 中所述。
- 二进制可执行文件不应在指令编码中包含秘密（Kerckhoffs 原则），因此指令时序可能泄露有关立即数、输入寄存器顺序等的信息。在二进制加载器为重定位目的修改可执行文件且希望保持执行位置（PC）秘密的系统中，这可能存在例外。这就是 LUI、AUIPC 和 ADDI 等指令在列表中的原因。
- 审计工具使用的规则相对简单易懂。简而言之，我们将明文、秘密密钥、扩展密钥、nonce 和其他此类变量称为"秘密"。秘密变量（算术上）修改任何其他变量/寄存器也会将其变为秘密。如果秘密最终出现在影响加载或存储的地址计算中，那就是违规。如果秘密影响分支条件，那也是违规。秘密变量位置或寄存器通过特定的清零/净化或通过被声明为密文（或其他不再秘密的信息）变为非秘密。本质上，秘密在是秘密时只能"触及" Zkt 列表上的指令。

## 32.5.3. 特定指令的合理性

- HINT 指令形式（通常是 _rd_ = `x0` 的编码）被排除在数据无关时间要求之外。
- 浮点（F、D、Q、L 扩展）目前被排除在常量时间要求之外，因为它们在标准化密码学中应用很少。如果特定算法（如 PQC 签名算法 Falcon）变得关键，我们可能考虑为某些浮点扩展添加浮点加、减、乘作为常量时间要求。
- 密码学家通常假设除法是可变时间的（而乘法是常量时间），并基于该假设实现其 Montgomery 约简例程。
- Zicsr、Zifencei 被排除。
- 某些指令在列表中仅仅是因为我们认为将它们包含在测试范围内没有害处。

## 32.6.4.6. 交叉开关置换指令

```
RV32, RV64:
    xperm4 rd, rs1, rs2
    xperm8 rd, rs1, rs2
```

`xperm4` 指令按半字节操作。`GPR[rs1]` 包含一个 `XLEN/4` 个 4 位元素的向量。`GPR[rs2]` 包含一个 `XLEN/4` 个 4 位索引的向量。结果是 `GPR[rs2]` 中的每个元素被 `GPR[rs1]` 中索引元素替换，如果 `GPR[rs2]` 中的索引超出范围，则为零。

`xperm8` 指令按字节操作。`GPR[rs1]` 包含一个 `XLEN/8` 个 8 位元素的向量。`GPR[rs2]` 包含一个 `XLEN/8` 个 8 位索引的向量。结果是 `GPR[rs2]` 中的每个元素被 `GPR[rs1]` 中索引元素替换，如果 `GPR[rs2]` 中的索引超出范围，则为零。

**评论：** _该指令可用于实现任意位置换。对于密码学，它们可以加速位片实现、分组密码的置换层、基于掩码的对策和 SBox 操作。_

_使用 4 位 SBox 的轻量级分组密码包括：PRESENT、Rectangle、GIFT、Twine、Skinny、MANTIS、Midori。_

_使用 8 位 SBox 的国家密码包括：Camellia（日本）、Aria（韩国）、AES（美国、比利时）、SM4（中国）、Kuznyechik（俄罗斯）。_

_所有这些 SBox 都可以使用_ `xperm8` _指令在常量时间内高效实现。注意，此技术也适用于基于掩码的侧信道对策。_


## 32.7. 熵源合理性和建议

此非规范性附录侧重于熵源的合理性、安全性、自认证和实现方面。因此，我们还讨论了密码学标准合规性和安全测试可能需要的非 ISA 系统特性。

## 32.7.1. 设计和自认证检查清单

密码学系统的安全性基于秘密位和密钥。这些位需要是随机的，并源自密码学安全的随机位生成器（RBG）。构建安全的 RBG 需要熵源（ES）。

虽然熵源实现不必是经过认证的设计，但 RISC-V 期望它们以兼容的方式运行，并且不会给用户带来不必要的安全风险。遵循适当安全标准的自我评估和测试通常是实现这一目标所必需的。

- ISA 架构测试。尽可能验证本规范中的 RISC-V ISA 要求是否被正确实现。这包括状态转换（第 32.4 节和第 32.7.6 节）、访问控制（第 32.4.3 节），以及 `seed` ES16 `entropy` 字只能破坏性读取。ISA 架构测试的范围是那些独立于物理熵源细节的行为。烟雾测试 ES 模块在设计阶段可能有帮助。

- 熵的技术论证。这可以采取随机模型或启发式论证的形式，解释为什么噪声源输出来自随机过程而非伪随机（确定性）过程，且不容易预测或外部观察。不需要完整的物理模型；可以引用研究文献。

- 熵源设计审查。熵源不仅仅是噪声源，还必须具有健康测试（第 32.7.4 节）、调节器（第 32.7.2.2 节）和具有明确定义接口的安全边界等特性。

- 实验测试。原始噪声源按照 NIST 800-90B 第 3 节的定义进行熵估计。还需要通过实验证明调节器和健康测试组件能够适当地工作以满足 ES16 输出熵要求。

- 弹性。上述物理工程步骤应考虑设备的运行环境，该环境可能是意外的或敌对的。

**评论：** _RISC-V 熵源规范的目标之一是，标准的 90B 熵源模块或 AIS-31 RNG IP 可以从第三方获得许可并与 RISC-V 处理器设计集成。与较旧的（FIPS 140-2）RNG 和 DRBG 模块相比，熵源模块可能具有相对较小的面积（仅几千个 NAND2 门等效）。CMVP 正在引入"熵源验证范围"，这潜在地允许 90B 验证被重用于不同的（FIPS 140-3）模块。_

## 32.7.2. 标准和术语

作为一项基本安全功能，随机数的生成受众多标准和技术评估方法的约束，主要的是美国联邦使用所需的 FIPS 140-3 和国际高安全性评估中使用的通用标准方法（Common Criteria Methodology）。

注意，FIPS 140-3 与其前身 FIPS 140-2 相比是一个显著更新的标准，仅在 2020 年代才开始使用。

这些标准为 RISC-V 熵源设计设定了许多技术要求，我们尽可能使用它们的术语。

`seed` CSR 提供熵源（ES）接口，而不是有状态的随机数生成器。因此，它可以支持任意安全级别。密码学（AES、SHA-2/3）ISA 扩展可用于构建从熵源播种的高速 DRBG。

## 32.7.2.1. 熵源（ES）

熵源通过采样和处理来自噪声源的数据构建。我们在此工作中仅考虑真实随机性的物理源。由于这些直接基于自然现象并受到环境条件的影响（可能是敌对的），它们需要监控这些源的"健康"和质量的功能。

物理熵源的要求在美国联邦 FIPS 140-3 评估的 NIST SP 800-90B（第 32.4.2.1 节）和高安全性通用标准评估的 BSI AIS-31（第 32.4.2.2 节）中规定。这些标准强制要求的健康测试和熵度量类型存在一些分歧，RISC-V 支持这两种替代方案。

## 32.7.2.2. 调节：密码学和非密码学

原始物理随机性（噪声）源很少是统计完美的，一些源生成非常大量的位，需要"去偏"并减少到较少的位数。这个过程称为调节。安全哈希函数是密码学调节器的一个例子。重要的是要注意，即使哈希可能使任何数据看起来随机，但它不会增加其熵含量。

非密码学调节器和提取器（如 von Neumann 的"去偏硬币抛掷"）更容易高效实现，但可能比密码学哈希减少更多的熵含量（在移除的单个位中），密码学哈希非常有效地混合输入熵。然而，它们不需要密码分析或计算硬度假设，因此本质上更具未来证明性。更详细的讨论见第 32.7.5.5 节。

## 32.7.2.3. 伪随机数生成器（PRNG）

伪随机数生成器（PRNG）使用确定性数学公式从较少量的"种子"随机性创建大量随机数。PRNG 也分为密码学和非密码学的。

非密码学 PRNG（如许多编程库中的 LFSR 和线性同余生成器）可能生成统计上令人满意的随机数，但绝不能用于密码学密钥生成。这是因为它们不是为抵抗**密码分析**而设计的；通常可以从某些输出中数学推导出 PRNG 的"种子"或内部状态。这是一个安全问题，因为知道状态使攻击者能够计算未来或过去的输出。

## 32.7.2.4. 确定性随机位生成器（DRBG）

密码学 PRNG 也称为确定性随机位生成器（DRBG），这是 SP 800-90A 使用的术语。强密码学算法如 AES 或 SHA-2/3 用于从种子产生随机位。秘密种子材料就像密码学密钥；从 DRBG 输出确定种子与破解 AES 或强哈希函数一样困难。这也说明了种子/密钥需要足够长并来自受信任的熵源。DRBG 仍应经常刷新（重新播种）以实现前向和后向安全性。


## 32.7.3. 具体合理性和考量

## 32.7.3.1. **`seed`** CSR

该接口被设计为简单，以便供应商和设备无关的驱动程序组件（例如，在 Linux 内核、嵌入式固件或密码学库中）可以使用 `seed` 生成真正的随机位。

熵源不需要高带宽接口；单个 DRBG 源初始化仅需要 512 位（256 位熵），DRBG 输出可由任意数量的调用者共享。一旦启动，DRBG 仅需要新熵来缓解状态泄露的风险。

从安全角度来看，读取时刷新秘密熵位的副作用是至关重要的。因此，我们对此特定 CSR 强制要求写入操作。

阻塞指令可能更易于使用，但大多数用户应该查询 (D)RBG 而不是熵源。没有轮询风格的机制，熵源在某些情况下可能挂起数千个周期。`wfi` 或 `pause` 机制（至少潜在地）允许在 MCU 上节能睡眠，在高端 CPU 上进行上下文切换。

特定 `OPST = seed[31:0]` 两位机制的原因是提供冗余。"故障"位组合 `11` ( `DEAD` ) 和 `00` ( `BIST` ) 更可能因电气原因在功能发现失败且熵源实际上不可用时出现。

16 位带宽是一个折中，其动机是希望在返回值中提供冗余、对潜在功耗/EM 泄露的一些保护（通过第 32.7.5.6 节讨论的 2:1 密码学调节进一步缓解），以及希望在 RV32 和 RV64 架构上所有位"在同一位置"以便于编程。

## 32.7.3.2. NIST SP 800-90B

SP 800-90C 指出，每个 n 位的经调节块需要 n+64 位输入熵才能达到全熵。因此，NIST SP 800-90B 最小熵评估必须保证每个 256 位块至少 128 + 64 = 192 位输入熵。只有这样，来自熵源的 16 * 16 = 256 位的哈希才会产生期望的 128 位全熵。这意味着最小熵率为 192/256=12/16=0.75。期望的香农熵要大得多。

在 FIPS 140-3 / SP 800-90 分类中，RBG2(P) 构造是一个密码学安全的 RBG，具有对物理熵源 ( `seed` ) 的连续访问，输出由完全播种的安全 DRBG 生成。熵源还可用于构建 RBG3 全熵源。输出字的连接对应于 `Get_ES_Bitstring` 函数。

128 位输出块大小被选择，因为那是在 (Turan et al., 2018) 附录 F 中指定的 CBC-MAC 调节器的输出大小，也是我们预期在应用中看到的最小密钥大小。

如果选择 NIST SP 800-90B 认证，熵源应至少实现 (Turan et al., 2018) 第 4.4 节中定义的健康测试：重复计数测试和自适应比例测试，或者表明相同的缺陷将由供应商定义的测试检测到。

## 32.7.3.3. BSI AIS-31

PTG.2 是 BSI AIS 20/31 中定义的安全和功能类之一。PTG.2 源要求作为其他类型 BSI 生成器（例如，DRBG，或通过适当软件后处理的 PTG.3 TRNG）的构建块。

为验证目的，PTG.2 要求可映射到安全控制 T1-3（第 32.7.4 节）和接口如下：
- P1 [PTG.2.1] 启动测试映射到 T1 和复位触发（按需）的 `BIST` 测试。
- P2 [PTG.2.2] 连续测试完全失败映射到 T2 和 `DEAD` 状态。
- P3 [PTG.2.3] 在线测试是 T2 的连续测试——在 `BIST` 状态下阻止熵输出。
- P4 [PTG.2.4] 与设计有效的熵源健康测试相关，我们鼓励这样做。
- P5 [PTG.2.5] 原始随机序列可通过 GetNoise 接口检查（第 32.7.6 节）。
- P6 [PTG.2.6] 测试程序 A 是评估过程的一部分，我们建议即使不寻求 AIS-31 认证也使用这些测试进行自我评估。
- P7 [PTG.2.7] "内部随机位"的平均香农熵超过 0.997。

注意 P7 涉及香农熵，而不是 NIST 源的最小熵。因此，最小熵要求也需要说明。按 AIS-31 标准构建和认证的 PTG.2 模块也可以在 2:1 密码学调节后满足"全熵"条件，但不一定如此。技术验证过程有些不同。

## 32.7.3.4. 虚拟源

所有不是直接物理源（满足 SP 800-90B 或 AIS-31 PTG.2 要求）的源都需要满足虚拟熵源的安全要求。假设虚拟熵源不是限制性的共享带宽资源（而是软件 DRBG）。

DRBG 可用于供给其他（虚拟）DRBG，但这不会增加系统中熵的绝对量。熵源必须能够支持当前和未来的安全标准和应用。256 位要求映射到 NIST 后量子密码学的"类别 5"以及 Suite B 和更新的美国政府 CNSA Suite 中的 TOP SECRET 方案。

## 32.7.3.5. 直接硬件访问的安全考量

ISA 实现和系统设计必须努力确保硬件-软件接口最小化对抗信息流的途径，即使规范中没有明确禁止。

出于安全原因，虚拟化需要对物理熵输出进行调节和 DRBG 处理。如果单个物理熵源在多个不同的虚拟机之间共享，或者客户操作系统不受信任，建议这样做。虚拟熵源对耗尽攻击具有显著更强的抵抗力，也降低了隐蔽信道的风险。

直接的 `mseccfg.[s,u]seed` 选项允许围绕组件绘制安全边界，涉及敏感安全参数（SSP）流，即使该组件不在 M 模式下。这在实现受信飞地时很有帮助。此类模块可以强制整个密钥生命周期从诞生（在熵源中）到死亡（清零）发生，而密钥不会跨越边界传递给外部代码。

**耗尽**：主动轮询可能使熵源对另一个同时运行的消费者不可用。这可以（例如）延迟该虚拟机的实例化，如果它需要熵来完全初始化。

**隐蔽信道**：对熵源等组件的直接访问可用于跨安全边界建立通信信道。一个消费者的主动轮询使资源对另一个（不频繁轮询的）消费者不可用，变为 WAIT 而不是 ES16。此类交互可用于建立低带宽信道。

**硬件指纹**：熵源（及其噪声源电路）可能具有唯一可识别的硬件"签名"。这在某些应用中可能是无害的甚至有用的（因为随机源可能表现出类似物理不可克隆函数（PUF）的特性），但在其他应用中非常不期望（匿名虚拟化环境和飞地）。DRBG 掩盖了此类统计特征。

**侧信道**：针对现实密码系统的一些最具破坏性的实际攻击使用了看似无关紧要的附加信息，如填充错误消息或时序信息。

我们敦促实现者不要通过状态或自定义位创建不必要的信息流，或允许任何其他机制禁用或影响熵源输出。所有信息流和交互机制都必须从对抗性角度进行考虑：越少越好。

作为侧信道分析的示例，我们注意到熵轮询接口通常不是"常量时间"的。需要分析通过时序预言机泄露了何种信息；一种方法是将其建模为拒绝采样器。这样的时序预言机可以揭示有关噪声源类型和熵源使用的信息，但不能揭示随机输出 `entropy` 位本身。如果确实如此，则需要额外的对策。


## 32.7.4. 安全控制和健康测试

密码学熵源的主要目的是产生秘密密钥材料。在几乎所有情况下，硬件熵源必须实现适当的**安全控制**以保证不可预测性、防止泄露、检测攻击，并拒绝对抗性控制熵输出或其生成机制。明确的安全控制是安全测试和认证所必需的。

内建于设备的许多安全控制称为"健康检查"。健康检查可以采取完整性检查、启动测试和按需测试的形式。这些测试可以在硬件或固件中实现，通常是两者兼有。若干项由 NIST SP 800-90B 等标准强制要求。适当健康测试的选择取决于认证目标、系统架构、威胁模型、熵源类型和其他因素。

健康检查并非用于硬件诊断，而是用于检测安全问题。因此，在故障情况下的默认操作应旨在损害控制：限制进一步输出并防止生成弱密码学密钥。

我们讨论三个具体的测试要求 T1-T3。测试要求源自熵源的定义；没有它，该模块仅仅是一个噪声源，无法信任其安全生成密钥材料。

## 32.7.4.1. T1：按需测试

通过复位、重启或上电硬件（非 ISA 信号）调用一系列简单测试。在初始启动自检期间，实现将简单地返回 `BIST` ；在任何情况下，驱动程序必须等待它们完成后才能开始密码学操作。在失败时，熵源将进入无输出的 `DEAD` 状态。

合理性：从软件侧与硬件自检机制的交互应最小化；术语"按需"并不意味着最终用户或应用程序应该能够在现场调用它们。

## 32.7.4.2. T2：连续检查

如果在连续测试或环境传感器中检测到错误，熵源将进入无输出状态。我们定义，如果熵源从活跃状态（ `WAIT` 或 `ES16` ）返回到 `BIST` 状态，则发出非关键警报信号。关键故障将立即导致 `DEAD` 状态。基于硬件的连续测试机制不得使统计信息在外部可用，并且必须定期或通过复位、上电或类似信号按需清零。

合理性：当设备运行时可能发生物理攻击。设计应避免通过揭示详细状态信息来引导此类主动攻击。检测到攻击后，默认操作应旨在损害控制——防止生成弱密码学密钥。

某些测试的统计性质使"类型 1"误报成为可能。也可能需要发出非致命警报信号；AIS 31 规定了即使设备功能正常也可能以不可忽略的概率发生的"噪声警报"；这些可以用 `BIST` 发出信号。在无操作员的自主系统中，对非致命警报条件很少有可以或应该做的事情。

统计运行时健康检查（如计数器）的状态可能与某些秘密密钥材料潜在相关，因此有清零要求。

## 32.7.4.3. T3：致命错误状态

由于大多数密码学操作的安全性取决于熵源，系统范围的"默认拒绝"安全策略方法适用于大多数熵源故障。硬件测试失败应至少导致 `DEAD` 状态，并可能复位/停止。这是一个致命问题：如果不能保证熵源的安全操作，则**不得**允许其（或其密码学客户端应用程序）运行。

合理性：这些测试可以补充其他完整性和防篡改机制。

某些硬件随机生成器由于其物理构造而暴露在相对非对抗性的环境和制造问题中。然而，即使是这种"无害"的故障模式也可能指示**故障攻击**，因此应作为系统完整性故障而不是诊断问题来处理。

安全架构师将理解仅在测试阈值使得整个设备生命周期内误报概率可忽略时才使用永久性或难以恢复的"安全熔丝"锁定。

## 32.7.4.4. 信息流

在密码学中，此类带外信息源称为"预言机"。

为保证敏感数据不会被读取两次，并且不同的调用者不会获得相关的输出，要求硬件在每次读取（成功轮询）期间对随机性通路实现**读时擦除**。出于同样的原因，只有完整且完全处理的随机字才应通过 `entropy`（ `seed` 的 ES16 状态）提供。

这也适用于原始噪声源。原始源接口已委托给可选的供应商特定测试接口。重要的是，测试接口和主接口不应同时运行。

噪声源状态应在最大程度上受到保护，免受对抗性知识或影响。用于此的方法应予以记录，包括描述（概念上的）安全边界在保护噪声源免受对抗性观察或影响方面的角色。

—— NIST SP 800-90B，噪声源要求

熵源是一个单一资源，会受到耗尽和隐蔽信道的影响。观察熵可能等同于观察噪声源输出，因为密码学调节仅作为后处理步骤强制要求。SP 800-90B 和其他安全标准强制要求保护噪声位免受观察和影响。

## 32.7.5. 实现策略

作为一般规则，RISC-V 仅规定 ISA。我们提供一些额外建议，以便可以创建可移植的、供应商无关的中间件和内核组件。实际的硬件实现和认证留给供应商和电路设计者；本节中的讨论纯粹是信息性的。

在考虑实现选项和权衡时，必须着眼于整个信息流：

1. 噪声源从稳定且充分理解的物理随机事件生成私密的、不可预测的信号。
2. 采样将噪声信号数字化为原始位流。此原始数据也需要受到设计的保护。
3. 连续健康测试确保噪声源及其环境满足其运行参数。
4. 非密码学调节器去除输入噪声中的大部分偏差和相关性。
5. 密码学调节器产生全熵输出，完全与理想随机无法区分。
6. DRBG 接收 `>=256` 位种子熵作为密钥材料，并使用"单向"密码学过程按需快速生成位（而不透露种子/状态）。

步骤 1-4（可能 5）被视为熵源 (ES) 的一部分，由 `seed` CSR 提供。添加软件侧的密码学步骤 5-6 和控制逻辑将其补充为真随机数生成器 (TRNG)。

## 32.7.5.1. 环形振荡器

我们将给出一些可以在处理器本身中实现（使用标准单元）的常见噪声源的示例。

当今生产中使用的最常见的熵源类型基于"自由运行"环形振荡器及其时序抖动。在此，奇数个反相器连接成一个环路，相对于参考时钟从中采样噪声源位。如果采样率足够低，采样位序列可能期望是相对不相关的（接近 IID）。然而，通常需要进一步处理。

AMD、ARM 和 IBM 是用于高安全性应用的环形振荡器 TRNG 的示例。

还有相关的基于亚稳态的生成器设计，如过渡效应环形振荡器 (TERO)。差分/反馈 Intel 构造略有不同，但也属于同一通用的亚稳态振荡器类别。

环形振荡器的主要好处是：(1) 它们可以使用标准单元库实现而无需外部组件——甚至可以在 FPGA 上实现，(2) 存在关于其行为的既定理论，以及 (3) 存在充足的先例用于在最高安全级别进行测试和认证。

环形振荡器也有众所周知的实现陷阱。它们的输出有时高度依赖温度，这在测试和建模中必须考虑。如果环形振荡器构造是并行的，重要的是每个链中的级数和/或反相器数量要合适，以避免由于谐波"Huyghens 同步"导致的熵减少。此类谐波也可以在频率注入攻击中被恶意插入，这可能产生毁灭性的结果。对策与电路设计有关；环境传感器、电气滤波器和差分振荡器的使用可能有所帮助。

## 32.7.5.2. 散粒噪声

由离散事件组成并建模为泊松过程的随机源类别称为"散粒噪声"。认证它们有长期先例；AIS 31 文档本身提供了基于噪声二极管的参考设计。散粒噪声源通常比环形振荡器更能抵抗温度变化。这些生成器中的一些也可以完全使用标准单元实现。


## 32.7.5.3. 其他类型的噪声

可能可以认证更奇特的噪声源和设计，尽管它们的随机模型需要同样充分理解，且其 CPU 接口必须安全。关于量子熵源的讨论见第 32.7.5.8 节。

## 32.7.5.4. 连续健康测试

健康监控需要维护与噪声源相关的一些状态信息。测试应以特定数量的样本保证状态刷新（无挂起状态）的方式设计。我们建议刷新大小 `W =< 1024` 以匹配 NIST SP 800-90B 要求的测试。在系统复位时状态也会完全清零。

两个强制测试可以用最少的电路构建。不需要完整的直方图，只需要简单的计数器寄存器：重复计数、窗口计数和样本计数。每当输出样本值变化时，重复计数重置；如果计数达到某个截止限制，则发出噪声警报 ( `BIST` ) 或失败 ( `DEAD` ) 信号。窗口计数器用于保存每隔 W 个输出。在后续窗口中计算此参考样本的频率；截止值在标准中定义。我们看到，强制测试的结构使得，如果实现良好，不会携带超过 `W` 个样本限制的信息。

SP 800-90B 第 4.5 节明确允许额外的开发者定义测试，在 FIPS 140-1 的早期版本中定义了更多测试（后来被"划掉"）。额外测试的选择取决于物理源的性质和实现。

特别是如果在硬件中使用非密码学调节器，AIS 31 在线测试可能由驱动程序软件实现。它们也可以在硬件中实现。对于某些安全配置文件，AIS 31 强制要求其容差设置在"正常使用"下每年警报概率至少为 10[-6] 的方式。此类要求在现代应用中是有问题的，因为对于关键系统来说其概率太高。

对于无操作员的自主系统中的非致命警报条件，很少有可以或应该做的事情。然而，AIS 31 允许 DRBG 组件在其熵源失败的情况下继续运行，因此我们建议重新进入临时 `BIST` 状态（第 32.7.4 节）以在必要时应发出非致命统计错误信号。驱动程序和应用程序可以对此做出适当的反应（或简单地记录它），但这不会直接影响 TRNG 的可用性。永久错误条件应导致 `DEAD` 状态。

## 32.7.5.5. 非密码学调节器

如第 32.7.2.2 节所述，物理随机性源通常需要一个称为**调节**的后处理步骤来满足期望的质量要求，这些要求在第 32.4.2 节中概述。

此接口采取的方法是允许非密码学和密码学过滤的组合进行。第一阶段（硬件）仅需要能够将熵蒸馏到舒适地高于必要水平。

- 可以从噪声源中取出一组位并将它们异或在一起，以产生偏差更小（且更独立）的位。然而，这样的异或可能引入"伪随机性"并使输出难以分析。
- von Neumann 提取器查看连续的位对，拒绝 00 和 11，并分别为 01 和 10 输出 0 或 1。它将位数减少到原来的不到 25%，但输出在可证明上无偏（假设独立性）。
- Blum 提取器可用于其行为类似 N 状态 Markov 链的源。如果其假设成立，它也消除依赖关系，创建独立同分布 (IID) 的源。
- 其他线性和非线性校正器，如 Dichtl 和 Lacharme 讨论的那些。

注意，硬件也可以在熵源中实现完整的密码学调节器，尽管软件驱动程序仍然需要密码学调节器（第 32.4.2 节）。

合理性：非密码学提取器的主要优势在于其能效、相对简单性和对数学分析的适应性。如果设计良好，它们可以与噪声源本身的随机模型一起评估。它们不需要计算硬度假设。

## 32.7.5.6. 密码学调节器

为安全使用，ISA 边界软件侧始终需要密码学调节器。如果必要，它们也可以在硬件侧实现。在任何情况下，`entropy` ES16 输出在用作密钥材料或被认为是"全熵"之前，必须始终压缩 2:1（或更多）。

密码学调节器的示例包括 Linux 操作系统的随机池、安全哈希函数（SHA-2/3、SHAKE）和 SP 800-90B 附录 F 中的 AES / CBC-MAC 构造。

在某些构造中，如 Linux RNG 和基于 SHA-3/SHAKE 的生成器，密码学调节和输出 (DRBG) 生成由同一组件提供。

合理性：对于许多低功耗目标构造，Intel 和 AMD 使用的硬件 AES CBC-MAC 调节器类型将过于复杂和耗能，无法仅为了服务 `seed` CSR 而实现。另一方面，如果要求高质量随机输出，更简单的非密码学调节器可能在输入熵上过于浪费——（ARM TrustZone TRBG 在 200 MHz 时仅输出 10Kbit/sec。）因此，在硬件和软件生成之间做出了节省资源的折中。

## 32.7.5.7. 最终随机：DRBG

到达最终用户和应用程序的所有随机位必须来自密码学 DRBG。这些通常由驱动程序组件在软件中实现。如果可用，应使用 RISC-V AES 和 SHA 指令集扩展，因为它们提供了额外的安全特性，如时序攻击抵抗力。

目前推荐的 DRBG 在 NIST SP 800-90A (Rev 1) 中定义：`CTR_DRBG`、`Hash_DRBG` 和 `HMAC_DRBG`。认证通常要求对称组件和整个 DRBG 的已知答案测试 (KAT)。这些在软件中实现比在硬件中显著容易。除了可直接认证的 SP 800-90A DRBG 外，可以使用基于 ChaCha20 的 Linux 风格随机池构造，或基于 SHAKE256 的适当构造。

这些只是建议；程序员可以调整 CPU 熵源的使用以满足未来要求。

## 32.7.5.8. 量子与经典随机

NCSC 相信经典 RNG 将在可预见的未来继续满足我们对政府和军事应用的需求。—— 英国 NCSC QRNG 指南，2020 年 3 月

量子随机数生成器 (QRNG) 是一种 TRNG，其随机性来源可以被明确识别为特定的量子现象，如量子态叠加、量子态纠缠、海森堡不确定性、量子隧道效应、自发辐射或放射性衰变。

直接量子熵在理论上是最好的熵。基于电子噪声的典型 TRNG 也在很大程度上基于量子现象，并且同样不可预测——区别在于对于经典 TRNG 来说，所涉及的量子物理学和经典物理学的相对量难以量化。

QRNG 的设计方式允许对量子起源熵的量进行建模和估计。这种区别在 QKD（量子密钥分发）安全机制所使用的安全模型中很重要，该机制可用于通过直接使用量子力学效应来保护物理层（如光纤电缆）免受拦截。

这种安全模型意味着许多可用的 QRNG 设备不使用密码学调节，可能无法满足密码学统计要求。许多实现者可能认为它们是熵源而不是 TRNG。

关于 QRNG 实现安全性的研究相对较少，但许多 QRNG 设计可以说比经典生成器（如环形振荡器）更容易受到泄露，因为它们倾向于使用外部组件和混合材料。例如，光子探测器信号的放大可能在功耗分析中可观察，而经典基于噪声的源被设计为抵抗这一点。

## 32.7.5.9. 后量子密码学

PQC 公钥密码学标准不要求量子起源的随机性，只要求足够安全的密钥材料。回想一下，密码学旨在保护数据本身的机密性和完整性，并不对物理通信信道（如 QKD）提出任何要求。

经典优质 TRNG 完全适合为经典计算机上可实现但量子计算机难以破解的 PQC 协议生成秘密密钥。在密码学中重要的是秘密密钥具有足够的真实随机性（熵），并且它们被安全地生成和存储。

当然，必须避免基于量子计算机容易解决的问题的 DRBG，如 Blum-Blum-Shub 生成器情况下的因子分解。大多数对称算法不受影响，因为最好的量子攻击相对于密钥大小仍然是指数的。

作为示例，原始的 Intel RNG，其输出生成基于 AES-128，可以使用 Grover 算法以大约平方根的努力进行攻击。虽然即使是"64 位"量子安全性也极难破解，但许多应用规定更高的安全要求。NIST 将 AES-128 定义为"类别 1"等效后量子安全性，而 AES-256 是"类别 5"（最高）。我们通过暴露对熵源的直接访问来避免这个可能的未来问题，该熵源可以仅从信息论假设中推导出其安全性。

## 32.7.6. 建议的 GetNoise 测试接口

熵源的合规性测试、表征和配置需要访问原始的、未调节的噪声样本。此概念测试接口在 NIST SP 800-90B 第 2.3.2 节中命名为 GetNoise。

由于这种类型的接口对于安全测试是必要的，并且也构成密码学密钥生成过程的潜在后门，我们定义了一个安全行为，兼容的实现可以在测试期间暂时禁用熵源 `seed` CSR 接口。

为了使共享的 RISC-V 自认证脚本（和驱动程序）能够以安全的方式适应测试接口，我们建议它被实现为一个自定义的、仅 M 模式的 CSR，在此表示为 `mnoise`。

此非规范性接口不打算用作随机性源或其他生产用途。我们为此接口定义了单个位的语义，`mnoise[31]`，命名为 `NOISE_TEST`，如果实现，将影响 `seed` 的行为。

当 `mnoise` 中的 `NOISE_TEST = 1` 时，`seed` CSR 不得通过 `ES16` 返回任何内容；除非源是 `DEAD` ，否则应处于 `BIST` 状态。当 `NOISE_TEST` 再次禁用时，熵源应通过适当的清零和自检机制从 `BIST` 返回。

其他输入和输出位的行为主要留给供应商（因为它们取决于物理熵源的技术细节），自定义 `mnoise` CSR 的地址也是如此。CSR 的其他内容和行为只能在 `mvendorid`、`marchid` 和 `mimpid` CSR 标识符的上下文中解释。

当未实现时（例如，在虚拟机中），`mnoise` 可以永久读为零 ( `0x00000000` ) 并忽略写入。当可用但 `NOISE_TEST = 0` 时，`mnoise` 可以返回非零常量（例如 `0x00000001` ）但不返回噪声样本。

 * Byte 0 of state is input column 0, bits  7..0.
 * Byte 5 of state is input column 1, bits 15..8.
