# 第10章 "Zimop" 可能操作扩展，版本 1.0

本章定义了 "Zimop" 扩展，引入了 _可能操作_（MOPs）指令的概念。MOP 最初被定义为简单地向 `x[rd]` 写入零，但被设计为可被后续扩展重新定义以执行其他某些动作。Zimop 扩展为 40 个 MOP 定义了编码空间。

_有时定义这样的指令集扩展是很有用的：当该扩展未实现时，其指令不引发非法指令异常，而是不采取有用动作（除了写入_ `x[rd]` _）。例如，具有控制流完整性检查的程序可以在没有相应扩展的实现上正确执行，只要这些检查被简单地忽略即可。将这些检查实现为 MOP 允许相同的程序在有或没有相应扩展的实现上运行。_

_尽管在某些方面类似于 HINT，MOP 不能被编码为 HINT，因为与 HINT 不同，MOP 允许改变架构状态。_

_由于 MOP 可能被后续扩展重新定义，标准软件不应执行 MOP，除非它有意针对一个已重新定义该 MOP 的扩展。_

Zimop 扩展定义了 32 条 MOP 指令，命名为 MOP.R._n_，其中 _n_ 是介于 0 到 31（含）之间的整数。除非被另一个扩展重新定义，这些指令简单地写入 0 到 `x[rd]`。其编码允许未来扩展定义它们读取 `x[rs1]` 以及写入 `x[rd]`。

_MOP.R.n 的推荐汇编语法是 MOP.R.n rd, rs1，任何_ `x` _寄存器标识符对任一参数都是有效的。类似地，对于 MOP.RR.n，推荐语法是 MOP.RR.n rd, rs1, rs2。重新定义 MOP 的扩展可以定义替代的汇编助记符。_

_这些 MOP 编码在 SYSTEM 主操作码中，部分原因在于预期它们的行为将由特权 CSR 状态调制。_

_这些 MOP 被定义为向_ `x[rd]` _写入零，而不是不执行操作，以简化指令解码并允许通过判断结果的零与否来测试特性的存在。_

Zimop 扩展中定义的 MOP 不携带从 `x[rs1]` 或 `x[rs2]` 到 `x[rd]` 的句法依赖，但重新定义该 MOP 的扩展可以施加这样的要求。

_不携带句法依赖使得简单实现无需读取_ `x[rs1]` _和_ `x[rs2]` _。_

## 10.1. "Zcmop" 压缩可能操作扩展，版本 1.0

本节定义了 "Zcmop" 扩展，该扩展定义了八条 16 位 MOP 指令，命名为 C.MOP._n_，其中 _n_ 是介于 1 到 15（含）之间的奇整数。C.MOP._n_ 编码在对应于 C.LUI x_n_, 0 的保留编码空间中，如表 10 所示。与 Zimop 扩展中定义的 MOP 不同，C.MOP._n_ 指令被定义为 _不_ 写入任何寄存器。其编码允许未来扩展定义它们读取寄存器 `x[`_`n`_`]`。

Zcmop 扩展依赖于 Zca 扩展。
